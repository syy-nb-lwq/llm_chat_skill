## 本地单用户化改造（多用户隔离剥离）

**背景**：项目实际是跑在使用者本地的单用户工具，之前却按多用户设计，积累了
一整套 `user_id` / 令牌 / 假用户服务 / 数据隔离机制。docs/17 里的 P0-1
（产物越权）、P0-2（执行串味）都建立在多用户并发的前提上。

**用户决策**：彻底删除 `user_id`（含 SQLite schema 与 SQL 过滤），
保留 F0–F3 多智能体地基、剥离其中的用户维度。

### 做了什么

| 层 | 改动 |
|---|---|
| 身份 | `core/identity.py` 四级标识 → 三级（去掉 `user_id`）；`core/agentkit/identity.py` 同步 |
| 执行隔离 | `core/exec_context.py`：`scope_key` 从 `user::session` 改为只用 `session_id`；**并发隔离保留** |
| 存储 | `core/memory_db.py` / `core/session_memory.py`：schema 删 `user_id`/`tenant_id` 列 + 迁移（`DROP COLUMN`）；检索 SQL 去掉 user 过滤 |
| 鉴权 | `infra/auth.py` 重写为只保留 `gen_session_id`/`gen_client_id` + no-op `require_auth`；删除 `core/user_service.py` |
| 后端 | `backend/session.py`（`ClientIdentity` 去 user/token）、`backend/websocket_handler.py`（去令牌校验）、`backend/main.py`（删 22 处 `@require_auth` 实际校验、`/api/users` 改单用户） |
| 工具 | `tools/proposal.py` / `hub.py` / `meta_tools.py`：`owner_user_id` → 只留 `owner_agent_id` |
| 前端 | `websocket.js` 去 token 收发；`config.js` owner token 变 no-op；`MemoryPanel`/`App.vue` 改用 `session_id` query |
| 记忆 | `core/memory_writer.py`、`core/semantic_memory.py`、`core/agentkit/memory.py`、`core/agentkit/sources.py`：去 `user_id` 参数，保留 scope/agent 分层 |

### 关键坑

1. **SQLite 删列**：用 `ALTER TABLE ... DROP COLUMN`（3.35+），但列上有索引时
   会失败 —— 必须先 `DROP INDEX`。`memory_db` / `session_memory` 都写了幂等迁移。
2. **`require_auth` 注入 `request` 参数**：保留注入但去掉 `annotation=Request`
   会让 FastAPI 把它当必填 query 参数 → **全部接口 422**。正确做法是直接
   `return func`（no-op）。
3. **批量正则替换的副作用**：`user_id=xxx` 的替换会误伤 `owner_user_id=xxx`
   → 变成 `owner_owner_agent_id`。涉及字段名时不能无脑正则。
4. **位置参数**：`append_message(sess, "u1", role, content)` 这种
   **位置传参**的 user_id，正则处理实参名抓不到，要单独按方法名处理。

## 记忆三层化（工作 / 短期 / 长期）

**背景**：记忆散在 5 个平级模块（`memory.py` / `memory_db.py` / `semantic_memory.py`
/ `session_memory.py` / `skill_quality.py`），调用方要自己判断该用哪个；"失败记录"
在两处存储各有一份；工作记忆（本轮工具返回/结论）根本没有，散在 `handle()` 的局部变量里。

**方案**：新增 `core/memorykit/` 作为三层的**唯一门面**，主链只认三张脸：
- `working.py`（新）工作记忆：轮级工作台，contextvar 暴露，4k/200 槽位上限，
  失败才 `dump()` 到 `memory/turns/`，轮末 `clear()`
- `short_term.py` 短期记忆：薄适配 `SessionMemoryStore`（不重写 SQL，store 不缓存以便测试隔离）
- `long_term.py` 长期记忆：收口画像 / 经验 / 技能台账三个子库

**改动点**：`core/agent.py`（begin_turn/set_plan/set_tool_results/end_turn、画像读写、
落库、摘要、reset 全部走门面）、`agents/manager.py::profile_block` 降级为兼容转发、
`backend/main.py` 的 sessions/memories 六个端点走门面、`ARCHITECTURE.md` §6.1 重写
（职责表 + 调用矩阵 + 单向沉淀）、新增 `tests/test_memory_layers.py`（11 条契约测试）。

**关键约束**：单向沉淀 工作→短期→长期；写入口唯一（短期只有 `Context.sink`，
长期只有后台写入器）；画像 ≤400 字常驻且每轮只读一次。

**验证**：全量 pytest 绿（1 个 MCP 用例在改动前就失败，环境相关）。

## 排障：前端报「连接未初始化或令牌无效」

**现象**：单用户化改造后前端仍收到 `错误: 连接未初始化或令牌无效`。

**根因**：8000 端口跑的是 **11/18 15:03 启动的旧进程**（早于 `1b48b2a` 重构），
旧代码每条 `chat/reset/feedback` 都要校验 `init` 签发的 session token；新前端
`websocket.js:323` 已只发 `{content}`，空 token 必然过不了 `verify_session_token`。
文案本身是判别器：旧版是「连接未初始化或令牌无效」，新版只剩「连接未初始化」。

**处理**：kill 旧进程 → `D:/python/python3.13/python.exe backend/main.py`
（唯一装了 `fastapi_websocket_pubsub` 的解释器；全局命中的 3.13.12 缺 fastapi）。

**验证**：`/api/health` 200（2 源 32 工具）；真实浏览器重连后日志出现
`identity issued` + `Client initialized`；自写 WS 冒烟 init → 收到 `connected`
（payload 仅 `client_id`/`session_id`，无 token）。

**经验**：改完后端必须重启进程，`docs/19` 里 P0-02「重连重建 Agent」的排查也受此影响。
