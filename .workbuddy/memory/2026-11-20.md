## 「新对话」失效修复（reset 可见性）

用户问"重启后对话不刷新吗、怎么开新对话"，查下来发现 reset 是半残的：

- 重启不丢是**设计**：前端 localStorage 存 `client_id` + `session_id`，重连带
  session_id → 后端复用 Session → Agent 从 sessions.db 恢复最近 8 条；前端
  `loadHistory()` 拉 `/api/session/messages` 渲染。这套是 docs/13 的"短期记忆全量保留"。
- 但「新对话」（输入框右边 ↺）只做了本地清屏 + `mark_reset`，而前端恢复用的
  `/api/session/messages` **不按 `reset_at_seq` 过滤** → 点完刷新，旧对话全回来；
  更糟的是 Agent 侧是按 reset 点过滤的，于是**界面显示旧对话、模型已经忘了**。
  实测：reset 后 `get_messages` 18 条 / 过滤后 0 条。
- 修复：`short_term.messages()` 加 `from_seq`，接口传 `reset_at_seq`。
  **过滤必须在 SQL 里** —— 先 LIMIT 再 Python 筛，reset 前消息一多就把新消息
  挤出窗口，表现成"重置后新说的话也看不见"。测试用 limit=1 钉住这个坑。
- 管理员接口 `/api/sessions/{sid}/messages` 保持不过滤（看全量档案），docstring 写明两个口径。
- 前端 ↺ 的 title 改成"新对话（清空当前上下文，历史仍保留在库里）"。

另外：真实库里所有会话 `reset_at_seq` 都是 0，说明这个按钮此前从未成功用过。

踩坑：heredoc `cat >>` 因重试写了两遍测试函数，F811 才暴露；删 37 行恢复。
教训：追加到文件的操作失败重试后，要检查是否重复写入。

## 会话列表 + 真正的「新对话」（d2878da）

用户接着问"为什么没有对话列表，新对话去哪儿建"。根因不是 bug 而是没做：
前端从来没有会话列表；输入框旁的 ↺ 做的是 reset（同一 session 内挪
`reset_at_seq`），点完列表里什么都不会变。上次修的 from_seq 过滤是对的方向，
但产品上"清空上下文"和"新对话"是两件事，用户要的是后者。

做法：
- 换会话**不用重连 WS**：对同一 conn 重发 `init` 即可。`issue_identity` 每次签发
  新 `client_id` 并覆盖 `conn_id → client_id` 映射，后续 `chat/{conn}` 就落到新会话
  （`get_or_create` 按新 session_id 新建/复用 Agent）。`switchSession('')` 不传
  session_id 就是新对话，服务端 `gen_session_id()`。
  ⚠️ 必须先清 localStorage 的 `skill_agent_session`，否则下次重连又带回旧会话。
- `GET /api/sessions` 加 `title`：**不加列**，从 `reset_at_seq` 之后第一条 user
  消息现算（一条 SQL 批量取，不要按会话循环查 —— 每次 _connect 都是新连接）。
  压平换行 + 36 字截断。reset 之后取是因为"这个会话从这儿重新开始"。
- 新会话在库里**没有行**（`ensure_session` 要等第一条消息），所以 SessionList 会把
  当前 activeId 补成一条「刚创建」占位项，否则用户点完新建找不到自己刚开的那条。
- 流式输出中禁止切换/新建：事件按连接推送（`events/{conn}`），旧那轮 delta 会飘进
  新会话界面。用 `busy = pendingIndex >= 0` 做闸门。
- 侧栏 7 个 tab 塞 320px：`font-size:10px` + `flex:1 0 auto` + `overflow-x:auto`
  （不换行，宁可滚也不顶掉侧栏高度）。
- ↺ 改成 ＋「新对话」；`reset/{conn}` 保留在协议层给脚本/测试，UI 不再挂。

验证：`scripts/e2e_switch_session.py`（手测，不进 CI）实测同一连接三次 init：
新签发 → 切到已有 6 条那条 → 再新签发，全部按预期。init 不写库，库仍是 7 条。

测试：标题 5 条 + 换会话 3 条，全量 1072 passed / 1 failed（唯一失败是既有的
`test_mcp_source::test_closed_connection_fails_pending`，与本次无关）。

顺手补的文档：docs/06（会话与切换、init 重发表、两条界面约束）、docs/13（"新对话"
vs reset 的区别表）。

## 长期记忆改成「会话级归纳」（不是逐句抠）

用户：「所以记忆的总结不要是单独记住一句话，而是说要综合来看才能沉淀。」

诊断：旧路径每轮在 `handle()` **开头**起一个 task，输入是「当前这一句 + 前 6 轮
（仅供消解指代）」，而证据被要求逐字出现在**当前这一句**里。两个结构性后果：

- 一句话就足以生成一条长期结论（「这次先这样」只要不含临时词就能变成偏好）
- 多轮才看得出的模式反而沉淀不下来（三轮都说"短一点"，没有任何单句能支撑它）

改法：

- `core/digest_window.py`：按 session 累积，攒满 `PROFILE_DIGEST_WINDOW`(6) 轮才归纳。
  <3 字的轮次（「继续」「好」）不占位 —— 否则一串继续会把窗口撑满，白跑一次 LLM。
  满窗后保留尾部 2 轮做下一批上下文（跨批的"反复出现"不断线）。
  reset 时 `flush()` 整批交出去（之后它们不会再参与任何归纳）。
- `core/profile_digest.py`：证据变数组 `[{turn, quote}]`，quote 必须在**声明的那一轮**
  用户原话里逐字出现（不是在整个 blob 里找，否则能拿第 5 轮冒充第 1 轮）；
  `kind=inferred` 必须 ≥2 个不同轮次；`kind=stated` 允许单轮；
  content 含「这次/刚才/这一版」直接丢；漏标 kind 按 inferred（不让"忘标"成为后门）。
- `Agent`：调用点从轮首 `_begin_turn` 移到轮末 `_persist_turn` —— 归纳要看
  "问了什么、答了什么、他接着怎么纠正"，轮首只有一句提问，那正是"记住一句话"的做法。
  「记住…」仍立即单写（结论合法性来自那句话本身，不该让他等攒满）。
- 面板：`/api/memory/profile` 返回 `evidence_turns` + `applies_to`，
  前端显示「综合自 3 轮（第 2、3、4 轮）」/「仅适用于 minimax」——
  用户能自己判断这条是不是从一句话推的。

真实 LLM 实测（5 轮：三轮反复要简短 + 一句身份 + 一个临时参数）：

```
[preference] 用户希望回答简短，只给结论，不讲过程  turns=[2,3,4]  ← 跨三轮
[fact] 用户从事横屏短剧制作，单集 90 秒             turns=[4]      ← stated
（"这次先切 3 个镜头"没有被抽成偏好）
```

单轮「帮我写个爬虫，这次先抓前十页就够了」→ 一条都不产出。

踩坑（三个都是自己写的 bug）：

1. `flush()` 复用 `_take()`，而 `_take` 会保留尾部几轮 → **reset 两次会把同一批反复
   归纳**。改成 flush 整批清空。
2. `digest_with_llm` 的"总长 < 20 字就跳过"把一句 19 字的身份陈述
   （「我叫老王，自己是做电商的」）直接吞了，表现为"单轮永远抽不出东西"。
   降到 10 —— 「继续」「好」早被窗口挡掉了，这里只是兜底。
3. 提示词缺 `applies_to` 判据，模型把「用户叫老王」限定成 `applies_to=拼多多`
   （只因为句子里提到了拼多多）。补上：身份/行业/姓名永远全局。

测试 +31（digest 29 + 显式记住 1 + evidence 落库 1）。全量 1117 passed / 1 failed，
唯一失败仍是既有的 `test_mcp_source::test_closed_connection_fails_pending`。
棘轮 360：新增的 except 全部收窄（json→ValueError、float→TypeError/ValueError、
create_task→RuntimeError/TypeError），并抽出 `_write_candidates` 去掉重复捕获。

已知边界（写进 docs/13）：窗口是纯内存，重启丢"已攒未满窗"的几轮；聊两三句就走的
会话不会沉淀任何画像；「这次用 5 秒」出现两轮仍可能被归纳成偏好（结构拦不住，
只能靠提示词 + content 临时词拦截）。

## 文件上传：能力一直在，缺的是入口

用户问：「有文档处理能力，为什么没有地方上传文件呢？」

查下来不是能力缺失，是**链路断在最后一米**：

- `tools/document.py` 的 read_document / locate_document 一直注册在 hub 里
  （`/api/tools` 能看到），能解析 docx/xlsx/pptx/pdf/md/txt/csv…
- 但它们吃的是**后端进程磁盘上的绝对路径**
- 前端从来没有上传口 —— 浏览器里的 File 对象对后端完全不可见

所以"能读 PDF"这件事，用户无从触发。这和会话列表那次是同一类问题：
能力在，入口不在。

做法：

- `POST /api/upload`（multipart）→ 落盘 `memory/uploads/<session>/<8位随机>_<原名>`
  - 白名单校验在**落盘之前**（不在 `SUPPORTED_SUFFIXES` 里直接 415）
  - 多读 1 字节判超限（分块上传没有 Content-Length，先 stat 再 read 不可靠）
  - 先写 `.part` 再 rename：半截文件绝不能被 read_document 看到
  - 文件名只留 basename（挡 `../../.env`）+ 随机前缀（同名不覆盖，
    历史消息里的路径要一直有效）
  - 落盘后用 `detect_format` 做**轻量探测**（只读文件头，不解析正文）：
    `readable=false` 的文件前端直接拒收，不让 agent 白跑一次再报错
- 前端 `ChatPanel.vue`：📎 按钮 + 拖拽上传 + 附件 chip + 换会话清空
- **附件清单拼在消息正文尾部**（`【已上传文件】\n- 名字 → 路径`），
  不是走 WS 协议字段。理由：这份清单必须**跟消息一起被存下来** ——
  否则下次打开会话，用户看到「帮我总结这个文档」不知道是哪个文件。
  代价是正文多一段路径，`parseMessage` 渲染时拆成 chip，`_make_title` 算标题时剥掉。
- `DELETE /api/sessions` 顺带 `_purge_upload_dir`：上传物只属于这条会话，
  会话没了就是垃圾。`default` 目录是共享落点，**任何情况下都不删**
  （所以 purge 里刻意不走 `_safe_upload_folder` 的 default 兜底）。

记忆侧：`core/profile_digest.strip_attachments()` 在归纳前切掉附件段。
`build_transcript` 和 `validate_digest` **必须用同一个剥离版本**，
否则模型引用的原话在校验时对不上，整条结论会被误判成编造。
顺带修了 `digest_with_llm` 的"总长 < 10 就跳过"——原来按原文算，
一条 80 字路径 + "看看"就能骗过阈值，白调一次 LLM。

端到端实测（`scripts/e2e_upload_and_read.py`，真实 WS + 真实 LLM）：
生成一份含「营收 1280 万元」的 docx → 上传 → 拼附件段提问 →
Agent 调用 `['read_document']` → 回答"本季度营收1280万元、同比增长23%"。
**这是整件事的验收线**：接口返回 200 只证明文件落地了，不证明 agent 用得上。

踩的坑：
1. 测试里 `../../.env` 期望 200，实际 415 —— 因为 `.env` 本身不在白名单。
   改成 `../../evil.txt`（穿越但后缀合法），另加一条"dotfile 直接被拒"。
2. `test_digest_ignores_attachment_paths` 断言用了 `captured.get(..., "")` 兜底，
   即使没调用也会通过 —— 加 `assert captured.get("transcript")` 立刻暴露是空转
   （写入器的 `_digest_extractor` 在测试里被换成了离线替身，根本不发提示词）。
   改成直接对 `digest_with_llm` 断言最终 prompt。
3. `delete_session` 靠 `session_messages` 的删除行数判断"删到了没有"，
   空会话返回 False（接口 404）—— 但空会话照样有上传文件（传完不说话就删）。
   把 `_purge_upload_dir` 挪到 raise 之前。

还没做（写进 docs/06）：图片/音视频上传（`read_media_file` 工具在，但没有视觉链路），
单文件 30 MB 上限是拍的（文档类够用）。
