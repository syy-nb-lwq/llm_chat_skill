# 18 · 智能体基础设施规划（地基优先）

> 日期：2026-11-19
> 定位：**先把"智能体"这件事的地基打好，再盖楼。**
> 本文回答三个问题：
> 1. 我对你当前设计的理解是什么（可核对的规格）；
> 2. 这个设计现在缺什么（不足清单，带代码证据）；
> 3. 智能体基础设施需要哪些底座、每个底座要考虑哪些细节、按什么顺序建设。
>
> 本文只做规划，不做改造。改造在本文确认后按 §8 的阶段执行。

---

## 0. 摘要（一页看完）

**你的设计是对的，方向不用改**：主智能体做编排不动手、子智能体是"有岗位的员工"、上下文按需注入而不是全量倾倒、子智能体之间能协作、能自己造工具 —— 这条路线跟行业里 Agent 编排的收敛方向一致，本仓库也已经有雏形（`core/subagents.py`、`core/goal_runner.py`、`tools/proposal.py`、`skills/registry.py`）。

**但这个设计目前是"骨架 + 若干硬编码约定"，不是"基础设施"。** 具体表现为五条：

| # | 现状 | 后果 |
|---|---|---|
| 1 | "主智能体不执行"没有判定标准 | 要么形式上派活实质自己干，要么每个小任务包一层子智能体，白烧两次 LLM |
| 2 | "上下文足够且清晰"没有契约 | 子智能体拿的是主对话的**全量快照**（`core/subagents.py:366-371`），工具/技能也是全量注入 |
| 3 | 记忆的 `scope` 是**死字段** | 写路径恒为 `user`（`core/memory_writer.py:60,568,589`），三条检索 SQL 一律不过滤（`core/memory_db.py:302,362,437`），"员工的工位记忆"无处安放 |
| 4 | 子智能体之间**没有通信协议** | 只有子→主单向回传（`tools/subagent_tool.py:78-116`），没有路由、时序、预算、失败语义 |
| 5 | 工具没有归属与可见性 | `ToolProposal` 无 owner 字段（`tools/proposal.py:140-164`），全局 `ToolHub` 共享，多用户下互相可见 |

**结论：先建 7 个底座 + 1 个运行时，再谈业务场景。**

```
底座：身份作用域 │ 角色契约 │ 上下文装配 │ 记忆门面 │ 工具门面 │ 消息总线 │ 观测审计
运行时：AgentRuntime（生命周期/并发/超时/预算/取消/恢复）
编排：DelegationPlan（DAG）→ 调度 → 收集 → 验收 → 合成
```

**建设顺序**：F0 止血 → F1 契约 → F2 上下文与记忆 → F3 通信 → F4 工具归属 → F5 运行时与主/子落地 → F6 编排闭环 → F7 度量基线。

## 1. 我对你当前设计的理解（请先核对这一节）

把你要的东西翻译成**可检验的规格**。后面所有设计都围绕这 12 条规格展开。

### 组 A：主智能体是"总经办"，不是"执行者"

| # | 规格 | 判定方式 |
|---|---|---|
| A1 | 主智能体**不直接产生外部事实**：不联网、不跑代码、不写业务文件、不造工具、不发外部请求 | 主智能体的工具表里没有执行类工具；执行类动作只能由子智能体发起 |
| A2 | 主智能体**必须**做：理解目标、拆分任务、选择角色、组装上下文、派发、监控、裁决、验收、合成、澄清、汇报 | 有对应模块与事件 |
| A3 | 主智能体的产出是**任务简报（TaskBrief）**，不是结果本身 | 派发接口的入参是可校验的结构体 |
| A4 | 主智能体的最终回答是**对子智能体结论的合成**，不是自己重做一遍 | 回答生成层拿不到执行类工具，只拿到报告包 |

### 组 B：子智能体是"有岗位的员工"

| # | 规格 | 判定方式 |
|---|---|---|
| B1 | 每个子智能体有一份**岗位说明书（RoleProfile）**：能力项 + 技能集 + 工具白名单 + 记忆范围 + 工作区 + 预算 + 权限 + 汇报格式 | 有数据结构 + 校验 |
| B2 | 子智能体**只领一份活**，不负责全局目标拆解 | 拆解是主智能体的能力；子智能体只在被授权时可再拆一层 |
| B3 | 子智能体**要自检**：按验收标准检查自己的产出，通过才算 `ok` | 报告包里必须有 `acceptance_check` |
| B4 | 子智能体**只产出事实**，不直接对用户说话 | 报告包进主智能体，用户只看到主智能体的合成 |

### 组 C：上下文是"按需投喂"，不是"全量倾倒"

| # | 规格 | 判定方式 |
|---|---|---|
| C1 | 主智能体**挑选**给每个子智能体的上下文，且每个块都带 `source`（来源）与 `why`（为什么给） | 注入日志可查 |
| C2 | 有**预算**：每块上限 + 总量上限；超限有明确裁剪顺序，且**目标与验收标准永不裁** | 预算实现 + 单测 |
| C3 | 技能、工具、历史都是**按需召回**，不是全量注入 | 两阶段召回接入生产 |

### 组 D：协作、通信与自治

| # | 规格 | 判定方式 |
|---|---|---|
| D1 | 子智能体之间可通信，但**只走定向消息 + 黑板槽位**，不做广播 | 消息总线限制 `to` |
| D2 | 通信有**预算**（条数/字节/轮次），有**审计**（每条落盘），有**失败语义**（对方已完成/未完成/已死） | 消息总线实现 + 审计文件 |
| D3 | 子智能体可以**自造工具**，但造出来的工具有**归属与可见性**：私有工作台 vs 公共发布 | `ToolProposal` 带 owner + 可见级别 |
| D4 | 子智能体**不直接写用户长期记忆**；它的经验以"候选"形式回流，由主智能体合并 | 记忆门面分角色授权 |

**如果这 12 条和你的本意一致，后面的方案就是把它落成代码；如果有偏差，请先纠正 §1，我按纠正后的版本改 §2–§8。**

## 2. 不足清单（带代码证据）

每一条给：**现象 → 为什么是问题 → 缺什么**。

### P0-1 「主智能体不执行」缺判定标准，会双向翻车

**现象**：现在主智能体自己执行工具：`core/agent.py:921-924` 的 `_run_plan_tasks` → `LearningAgent.execute_dag`；子智能体只是主智能体"可选地用一下"的帮手（`tools/subagent_tool.py` 是规划层能产出的一个 `tool_tasks` 类型）。

**为什么是问题**：这条期望如果不先定义清楚，会落到两个极端：
- **极端 A（形同虚设）**：主智能体照旧自己跑工具，只是名义上"派了活"，多烧一次 LLM 和一遍上下文；
- **极端 B（仪式主义）**：连"查个天气"都包一个子智能体，单任务成本翻倍，首 token 更慢。

**缺什么**：一条**可判定的分界线**。本方案采用：

> **分界线 = 这次动作是否产生外部事实或副作用。**
> - 产生外部事实/副作用（联网取数、跑代码、写文件、造工具、发外部请求）→ 必须下沉到子智能体；
> - 不产生外部事实（读自己的上下文、查技能目录、看工具签名、检索记忆、组装任务简报、决定问用户什么）→ 主智能体自己做，这叫编排，不叫执行。

外加两条豁免：**闲聊 / 澄清 / 技能教学**属于"与人对话"，主智能体直接完成，否则体验荒谬。

### P0-2 「上下文足够且清晰」现在恰好是反面：全量快照

**现象**：子智能体每轮拿到的是主对话的**完整快照**（`core/agent.py:950` → `core/subagents.py:366-371`），并且因为子智能体复用 `ManagerAgent.plan`，它看到的是**全量工具签名**（`agents/manager.py:146-178`，枚举来自 ToolHub 全量）和**全量技能列表**（`agents/manager.py:219,306-307,853-862`，无预算）。

**为什么是问题**：
- 成本与延迟：规划层提示词随工具数线性膨胀（`docs/17` P1-4 已点名"技能库养到 10 个就装不下"）；
- 上下文污染：子智能体看到与本任务无关的技能与工具，会误选（"用工具做它不熟的事"）；
- 不可复盘：现在无法回答"这个子智能体当时看到了什么"，所以它做错了只能靠猜。

**缺什么**：`ContextBundle`（上下文包）—— 带来源、理由、预算、裁剪记录的结构化注入物。见 §4.3。

### P0-3 记忆的 `scope` 是死字段，"员工的工位记忆"无处安放

**现象**：`MemoryEntry.scope` 注释写着 `session|user|project|global`（`core/memory_db.py:36`），但写路径**恒为 `user`**（`core/memory_writer.py:60,568,589`），三条检索 SQL（FTS / CJK / 向量，`core/memory_db.py:302,362,437`）**都不按 scope 过滤**。

**为什么是问题**：子智能体如果按你设想"有自己的记忆"，在当前实现里**没有任何地方可以放**——它写的和主智能体写的是同一个池子，还会污染用户画像（这正是 `docs/15` §6 禁止子智能体写长期记忆的原因，但那是"堵"，不是"给路"）。

**缺什么**：记忆门面（§4.4）+ 四个写入层：
`会话记忆` → `智能体私有记忆` → `用户长期记忆` → `程序记忆（技能/工具，走治理）`。
并把 scope 过滤真正落到 SQL 上。

### P0-4 子智能体之间没有通信协议

**现象**：子智能体只能把结论回给主智能体（`core/subagents.py:488-492` 的 `findings`），彼此无通道；`docs/15` §6 明确写了"不做子智能体互相通信"。

**为什么是问题**：你期望"子智能体之间可以相互协作、通信"。但**自由通信会立刻变成不可调试的黑盒**：互相问来问去、循环、上下文互相污染、没人知道谁说了什么。而"完全禁止"又达不到你的目标。

**缺什么**：**受控协作**——静态依赖 + 定向消息 + 黑板槽位 + 预算 + 审计。见 §4.6、§5.3。

### P0-5 工具没有归属与可见性，多用户下互相可见

**现象**：`ToolProposal` 无 `user_id/owner` 字段（`tools/proposal.py:140-164`），存 `memory/tools/proposals/*.json`，发布后进**全局单例** `ToolHub`（`tools/hub.py:22,391-399`），重启恢复也进同一个全局 hub（`tools/proposal.py:595-622`）。

**为什么是问题**：子智能体自造工具这条链一旦放开，多用户/多租户下 A 的子智能体造的只读 HTTP 工具会被 B 用；`docs/17` P0-1（产物越权）就是同一类问题的另一个面。

**缺什么**：工具门面（§4.5）：**私有工作台**（子智能体自用，不进公共 hub）+ **公共发布提案**（审批后进全局 hub，带 owner 与可见范围）。

### P0-6 执行目录不隔离，并发子智能体会串味

**现象**：`python_exec` 的执行目录是全局单例 `memory/workspace/_run`（`tools/python_exec.py:609-620,88-92`），`write_script` 的 `run_id` 在工具实例化时随机一次、全进程共享（`tools/script_writer.py:85-87,147`）。`docs/17` P0-2 已实测出"用户 A 执行了用户 B 的代码"。

**为什么是问题**：编排型架构下，**同一时刻多个子智能体并行跑代码是常态**，这个 bug 会从"偶发串味"升级为"常态性数据错误"。

**缺什么**：执行/工作目录按 `user_id / session_id / agent_id / execution_id` 四级隔离 —— 这是所有并行编排的前提，必须在 F0 修。

### P1-7 没有"验收"环节，主智能体只是转发器

**现象**：`ResultValidator` 只在**发布路径**用（`backend/main.py:899-945`、`core/critic.py:360-390`），**运行期没有**。运行期的成功判定是"工具调通了"（`core/critic.py` 成功率 = 成功工具数/工具总数，`docs/10` §4.5）。

**为什么是问题**：如果主智能体不执行、只汇总，那么"结果对不对"的把关责任 100% 落在它身上。没有验收机制，它只能把子智能体的结论原样转发，编排价值归零（`docs/17` P1-6 说的"5.6 秒的假成片被当成交付物"就是这个洞）。

**缺什么**：报告包里带 `acceptance_check`（子智能体自检）+ 主智能体的**验收裁决**（不合格 → 定向返工，有次数上限）。

### P1-8 预算只有"轮次 + 时长"，没有分层继承与结算

**现象**：`goal_runner` 只有 `max_rounds(6)` + `budget_s(180)`（`infra/config.py:117-122`）；子智能体只有 `max_concurrent(3)` / `timeout(90s)` / `rounds(2)`（`core/subagents.py:88-94`），**没有 token / 成本 / 工具调用数 / 消息条数**的账。

**为什么是问题**：编排型系统的成本是**乘性**的（主 × 子 × 轮次）。没有分层预算与结算，跑飞了只能在最后看总时长。

**缺什么**：`Budget` 对象（§4.2）+ 父子继承规则 + 结算报告。

### P1-9 跨轮次的任务状态不持久化

**现象**：`SubAgentPool` 是**进程内单例**（`core/subagents.py:497-509`），任务状态只在内存；`SessionManager` 也在进程内（`backend/session.py`）。

**为什么是问题**：进程重启 → 未完成的编排任务、任务图、黑板内容全部蒸发。`docs/15` §5 把"跨轮次的任务计划持久化"列为 P3。

**缺什么**：编排图与黑板的持久化（进 `memory/sessions.db` 或独立 `memory/orchestration.db`），支持"重启后续跑"。

### P1-10 缺人在环的中途干预

**现象**：`docs/15` §5 把"人在环：循环中途可以打断/改目标"列为 P3，未实现。

**为什么是问题**：编排型系统把执行权交出去之后，**必须**有收回执行权的通道，否则用户只能等超时。

**缺什么**：控制面消息 `TASK_UPDATE`（纠偏）/ `TASK_CANCEL`（取消），以及前端"停止/改目标"按钮。

### P2-11 记忆里的"经验"没有回流通道

**现象**：子智能体踩的坑（失败原因、试错过程）只留在 `findings` 摘要里（`core/subagents.py:474-486`，每条截断 500 字符）。

**为什么是问题**：同样一个坑，下次换个子智能体还会踩一遍。"员工成长"需要经验沉淀。

**缺什么**：子智能体写**智能体私有记忆 / 经验候选**，主智能体定期合并进"教训库"。

### P2-12 技能召回是死接口，检索策略没上线

**现象**：`SkillRegistry.match(user_input, top_k=3)`（`skills/registry.py:126-153`）实现了，但**生产代码从不调用**；生产是"全量技能塞进规划层提示词"（`agents/manager.py:219,306-307`）。且它是单阶段关键词打分，不是两阶段召回。

**为什么是问题**："上下文按需投喂"这条期望，**技能是最典型的适用对象**，现在完全没实现；技能库一旦到 10 个，提示词就爆（`docs/17` P1-4）。

**缺什么**：两阶段召回（结构化过滤 → 关键词/向量召回 top-k → LLM 重排）接入生产。§4.3 的上下文装配器依赖它。

## 3. 智能体能力模型（第一个底座）

在讨论"主智能体该会什么、子智能体该会什么"之前，先把"一个智能体要具备哪些能力"定下来 —— 这是角色契约的依据，也是"基础设施够不够"的检查表。

### 3.1 十项能力

| 组 | 能力 | 含义 | 失败表现 |
|---|---|---|---|
| **认知** | C1 目标解析 | 把模糊需求变成可验收的目标（验收标准、交付物、约束） | 做完了但不是用户要的 |
| | C2 情境装配 | 知道"手上有什么"：画像、技能、工具、已有产物、工作区、历史 | 重复劳动 / 用错工具 |
| | C3 计划分解 | 拆成可独立完成的子任务，标出依赖与并行组 | 串行做完 / 只做一件 |
| **执行** | C4 资源获取 | 调工具、连 MCP、造工具，取得外部事实 | 只能靠模型知识编 |
| | C5 执行与自检 | 干活 + 按验收标准检查产出 | 交付物是错的 |
| | C6 恢复 | 失败重试、换路、升级上报 | 卡死 / 静默失败 |
| **协同** | C7 沟通 | 对上汇报、对同伴定向通信、对用户澄清 | 结论没人接住 / 反复问用户 |
| | C8 交接 | 把结论与产物按格式交给下游或上游 | 下游拿不到必要信息 |
| **自我约束** | C9 预算管理 | 知道自己还有多少钱/多少轮/多少时间 | 烧钱 / 无限循环 |
| | C10 升级与求助 | 判断"我搞不定"，带着已获信息求助 | 硬扛到超时 |

### 3.2 能力 × 角色 授权矩阵

**三态**：`●` 主责 ／ `◐` 受限 ／ `—` 不做。

| 能力 | 主智能体（总经办） | 子智能体·执行型 | 子智能体·审查型 | 子智能体·调研型 |
|---|---|---|---|---|
| C1 目标解析 | ● | ◐（只解析自己的简报，遇到歧义回报） | — | ◐ |
| C2 情境装配 | ●（决定给谁什么） | ◐（只读自己的上下文包） | ◐ | ◐ |
| C3 计划分解 | ● | —（除非显式授权再拆一层） | — | — |
| C4 资源获取 | — | ● | ◐（只读工具） | ● |
| C5 执行与自检 | — | ● | ●（只验不改） | ● |
| C6 恢复 | ◐（重派/改简报） | ● | ◐ | ● |
| C7 沟通 | ● | ◐（对主 + 定向对同伴） | ◐ | ◐ |
| C8 交接 | ● | ● | ● | ● |
| C9 预算管理 | ●（全局分配） | ◐（用完即停并回报） | ◐ | ◐ |
| C10 升级与求助 | ●（问用户） | ●（向主智能体升级） | ● | ● |

**这张表就是职责契约。** 它同时回答了"主智能体为什么不执行"（它没有 C4/C5 的工具授权）与"子智能体为什么不能乱来"（它没有 C3）。

> 落地方式：`RoleProfile.capabilities` 是一个**白名单**，运行时按白名单**裁剪工具表与提示词** —— 不是靠提示词请求模型"不要做"，而是**不给它工具**。

### 4.1 底座一：身份与作用域（Identity & Scope）

**职责**：让每一个智能体实例有唯一身份、可追溯的父子关系、明确的权限与预算边界。

**复用**：`core/identity.py` 的 `IdentityContext` 已有 `user_id/session_id/turn_id/execution_id/parent_execution_id`（`core/identity.py:26-55`），`child()` 已能派生分支身份 —— 直接扩展。

**新建**：

```python
# core/agentkit/identity.py
@dataclass
class AgentIdentity:
    agent_id: str                 # agent_<8hex>，全局唯一
    role_id: str                  # 角色，如 "researcher"
    role_name: str                # 人类可读名，如 "政策研究员"
    user_id: str
    tenant_id: str
    session_id: str
```

3. 身份**不隐含存储路径**（沿用 `core/identity.py` 的注释精神），路径由 scope 决定。

### 4.2 底座二：角色画像与能力契约（Role Profile & Capability）

**职责**：定义"一个岗位是什么"，并把能力矩阵变成**机器可校验**的配置。

```python
# core/agentkit/roles.py
```

**预置角色模板**（起步 4 个，够用即可，别一次写十个）：

| role_id | 用途 | 工具面 | 典型产出 |
|---|---|---|---|

**规则**：
1. 角色**不是提示词**，是**配置**：它决定工具表、技能集、记忆范围、预算、汇报格式。
2. 运行时按 `RoleProfile` 裁剪工具表（§4.5），未授权工具**不出现在 schema 里**。
3. 主智能体可以**动态生成角色**（当现有角色不匹配时），但必须过同一个校验器：白名单合法、预算 ≤ 父预算、能力项合法。

### 4.3 底座三：上下文装配器（Context Assembler）—— 对应期望 C1/C2/C3

**职责**：把"该给这个子智能体的信息"组装成一个**可审计、可预算、可复盘**的包。

```python
# core/agentkit/context.py
@dataclass
class ContextBlock:
    source: str      # session | memory | skill | tool | workspace | brief | peer
    why: str         # 为什么给这块（必填）
    chars: int
    content: str
    priority: int    # 裁剪优先级，数字越小越先被裁

@dataclass
class ContextBundle:
    blocks: list[ContextBlock]
    total_chars: int
    dropped: list[dict]     # 被裁掉的块及原因 —— 复盘用
```

**八类来源与选择规则**：

| # | 来源 | 选什么 | 上限（建议） | 裁剪优先级 |
|---|---|---|---|---|
| 1 | 角色与约束 | 角色契约摘要、硬边界（不能写用户记忆/不能越权） | 800 | 不裁 |
| 2 | 目标与验收 | TaskBrief 的 goal / acceptance / deliverable | 1500 | **不裁** |
| 3 | 用户画像 | 画像块（已有 ≤400 字符实现 `core/semantic_memory.py:294`） | 400 | 不裁 |
| 4 | 相关长期记忆 | 召回 top-k（带 source/why） | 2000 | 3 |
| 5 | 相关技能 | 两阶段召回 top-3 的方法与步骤（**不含全量列表**） | 2500 | 2 |
| 6 | 工具签名 | 仅白名单内工具的名+参数+一句说明 | 1500 | 4 |
| 7 | 工作区状态 | 与本任务相关的文件/产物清单 | 1200 | 5 |
| 8 | 对话切片 | 指代消解所需的最近 2–6 轮 | 1500 | 6 |
| 9 | 上游产出 | 黑板槽位的值或引用（**不是全量数据**） | 1200 | 1 |

**规则**：
1. **目标与验收永不裁**；其余按"优先级数字大 → 先裁"。
2. 每个块**必须**带 `why` —— 没有理由的上下文不允许注入（这是"够用且清晰"的可检验形式）。
3. 装配**有日志**：本轮注入了什么、裁了什么、为什么裁 → 落 `memory/audit/context_<exec>.jsonl`。子智能体做错时，第一件事就是看这份日志。
4. **依赖**：第 4、5 项依赖两阶段召回能力（§2 P2-12），必须先补。

### 4.6 底座六：消息总线（Message Bus）—— 对应期望 D1/D2

**职责**：让"谁跟谁说话"有唯一的、可审计的、可限流的通道。

```python
# core/agentkit/messaging.py
@dataclass
class Message:
    msg_id: str
    kind: str          # 见下表
    from_agent: str
    to_agent: str      # 不允许 "broadcast"
    thread_id: str     # 关联的 task_id
    reply_to: str | None
    payload: dict
    refs: list[str]    # 引用的产物/黑板槽位
    created_at: float
```

**消息类型**：

| kind | 方向 | 用途 | 载荷要点 |
|---|---|---|---|
| `TASK_ASSIGN` | 主→子 | 下达任务简报 | TaskBrief |
| `TASK_UPDATE` | 主→子 | 补充信息 / 纠偏 / 缩范围 | `note`, `changed` |
| `TASK_CANCEL` | 主→子 | 取消 | `reason` |
| `REPORT` | 子→主 | 交活 | ReportPacket |
| `QUERY` | 子↔子 / 子→主 | 问一个具体问题 | `question`, `need_by` |
| `ANSWER` | 任意→提问者 | 回答 | `answer` |
| `HANDOFF` | 子→子 | 交接（带上下文与产物） | `summary`, `refs` |
| `ESCALATE` | 子→主 | 我搞不定 | `why`, `tried`, `need` |

**路由规则**：
1. `to_agent` **必须是具体 agent**，不支持广播；
2. 子→子通信**只在编排图里存在依赖边时允许**；没有依赖边却要通信 → 走主智能体代理（主转发），并记一笔"编排缺失"；
3. 主→子 / 子→主 **不限**；
4. 每个 agent 有 `max_messages`（默认 8），超限 → 拒绝并回报主智能体；
5. 单条 payload ≤ 2KB；超了要传引用（黑板槽位/产物路径）而不是塞全文；
6. **保序**：同一对 agent 之间 FIFO；
7. **审计**：每条消息落 `memory/audit/messages.jsonl`（from/to/kind/summary/task_id/exec ids/字节数）。

**失败语义**（对方已结束/未结束/已死）：
- 收到 `QUERY` 时对方已完成 → 直接从其 `ReportPacket` 里找答案，回 `ANSWER`（不重新执行）；
- 对方仍在运行 → 排队，等它结束时回一次；超时 → 回"对方未响应"；
- 对方已死/超时 → 回"对方已失败，附错误"，并建议主智能体重派。

### 4.7 底座七：运行时与调度（Agent Runtime）

**职责**：把"派出去 - 跑起来 - 收回来 - 验收 - 合成"这条链变成有状态、有预算、可中断的机器。

## 5. 执行链与协作编排

### 5.1 任务简报（TaskBrief）—— 主智能体 → 子智能体的唯一契约

```python
@dataclass
class TaskBrief:
    task_id: str
    goal: str                       # 一句话、可独立执行
    acceptance_criteria: list[str]  # 可判定；子智能体据此自检
    deliverable: dict               # {"kind": "facts|file|data|code|report", "format": "..."}
    context: list[ContextBlock]     # 已装配好的上下文块（含 source/why）
    tools: list[str]                # 允许的工具（白名单子集）
    skills: list[str]               # 允许的技能 name@version
    depends_on: list[str]           # 依赖的 task_id
    inputs: list[str]               # 从黑板读哪些槽位
    outputs: list[str]              # 往黑板写哪些槽位
    budget: Budget
    escalate_when: list[str]
    report_schema: str
```

**规则**：TaskBrief **必须能被校验**（目标非空、验收标准非空、工具在白名单内、预算不超过父预算、依赖无环）。校验不过 → 主智能体重写简报，不下发。

### 5.2 报告包（ReportPacket）—— 子智能体 → 主智能体的唯一契约

```python
@dataclass
class ReportPacket:
    task_id: str
    status: str          # ok | partial | failed | timeout | blocked | cancelled
    summary: str
    findings: list[str]          # 结论要点（压过，不给原始大对象）
    evidence: list[dict]         # 来源/证据（链接、文件、命令输出摘要）
    artifacts: list[str]         # 产物路径或引用
    acceptance_check: dict       # {"passed": bool, "items": [{criterion, met, note}]}
    open_questions: list[str]
    confidence: float            # 0..1
    tools_used: list[str]
    proposed_tools: list[dict]   # 自造工具的提案摘要（私有或待发布）
    cost: dict                   # 轮次/秒/工具调用数
```

**规则**：
1. `status=ok` 但 `acceptance_check.passed=false` → 主智能体**不得**当作成功（这是 P1-7 的堵点）。
2. `findings` 有长度上限（压过），原始数据走 `artifacts` 引用 —— 这就是"上下文不倾倒"的回报侧对应。
3. `status` 五态必须如实，禁止把 `partial/failed` 报成 `ok`（沿用 `core/subagents.py:191-196` 的强制文本）。

### 5.3 协作模型：静态依赖 + 定向消息 + 黑板

**主智能体产出编排图（DelegationPlan）**：

```
DelegationPlan
  tasks: [TaskBrief...]          # 每个 brief 带 depends_on
  edges: [(from_task, to_task)]  # 依赖边 = 允许的通信对
```

**执行规则**：
1. **依赖满足即启动**（不等其他无关任务）—— 保留并行度；
2. 上游完成后，把 `outputs` 声明的槽位写入**黑板**（key → {value, producer, ts}）；
3. 下游启动时按 `inputs` **按键拉取**，不读整个黑板；
4. 下游缺信息且上游还在跑 → 发 `QUERY`（受消息预算约束）；
5. 上游已结束 → 直接从其 `ReportPacket` 回 `ANSWER`；
6. 上下游之间传的是**结论与引用**，不是原始数据（`artifacts` 路径 / 摘要）。

**为什么不做自由通信**：自由拓扑无法调试、无法复盘、无法预算。而"静态依赖 + 定向消息"覆盖了你期望的绝大多数协作场景（上游产出给下游用、下游问上游要个参数），同时保留可审计性。

### 5.4 主链的新形态

```
用户输入
 └─ [对话面] L0/L1 意图判别 → 闲聊 / 澄清 / 教学 / 任务
 └─ [控制面] 分解 → DelegationPlan(TaskBrief × N)
      ├─ 需澄清 → [对话面] 追问用户 → 回到分解
      └─ → [运行时] 按依赖调度
            └─ [执行面] 子智能体：规划(受限) → 取资源 → 执行 → 自检 → ReportPacket
                 ├─ [工具门面] 私有工作台 / 公共发布提案
                 └─ [消息总线] 与同伴定向通信
      → [控制面] 收集报告包 → 按 acceptance_criteria 验收 → 不过则定向返工（≤N 次）
      → [合成面] 组织最终回答（只拿报告包，不拿工具）
      → [记忆面] 合并经验候选 → 写用户长期记忆（仅主智能体）
```

**"不执行"的落地检查点**：合成面（回答生成层，`agents/orchestrator.py`）拿不到执行类工具；控制面只有编排工具（`delegate` / `agent_status` / `ask_user` / `cancel` / `read_skill_catalog` / `read_tool_catalog` / `read_memory`）。

## 9. 明确不做（地基阶段）

1. **不做自由广播式子智能体互联**（不可调试、不可预算）；
2. **不做无上限的子智能体递归**（深度默认 1，开放到 2 也必须只读 + 强预算）；
3. **不做"主智能体什么都能干"的万能插件** —— 主智能体的工具表必须能被审计；
4. **不在地基阶段引入新的向量库 / 记忆框架** —— 现有 SQLite + FTS + 可选 embedding 够用，先把 scope 落地；
5. **不在地基阶段改前端交互形态** —— 只加"停止/改目标"与编排可视化所需的最小事件；
6. **不把"氛围/性格"类提示词当基础设施**（`soul/SOUL.md` 保留现状，不进角色契约）。

## 10. 决策点与已拍板结论

| # | 决策 | 选项 | 结论 |
|---|---|---|---|
| D1 | "主智能体不执行"的判定标准 | A. 按"是否产生外部事实/副作用"<br>B. 按"是否调用工具"一刀切<br>C. 分场景 | **✅ 已定：A**（2026-11-19） |
| D2 | 闲聊 / 澄清 / 技能教学是否由主智能体直接做 | 是 / 否 | **✅ 隐含为"是"**（D1 的豁免项，本文已按此写） |
| D3 | 子智能体深度 | 保持 1 / 放到 2 | **暂定 1**，F6 稳定后再评估 |
| D4 | 子智能体自造工具的默认可见性 | 私有 / 全局 | **✅ 已定：全局**（2026-11-19） |
| D5 | 编排模式是否用 feature flag 双轨 | 是 / 直接切换 | **双轨**（F5-6），保证可回退 |
| D6 | 上下文预算默认值 | 每 agent 12k 字符 | **先 12k，实测后调**；目标与验收永不裁 |
| — | 首批改造范围 | F0 / F0+F1 / F0+F1+F2 | **✅ 已定：F0 + F1**（2026-11-19） |

### 10.1 D1 落地：分界线的可执行形式

主智能体的工具表被切成两块，**由配置裁剪，不由提示词约束**：

| 面 | 工具 | 归属 |
|---|---|---|
| **控制面**（主智能体保留） | `delegate`（派活）、`agent_status`（查状态）、`ask_user`（澄清）、`cancel_task`、`read_skill_catalog`、`read_tool_catalog`、`read_memory` | 主智能体 |
| **合成面**（主智能体保留） | 无工具，只读报告包 | 主智能体 |
| **执行面**（必须下沉） | 联网、执行代码、写文件、造工具、发外部请求、产物发布 | **仅子智能体** |

判定规则一句话：**会改变外部世界的动作 → 执行面；只读取并组织信息的动作 → 控制面。**
例外：闲聊 / 澄清 / 技能教学属于"与人对话"，主智能体直接完成（D2）。

### 10.2 D4 落地：全局发布，但保留收紧的开关

按你的决定，**子智能体自造的工具默认进全局 ToolHub**。落地时做三件事，避免这个决定带来不可逆的后果：

1. **数据模型保留 `owner_user_id` / `owner_agent_id` / `visibility`**（默认 `global`）—— 将来要改成按用户或按 agent 可见时，**改配置即可，不做数据迁移**；
2. **owner 必须落盘**（提案文件 + ToolHub 注册信息）—— 回答"这个工具是谁造的、能不能一键禁用"；
3. **命名带 owner 前缀可选开关**（`TOOL_NAMESPACE_BY_OWNER`，默认关）—— 多用户场景下打开即可避免同名互相覆盖。

**已知风险（明确记录，不隐藏）**：全局可见意味着**多用户/多租户部署下，A 的子智能体造的只读工具 B 也能用**（与 `docs/17` P0-1「产物越权」同类）。当前形态是"团队内部/单机"，可接受；若对外提供服务，需先做按 owner 隔离（数据模型已就位，只差过滤逻辑）。

### 10.3 首批范围（F0 + F1）的验收口径

- **F0**：并发不串味（执行目录隔离）、工具可溯源（owner 落盘）、技能库到 10+ 个时提示词不线性膨胀（两阶段召回上线）、跨 scope 不互相召回、审计文件可串联一轮任务。
- **F1**：12 条规格落成**机器可校验的数据结构**；校验器能拒绝「缺验收标准 / 预算超父 / 循环依赖 / 越权工具」；纯数据不依赖 LLM，可单测。

## 11. 一句话总结

> 你的设计不缺想法，缺**契约、边界和可执行的隔离**。
> 地基要做的就三件事：**（1）把"谁能做什么"变成配置而不是提示词；（2）把"给谁看什么"变成带预算、带来源、可审计的上下文包；（3）把"谁跟谁说话"变成带路由、带预算、带审计的消息总线。**
> 这三件做完，主智能体才真的可以只做编排，子智能体才真的是员工，而不是一个换了个名字的执行函数。

### 12.4 F3 通信总线

新增 `core/agentkit/messaging.py` —— 受控通信（不是自由聊天）：

| 能力 | 实现 |
|---|---|
| 消息类型 | `TASK_ASSIGN / TASK_UPDATE / TASK_CANCEL / REPORT / QUERY / ANSWER / HANDOFF / ESCALATE` |
| 定向 | `to_agent` 必须是具体 agent，**不支持广播**（`broadcast` 直接拒） |
| 有边 | 子↔子只在编排图**存在依赖边**时允许（`allow_pair` / `allow_pairs_from_edges`）；没有边 → 必须经主智能体转发 |
| 限额 | 每 agent 消息条数（默认 8）、单条载荷 ≤2000 字符（超了要改传 `refs` 引用） |
| 保序 | 同一对 agent FIFO（`drain` 按到达顺序） |
| 审计 | 每条消息落 `memory/audit/messages.jsonl` |
| 失败语义 | 对方**已完成** → 直接从报告包回答（不让它重做）；**在跑** → 排队；**已失败/已死** → 立刻回"不可用，没有可用结论"（不硬凑答案） |
