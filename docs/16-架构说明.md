# 架构说明

面向要接手这个项目的人。写的都是代码里能对上号的东西,不含规划和愿景。

- 代码规模:Python 37184 行 / 163 个文件,前端 12 个文件,测试 58 个
- 运行形态:FastAPI 后端 + Vue 3 前端,一条 WebSocket 承载全部交互

---

## 一、一次对话发生了什么

从 WebSocket 收到一句话,到用户看到回答,代码走的路:

```
backend/websocket_handler.py
  └─ core/agent.py::Agent.handle()
       ├─ 恢复会话历史(core/session_memory.py)
       ├─ 纠正检测(core/correction.py)        ← 纯规则
       ├─ 规划(agents/manager.py::plan)
       │    ├─ L0 结构守卫(core/intent_detector.py)   0 次 LLM
       │    ├─ L1 闭集判别(core/llm_judge.py)        1 次 LLM
       │    └─ L2 规划(agents/manager.py::_llm_plan)  1 次 LLM
       ├─ 目标循环(core/goal_runner.py)        ← 规划层说"没完"就再跑一轮
       │    └─ 工具执行(agents/learning.py::execute_dag)
       │         └─ tools/hub.py::call_tool()  ← 所有工具调用的唯一入口
       ├─ 回答生成(agents/orchestrator.py)
       ├─ ExecutionCritic 打分(core/critic.py)
       └─ 后台任务(不阻塞回答)
            ├─ 工具自修复(core/tool_repair.py)
            └─ 方法论沉淀(core/skill_harvest.py)
```

一句话请求("你好")走完这条链要 3 次 LLM 调用:判别一次、规划一次、生成一次。

## 二、分层与各自的职责

### 2.1 意图:三层,只有一层有规则

| 层 | 位置 | LLM 次数 | 干什么 |
|---|---|---|---|
| L0 结构守卫 | `core/intent_detector.py` | 0 | 只判空输入 → 澄清 |
| L1 闭集判别 | `core/llm_judge.py` | 1 | 6 标签分类,带置信度 |
| L2 规划 | `agents/manager.py::_llm_plan` | 1 | 选工具、排 DAG |

L0 里现在**没有任何"猜用户怎么说"的规则**。原来有,后来删了 —— 实机基线:规则+LLM 94.7%,纯 LLM 97.7%(130 条标注样本)。规则不仅更差,还会抢在 L1 前面把话拿走。

L1 置信度低于阈值(0.75)时,带着判断升级到 L2,而不是放弃。

### 2.2 记忆:按内容类型分,不是按 TTL

| 层 | 存哪 | 保留策略 | 怎么进上下文 |
|---|---|---|---|
| 短期 | `memory/sessions.db` | 会话内容全量保留 | 滚动摘要 + 最近 8 条 |
| 长期 | `memory/semantic_memory.db` | 按 normalized_key 去重、冲突时单槽替换 | 画像块常驻注入 system prompt(≤400 字符) |
| 经验 | `memory/failures/`、`memory/skills/` | 追加不覆盖 | 需要时检索 |

**存储 ≠ 注入**。存了不等于每轮都进提示词。

长期记忆由 LLM 抽取(`core/profile_llm.py`),但抽取结果必须带 `evidence` —— 用户原话的逐字片段,对不上就丢弃。结构上防幻觉,不是靠提示词约束。

### 2.3 工具:32 个,四种来源

```
tools/hub.py::ToolHub
  ├─ 内置 Python 工具   tools/*.py          18 个
  ├─ MCP 外部工具       tools/sources/mcp_source.py   14 个(取决于配了几个源)
  ├─ agent 自造的        tools/proposal.py → DeclarativeHttpTool / ScriptTool
  └─ 插件目录扫出来的     tools/sources/python_source.py
```

数量会随 MCP 源增减,内置那 18 个是固定的。

`call_tool()` 是唯一入口,所有调用都在这里记账(`core/tool_health.py`)。

### 2.4 方法论:技能库,带回归样例和质量账本

- 技能是 YAML,存 `skills/`
- `steps` 里有结构化步骤时,会直接编成工具 DAG(`core/dag.py`)
- 质量账本 `memory/skills/quality.jsonl` 记录使用量和采纳率
- 降级是算出来的(通过率 < 0.6 或采纳率 < 0.5),修好会自动恢复

## 三、自增长的三条回路

这三条回路是这个项目跟普通 chatbot 的区别。

### 3.1 工具自增长

```
create_tool 提案
  → 静态校验(名字/URL/参数/代码黑名单)
  → 风险分级
  → 跑 test_cases(真执行)
  → 发布进 ToolHub
  → 跨重启恢复
```

只读的声明式 HTTP 工具和代码工具**自动发布**;写操作、带密钥的必须人工批准(`/api/tool-proposals`)。

判断依据:`CODE_EXEC_ENABLED=true` 时 agent 已经能跑任意代码,再给一个代码工具并不扩大攻击面,所以不卡审批;关掉时它根本跑不起来,直接判高风险。

### 3.2 方法论自增长

做成一件多步任务后,`core/skill_harvest.py` 把过程提炼成技能草稿。门槛:至少 2 个不同工具,或至少 2 轮 —— 一问一答不沉淀。

草稿要人批准才生效(`/api/skill-drafts`)。垃圾技能比没有技能更糟:污染检索、占注入预算、可能被误选。

### 3.3 自诊断与自修复

```
每次工具调用 → 记账(core/tool_health.py)
  → 算健康度(滑动窗口失败率 / 连续失败)
  → 不健康的工具注入规划提示词(让 agent 换路)
  → agent 自造的工具可自动出 v2(core/tool_repair.py)
```

自动修复**只动 agent 自己造的工具**。内置工具的源码是项目自己的代码,不允许 agent 自动改写 —— 只报告、只提示绕开。

修的时候同样过校验和测试。测试不过就不替换,宁可留一个坏的旧版。

## 四、目标循环与子智能体

原来 `handle()` 是一条直线:规划一次、工具执行一轮、生成回答、结束。所以「造工具 → 用它 → 再算」这种任务,只要第一次规划没想全,就没有第二次机会。

现在加了目标循环(`core/goal_runner.py`):

```
round = 1
while round <= max_rounds:
    plan = 规划(目标, 已知结果)
    执行工具 → results
    if plan.goal_done:      停
    if 没有新结果:          停(防原地打转)
    if 超出预算:            停
    round += 1
```

**循环由规划层显式驱动**。规划层每次输出 `goal_done`,默认 `true` —— 所以简单问答行为和以前完全一样,永远只跑一轮。

有四道闸:

| 闸 | 默认 | 防什么 |
|---|---|---|
| 轮次上限 | 6 | 无休止跑 |
| 时长预算 | 180 秒 | 慢任务烧钱 |
| 无进展检测 | 动作签名相同且无新结果 → 停 | 原地打转 |
| 失败计数 | 强制 | 「两个子任务失败但说得像全成了」 |

子智能体(`core/subagents.py`)能并行处理互不依赖的子目标,各有独立上下文,只回结论。深度上限 1(不能递归派)、并发上限 3、单个超时 90 秒。

子智能体通过 contextvars 拿到主对话上下文和用户画像 —— 否则用户说「发」,它不知道指的是什么。

## 五、数据都存在哪

```
memory/
  sessions.db          短期记忆:会话和消息
  semantic_memory.db   长期记忆:用户画像(FTS5 索引)
  failures/YYYY-MM/    失败教训(critic 写的)
  successes/           成功记录
  skill_patches/       待批补丁
  skills/drafts/       待批方法论草稿
  tools/health.jsonl   工具调用流水
  users/               用户档案
  workspace/           产物目录(可下载的东西)
    _run/              python_exec 的常驻执行目录
  audit/traces.jsonl   每轮的执行轨迹
```

存储层有两套:`memory_db.py` / `session_memory.py` 直接用 sqlite,`semantic_memory.py` 额外建了 FTS5 全文索引。

检索(`core/memory_db.py`):向量(可选)+ FTS5 + CJK bigram(Python 侧),三路 RRF 融合。中文没有空格,纯 FTS 会失效,所以 bigram 那条是必需的。

## 六、沙箱与边界

### 6.1 python_exec

生成的代码在独立子进程里跑:

- 独立工作目录(`memory/workspace/_run`,常驻,相对路径跨调用有效)
- `-I` 隔离模式 + `-B` 不写 .pyc + `-X utf8`
- 环境变量白名单 —— **子进程拿不到 API key**
- AST 静态黑名单:禁 `eval`/`exec`/`compile`/`__import__`/`subprocess`/`os.system`
- 超时、输出截断、产物收集

**子进程隔离是崩溃隔离,不是安全边界。** 静态检查是启发式的。

黑名单按**点号全名**判断(`builtins.compile` 拦,`re.compile` 不拦)。早期只看最后一段,导致 `re.compile` 被误拦 —— 那次 agent 连着两次撞墙。

### 6.2 工具与产物的路径约束

- 输入路径必须落在授权根目录内(产物目录 + MCP 授权目录)
- 应用自身安装目录一律拒绝 —— 那里有 `.env`
- 敏感文件名拒绝(`.env`/`*.pem`/`*.key`/`*secret*`)

判据:**能被 agent 读 ≠ 能被用户下载。**

### 6.3 身份

**本地单用户**：只有使用者本人，没有多用户隔离、没有令牌、没有登录。

三级标识(`core/identity.py`):`session_id` / `turn_id` / `execution_id`。

`session_id` 是跨重启续聊的唯一凭据 —— 前端存在 localStorage，重连时带回，
服务端据此复用同一会话。会话内容全量落库，所以「刷新后历史没了」这个问题
在本地单用户下不存在。

## 十、几条贯穿全项目的约定

**1. 精确率是生死线。** 记忆、纠正检测、工具修复这几条写路径,错一条会持续污染之后的每一轮。所以宁可漏,不可错。纠正检测至今是纯规则 —— 漏判只是少学一次,误判会污染记忆库。

**2. 判定交给模型,边界交给代码。** 意图、抽取、修复方案都让 LLM 判;能不能执行、路径合不合法、证据对不对得上,全部在代码里硬校验。

**3. 状态要能算出来。** 技能降级、工具健康、记忆注入,都是从流水重算的,不是写死的标记。数据变好会自动恢复。

**4. 观测不能拖垮业务。** 记账、脱敏、追溯全部包了异常处理,失败只记日志。

**5. 失败要说清楚。** 回答里必须区分「做完了」和「没做完」;子任务失败必须出现在给模型的文字里;404 要告诉用户能怎么办。

## 十一、几个已知的坑

记下来是因为它们都真实发生过,以后容易再踩。

| 坑 | 症状 | 根因 |
|---|---|---|
| 规则抢在 L1 前面 | 意图判错率反而更高 | 规则不该替模型做决定 |
| `re.compile` 被拦 | agent 连撞两次静态检查 | 黑名单只看最后一段 |
| 相对路径跨调用丢失 | 第二轮读不到第一轮写的文件 | 每次新建临时目录、跑完就删 |
| 产物路径套娃 | 成片落在 `_run/workspace/output/` | 脚本按老习惯写了 `workspace/` 前缀 |
| 只有一个镜头的"成片" | 5.6 秒 vs 应有 16.9 秒 | 没 ffmpeg + subprocess 被禁,于是降级交付 |
| 上下文不共享 | 子智能体不知道"发"指什么 | `plan()` 根本没传 context |
| 看不见自己的文件 | 说"拿不到 key",其实自己刚存过 | 事实状态只在对话历史里,历史会被压缩 |
| 测试污染生产数据 | 账本里出现 `flaky`/`stub_1` | 测试没隔离 `memory/` |

## 十三、测试

```bash
python -m pytest -q          # 980 passed, 3 skipped
```

3 个 skipped 是需要真实 API key 的意图评估用例(`--live`)。

基线脚本:

| 脚本 | 干什么 |
|---|---|
| `scripts/profile_eval.py` | 画像抽取精确率/召回率 |
| `scripts/intent_eval_nightly.py` | 意图识别留出集评估 |
| `scripts/trace_report.py` | 从轨迹算耗时分布 |

**基线的用法**:改完提示词之后,再跑留出集并把新批次写进去。留出集要在改动**之后**生成,否则等于拿考卷背答案。`intent_eval_sealed.jsonl` 只跑一次。
