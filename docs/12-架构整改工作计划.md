## 0. 评审结论与编制背景

2026-07-25 对项目做了一次代码层面的深度评审（不只看文档，逐文件分析 import 关系、并发安全、错误处理、可观测性、测试有效性、扩展点设计），得出以下结论：

| 维度 | 结论 |
|---|---|
| **技术栈** | 可以升级，且有 6 个未使用依赖应立即删除；前后端都有过时点 |
| **架构** | **需要调整**。文档声称的四层分层在代码里已名存实亡，存在循环依赖、双轨存储、死代码、上帝文件等结构性问题 |
| **可演进性** | 中等。技能/工具扩展点设计较干净，但 Agent 层无注册表，新增 Agent 需改 `Agent.__init__` 和 `handle()` |

核心结构性问题（详见 §1）：

1. 记忆层"文档说委托、代码走双轨"
2. 分层循环依赖（core ↔ agents 双向、core 反向依赖 tools/skills）
3. 上帝文件（`backend/main.py` 1221 行、`core/agent.py` `handle()` 360 行）
4. 死代码（`core/critic.py` `suggest_improvements` 无调用点但 docstring 声称会调用）
5. 并发与状态安全（session GC TOCTOU、registry 无锁、模块级单例 8+ 处）

不需要推倒重来，但需要按 P0→P1→P2 顺序做一次结构化整改，否则后续每个新功能都会加剧技术债。

## 1. 核心结构性问题清单（评审发现）

### 1.1 记忆层"双轨存储"——文档说委托，代码没委托

文档 [05-core.md](./05-core.md) 声称 `MemoryStore` 内部委托到 `MemoryRepository`，但实际两套完全独立：

- `core/critic.py` → `MemoryStore.record_failure()` → 写 `memory/failures/`
- `core/agent.py` → `MemoryRepository.add_episode()` → 写 `memory/episodes/`

**后果**：`/api/patches` 与 `/api/episodes` 数据割裂，自演化闭环断链，failure 无法关联到 episode。

### 1.2 分层循环依赖

```
core/dag.py       → agents/learning.py    (基础设施反向依赖编排)
core/agent.py     → agents/*              (core 实际是编排根)
core/critic.py    → tools/base.py         (core 反向依赖能力层)
core/merger.py    → skills/models.py
agents/*          → core/*                (双向)
```

`backend/main.py` 出现 60+ 处函数内 lazy import 规避循环依赖——这是症状，不是设计。

### 1.3 上帝文件 + 上帝方法

- `backend/main.py` 1221 行，混了启动生命周期 + 20+ 路由 + 4 个业务函数。`approve_patch` 单函数 173 行、嵌套 3 层 if、新旧路径安全门禁不一致
- `core/agent.py` `handle()` 360 行，串了 6 个意图分支，每个分支重复"emit thinking → 执行 → emit final → record"模板
- emit 机制有两套排干机制（`_drain_pending` 中途排干 + `finally` 里 `gather`），且 critic future 用 `ensure_future` 立即调度，与 emit 的"延迟串行"语义冲突

### 1.4 死代码 + 文档撒谎

- `core/critic.py` `suggest_improvements`（约 60 行）全文无调用点，但 `_analyze` docstring 声称"confidence < 0.7 时调用 LLM"。复杂失败场景永远只走规则
- `backend/main.py` `approve_patch` 旧 schema 路径跳过 `_run_patch_regression` 和 `_build_patch_risk_summary`，绕过 M3-06 的发布门禁

### 1.5 并发与状态安全

- `backend/session.py:60-76` `gc` 存在 TOCTOU 竞态：锁内收集 → 释放锁 → 逐个 pop，窗口内被 touch 的 session 仍按旧快照被回收
- `skills/registry.py` 全文无锁，`reload()` 先 clear 再循环 `_index`，与并发 `add()` 会破坏一致性
- 模块级单例 8+ 处（sessions/hub/registry/store/config/logger/provider_manager/skill_manager_agent），测试靠 `reset_singletons` autouse fixture 手动重置
- `skills/registry.py:76` `max(versions.keys())` 字符串比较，"1.10.0" < "1.9.0"，active 版本会选错

### 1.6 代码层正确性 bug

| # | 位置 | 问题 |
|---|---|---|
| 1 | `agents/manager.py:131-153` vs `:99-124` | system_prompt 示例只有 `{type, params}`，schema 要求 `id/depends_on/parallel_group`，LLM 永远不会产出 DAG 字段 |
| 2 | `core/critic.py:424-428` vs `agents/learning.py:180` | 两模块对 `used_fallback` 定义相反，统计虚高 |
| 3 | `core/memory_repository.py:284-287` | FTS5 upsert 时只 INSERT 不 DELETE 旧 row，重复膨胀 |
| 4 | `core/memory_repository.py:644-691` | `recall` 是 async 但底层 SQLite 调用同步阻塞 |
| 5 | `core/memory_repository.py:201-243` | `_row_to_item` 按列下标魔法数字取值 |
| 6 | `agents/learning.py:62,86` | `_resolve_value` 把 dict/list 强转字符串 |
| 7 | `infra/auth.py:36` | `gen_session_id` 仅 16 bit 熵 + 时间戳，可预测 |
| 8 | `backend/main.py:935,1096,1106,1107,1121` | 路由层穿透 `store._registry._active_versions` 等私有属性 |

## P0 — 立即修复（高 ROI、低风险）

> 目标：修复影响正确性与安全性的 bug，删除冗余依赖。不改变 API 形态。

### P0-01 删除未使用依赖

- 优先级：高
- 范围：`requirements.txt`、`frontend/package.json`
- 内容：
  - Python 删除 6 个：`requests`、`PyPDF2`（已停止维护）、`trafilatura`、`beautifulsoup4`、`lxml`、`numpy`、`python-dotenv`（pydantic-settings 已内嵌）
  - 前端删除 2 个：`magic-string`、`@rollup/rollup-win32-x64-msvc`（平台锁定）
- 验收：`pytest -q` 全绿；前端 `npm test` 全绿；`pip install -r requirements.txt` 成功

### P0-02 修复技能版本比较 bug

- 优先级：高
- 范围：`skills/registry.py` L76、L100、L124
- 问题：`max(versions.keys())` 字符串比较，"1.10.0" < "1.9.0"，active 版本选错
- 修复：引入 semver 解析（`tuple(int(x) for x in v.split("."))`）或用 `packaging.version.Version`
- 验收：新增单测覆盖 "1.9.0" vs "1.10.0" vs "2.0.0" 场景

### P0-03 修复 Manager prompt 与 schema 不一致

- 优先级：高
- 范围：`agents/manager.py` L131-153 vs L99-124
- 问题：`system_prompt` 示例只有 `{type, params}`，但 `PLAN_SCHEMA` 要求 `id/depends_on/parallel_group`，LLM 永远不会产出 DAG 字段
- 修复：在 system_prompt 示例中补全所有字段，给出多步 DAG 示例
- 验收：e2e 测试覆盖"LLM 产出含 depends_on 的多步任务"场景

### P0-04 修复 session_id 可预测

- 优先级：高
- 范围：`infra/auth.py` L36
- 问题：`gen_session_id` = 时间戳 + 16 bit 熵，可预测
- 修复：全部用 `secrets.token_hex(16)`，去掉时间戳前缀
- 验收：单测验证长度与熵

### P0-05 修复 FTS5 索引重复膨胀

- 优先级：高
- 范围：`core/memory_repository.py` L284-287
- 问题：upsert 时 `INSERT INTO memories_fts` 无前置 DELETE，同 id 重复膨胀
- 修复：upsert 前先 `DELETE FROM memories_fts WHERE rowid=?`，或用 FTS5 external content table 模式
- 验收：单测覆盖"同一记忆更新多次后 FTS 命中不重复"

### P0-06 修复 used_fallback 定义冲突

- 优先级：高
- 范围：`core/critic.py` L424-428 vs `agents/learning.py` L180
- 问题：两模块对 `used_fallback` 定义相反，统计虚高
- 修复：统一为"实际触发了 fallback 路径才算 used"，即 `used_fallback = fallback_to is not None and not primary_result.success`
- 验收：单测覆盖"主路径成功 + 声明了 fallback"不算 used_fallback

### P0-07 Dockerfile 非 root 用户

- 优先级：中
- 范围：`Dockerfile`
- 内容：加 `RUN useradd -m app && USER app`
- 验收：`docker run` 后 `whoami` 返回 `app`

### P0-08 收紧依赖版本下限

- 优先级：中
- 范围：`requirements.txt`
- 内容：
  - `openai>=1.30`（原 `>=1.0.0`）
  - `anthropic>=0.35`（原 `>=0.25.0`）
  - `fastapi>=0.110`（原 `>=0.100.0`）
  - `pydantic>=2.7`（原 `>=2.0`）
- 验收：`pip install` 成功；启动正常

- 范围：`Dockerfile`
- 内容：
  - builder 阶段安装依赖 + 构建 frontend
  - runtime 阶段用 distroless 或 `python:3.12-slim` + 非 root 用户
  - 最终镜像不含源码、node_modules、.git
- 验收：镜像大小 < 300MB

### P4-02 前端生产化

- 优先级：中
- 范围：`docker-compose.yml`、新增 `frontend/Dockerfile`
- 内容：
  - 前端用 vite build 产出静态产物
  - nginx 托管 + 反向代理 `/api`、`/pubsub` 到 backend
  - 移除 `npm run dev` 开发模式
  - 统一端口（3000 或与 vite.config.js 一致）
- 验收：生产镜像无 node 进程

### P4-03 多环境配置

- 优先级：低
- 范围：`infra/config.py`、新增 `.env.example`/`.env.staging`/`.env.prod`
- 内容：
  - `ENV=dev|staging|prod` 加载对应文件
  - 环境变量覆盖 .env
  - secret 走 vault/KMS 或至少支持 `provider_api_key_fn` 回调
- 验收：三环境配置可切换

### P4-04 feature flag 独立 store

- 优先级：低
- 范围：`infra/config.py` L91-125
- 内容：
  - `set_feature_flag` 不再回写 `.env` 文件
  - 持久化走 SQLite 或配置中心
  - 加白名单：只允许 self_evolution 等 3-5 个 flag 运行时切换
- 验收：grep `_persist_env_var` 不再用于 feature flag
