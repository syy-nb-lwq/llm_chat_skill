# 现状评估与差距分析

> ⚠️ **历史快照** —— 本文是当时的评审/说明记录，**结论可能已过期**。
> 当前架构以根目录 [`ARCHITECTURE.md`../../ARCHITECTURE.md 为准；
> 活跃的问题与修复状态见 [`19-架构问题清单-2026-11.md`../19-架构问题清单-2026-11.md。
> 保留本文只为追溯"当时为什么这么判断"。

写这份文档的目的:回答两个问题 —— **这个项目现在能做什么、离预期目标还差什么。**

结论先说:**框架层面基本达成,产品层面差三步。**

所有判断都有实测支撑,不含推断。评估时间 2026-11-18。

---

## 后续决策：项目是本地单用户（2026-11-19）

本文的 P0-1（产物越权）与 P0-2（执行串味）都建立在**多用户并发**的前提上。
项目实际跑在使用者本地,只有他一个人 —— 这两条不再是缺陷：

| 原判定 | 单用户下的实际情况 |
|---|---|
| P0-1 产物越权：任何登录用户能下载任何人的文件 | 不存在"别人的文件"。鉴权链路（令牌 / user_id 归属校验）已整体移除 |
| P0-2 执行串味：用户 A 执行出用户 B 的代码 | 不存在"用户 B"。但**并发执行目录隔离仍保留**（按 `session_id` + `execution_id`）—— 并行的子智能体仍会抢同一个 `main.py`，那个坑是真的 |

相应地，多用户体系被整体剥离：`user_id` / `tenant_id`（含 SQLite schema 列）、
HMAC 令牌、假用户服务、`OWNER_TOKEN` 鉴权全部删除；记忆改为按 `scope` +
`agent_id` 分层隔离，工具归属改为 `owner_agent_id`。

**本文其余判断仍然成立** —— P1-3（首 token 32 秒）、P1-4（技能检索死接口）、
P1-5（技能库空）、P1-6（交付物无自检）、P2 系列，都是与用户数无关的问题。

「差的三步」相应调整为：
1. **交付物自检**（原第二步，P1-6）
2. **技能内容 + 检索两阶段**（原第三步，P1-4/P1-5）
3. **延迟结构**（P1-3，边做边说）

## 一、先看哪些能力是真能用的

我逐项实跑了一遍核心机制,不是看代码,是看结果。

| 能力 | 实测结果 | 耗时 |
|---|---|---|
| 工具调用 | `web_fetch` 拉取成功 | 3.3s |
| 代码沙箱 | 写文件 + 算 2^1024 + 产物收集,全通 | 0.2s |
| 目标循环 | 规划层说"没完"时真的跑了 3 轮 | <0.1s |
| 子智能体 | 派出后自己用了 web_search + web_fetch,带回结论 | 24.2s |
| 画像抽取 | 抽出 2 条,**证据逐字对得上** | 2.4s |
| 工具健康度 | 记账 + 判定,坏工具会被标出来 | <0.1s |
| 方法论沉淀 | 一次调研任务沉淀出草稿「产品快速调研」 | 3.4s |
| 工具自修复 | 正确拒绝修改内置工具源码 | <0.1s |

**这套机制是真的在跑,不是摆设。** 特别是画像抽取的证据校验 —— 它抽出来的每条都能指回用户原话。

## 二、缺陷清单

### P0-1 产物越权:任何登录用户能下载任何人的文件

```
用户乙(全新身份)下载 用户甲的产物 output/ai_drama_final_v2.mp4
  → HTTP 200,6003020 字节
未登录下载 → HTTP 401(这个是对的)
```

**根因**:`memory/workspace` 是全局单目录,`_resolve_artifact_user()` 只做**鉴权**(令牌有效即可),不校验**归属**。

**影响**:给团队用就等于所有产物互相可见。这跟项目定位("给团队/客户用的产品")直接冲突。

---

### P0-2 共享执行目录:并发时用户 A 执行了用户 B 的代码

```
用户A 期望输出 I_AM_USER_A,实际: 'I_AM_USER_B'
用户B 期望输出 I_AM_USER_B,实际: 'I_AM_USER_B'
✗ 串味了
```

**根因**:`python_exec` 的执行目录是 `memory/workspace/_run`(全局单例),而脚本固定写到 `_run/main.py`。两个并发请求会互相覆盖这个文件。

**影响**:不只是"输出串了"—— 是**执行了错误的代码**。对多用户产品,这是数据正确性事故。而且产物收集也会把别人的文件当成自己的交付物。

---

### P1-3 首 token 32 秒:工具全跑完才开始说话

从真实轨迹看一轮 task 的耗时:

```
plan        14387 ms   规划(含 L1 判别 + L2 规划)
tools       15987 ms   工具执行
first_token 32084 ms   ← 用户等 32 秒才看到第一个字
generate     5769 ms
total        40700 ms
```

**根因**:回答生成在 `execute_dag` **全部返回之后**才开始(`core/agent.py` 里 plan → tools → generate 是串行的)。

**影响**:这不是"慢",是"不知道在干嘛"。前端有 thinking 阶段提示,但用户仍然面对 30 秒空白。做产品这是硬伤。

---

### P1-4 技能检索是个死接口

`skills/registry.py::match(user_input, top_k)` 实现了带 top_k 的召回 —— **但没有任何生产代码调用它**。

现在的做法是 `agents/manager.py::_format_skills()` 把**所有**激活技能的完整 method 全量塞进提示词。

**影响**:
- 技能库空的时候没影响(现在就是空的)
- 一旦有 10 个技能,提示词会爆,planner 选技能的成本线性上升
- 这直接卡住"技能库能长大"这件事 —— 养到 10 个就装不下了

**讽刺的是**:我之前分析过要修这个,方案都写了,但一直没做。

---

### P1-5 技能库是空的

```
技能库(激活):0 个
待批草稿:9 个
```

方法论这根柱子,机制全齐(创建、版本、质量账本、回归样例、审批),**内容为零**。

草稿有 9 个,说明沉淀回路在跑;但没人批准,所以一个都没生效。

**影响**:按用户自己定的模型("skill 是做事的方法论"),这一项目前**不成立**。助手现在靠 LLM 现场规划,没在用任何沉淀下来的方法。

---

### P1-6 交付物没有自检

那个 5.6 秒的"成片"(实际应有 16.9 秒)能被当成成片交付。系统里**没有任何机制**能发现这件事。

现有的校验只到"工具执行成功"为止 —— 而 agent 是**成功执行**了一个错误的操作(复制文件代替拼接)。

**影响**:这是自增长体系的最后一块漏洞。前面的回路保证了"工具能造出来、能修好、能记账",但没保证**造出来的东西是对的**。

---

### P2-7 `execute_dag` 的接口陷阱

```python
async def execute_dag(self, tasks: List[ToolTask], ...)
```

规划层产出的 `tool_tasks` 是 **dict**,`execute_dag` 要的是 **ToolTask 对象**。传错报:

```
AttributeError: 'dict' object has no attribute 'id'
```

转换逻辑在 `core/agent.py::_run_plan_tasks` 和 `core/subagents.py` **各写了一遍**。

**影响**:我今天评估时自己就踩了这个坑。子智能体那处是今天上午刚补的,主路径到现在还没统一。

---

### P2-8 画像抽取每轮多一次 LLM 调用

每轮对话结束都会跑一次 LLM 抽取(短输入 <6 字会跳过)。

**影响**:对话成本增加约 1/3。抽取质量有证据校验兜着,值得,但这个开销应该记在账上,而不是默认开着。

---

### P2-9 新增链路没有基线

`tests/` 58 个文件覆盖得不错,但**自增长和自修复这几条新链路没有效果基线** —— 只有单元测试,没有"这条回路到底有没有提升"的度量。

## 三、能不能达成预期目标

用户的定位:

> skill 是做事的方法论;工具或者 mcp 是做事的工具;
> 智能助手就是要结合使用者的习惯,结合短期记忆和长期记忆,使用方法论来完成给出的任务。

逐条对账:

| 目标 | 状态 | 差什么 |
|---|---|---|
| 工具/MCP 层 | ✅ 达成 | 能造、能修、能记账、能跨重启恢复 |
| 使用者习惯 | ✅ 达成 | 画像有证据校验,常驻注入,能删 |
| 短期记忆 | ✅ 达成 | 全量保留 + 滚动摘要 |
| 长期记忆 | ✅ 达成 | 同上,机制齐 |
| **使用方法论** | ⚠️ **机制齐,内容空** | 库是 0;检索是死接口,库大了会装不下 |
| **主动发现并修复** | ⚠️ **半程** | 只能修自己造的工具;内置工具只能报告 |
| **交付物是对的** | ❌ **没有** | 无自检,会把 5.6 秒的假成片交出去 |

### 我的判断

**这是一个能力很强的框架,还不是一个好用的助手。**

差别在三层:

1. **框架层** —— 该有的骨架都有,而且是按"能自己长大"设计的,不是流水线。这一层做得比多数同类项目扎实。
2. **内容层** —— 空的。技能库 0 个激活,9 个草稿躺在那儿。方法论要用起来,得先有人批准、也得先有够用的技能。
3. **质量层** —— 缺一环。工具造得出来、修得动,但**造出来的东西对不对,没人验**。

### 差的三步(按优先级)

**第一步:隔离**(P0-1、P0-2)
这两个 bug 让"给团队/客户用"这件事现在不成立。修起来也不难:
- 产物按 `user_id` 分目录,下载时校验归属
- 执行目录按 `user_id` + `execution_id` 隔离,彻底断掉 `main.py` 覆盖

**第二步:质量门**(P1-6)
交付物自检:任务要求 vs 实际产出,不一致就自我否决。
比如"3 个镜头 → 16.9 秒"这个判据,系统应该能自己算出来。

**第三步:内容**(P1-5、P1-4)
技能库要真的有东西,靠两个动作:
- 把已有的 9 个草稿审一遍(不少可能是可用的)
- 检索改两阶段(`match()` 召回 top5 → LLM 选),否则养不大

## 四、几个可以说清楚的判断

### 1. 架构方向是对的

自增长的三个环节(造 → 用 → 修)都实现了,而且**边界划得清楚**:
- agent 只能改自己造的,内置源码不碰
- 写操作和带密钥的必须人批
- 修复必须过校验和测试,测试不过不替换

这套边界是这几天实打实踩出来的,不是设计出来的。

### 2. 但"自诊断"目前只能诊断到工具层

能查出"这个工具老失败",查不出"这次交付的东西是错的"。前者是**统计**,后者是**语义校验**,难度差一个量级。

### 3. 成本结构目前不健康

一轮 task 40 秒、4~5 次 LLM 调用(判别 + 规划 + 画像抽取 + 生成 + 可能的重规划)。
如果产品形态是"用户在等",这个延迟结构需要重新设计,至少要做到"边做边说"。

### 4. 有个反复出现的模式

这几天修的 bug 有共同点:**都是在"框架认为成功"的地方,实际上是失败**。
- 编译正则成功了 → 但被静态检查误拦
- 执行代码成功了 → 但跑的是别人的代码
- 拼接"成功"了 → 但没拼
- 造工具"成功"了 → 但工具不存在

**每次都是靠用户发现,不是靠系统发现。** 这正是 P1-6 要解的问题。

---

## 五、如果只做三件事

1. **隔离**(P0-1 + P0-2)—— 半天,让多用户可用
2. **交付物自检**(P1-6)—— 一天,让"做完了"这句话可信
3. **技能检索两阶段**(P1-4)—— 半天,让技能库能长大

这三件做完,系统才从"框架"变成"能交给别人用的东西"。

## 六、还没评估的

这次没覆盖,需要单独看:

- **长期成本**:对话量涨到几千轮时的表现
- **上下文质量**:滚动摘要的效果(摘要错了,后面全错)
- **MCP 稳定性**:外部源的断连重连
- **安全边界**:静态检查是启发式的,能绕过的写法应该列一遍
- **前端体验**:30 秒空白期的用户感受
