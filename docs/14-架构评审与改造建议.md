# 架构评审：当前实现能否达成工程目的

> 评审时间：2026-07-22
> 评审方式：读代码 + 实测（不是印象式评价）
> 结论范围：意图分层、记忆分层、技能学习、自演化、并发与部署
> **产品定位**：给团队/客户用的产品（不是单机自用）→ 并发、可观测、
> 真模型基线都是底线，不是加分项

---

## 0. 我理解的工程目的

从这几轮的对话倒推，你要的是一个**会越用越顺手的个人助理**：

| # | 目标 | 对应实现 |
|---|---|---|
| G1 | 准确理解我要干什么（不瞎猜、该问就问） | L0/L1/L2/L3 四层意图 |
| G2 | 记得住我（短期记得聊过什么，长期记得我是什么人） | 会话内容全量保留 + 用户画像 |
| G3 | 我教一次，以后自己会做 | `SkillTrainer` + 技能库 |
| G4 | 回答不对时能自己变好 | `ExecutionCritic` + 反思循环 |

如果实际目的是"做一个能演示的多智能体作品"，那 P0 里的 2.3/2.4 可以不急；
如果是"团队/客户真的在用"，**下面 P0 的 4 条必须解决**，否则它不会越用越顺手。

## 1. 结论

> **以下是评审当时的结论，保留原文作为对照。**
> 进度见 §6 改造路线 —— 2.1 / 2.2 / 2.3 / 2.4 / 2.5 / 3.1 / 4.2 已修，
> 4.1 部分已修，3.3 / 3.2 未动。

**管道是通的，智能没有被验证，反馈闭环是断的。**

- 能跑通的部分是真的通：WebSocket 事件流、身份与令牌、会话恢复、澄清事件、
  画像写入与隔离，都有实机验证撑着（不是只靠单测）。
- 但**"越用越好"这件事目前没有机制保证**：
  - 长期记忆影响不到回答本身（2.1）
  - 自演化拿不到"答案好不好"的信号（2.3）
  - 技能是提示词片段，不是可执行可验证的东西（2.4）
- 而且 **538 个测试里，LLM 全部是脚本替身** —— 验证的是管道，不是智能（4.1）。

一句话：**现在的系统可以"稳定地把错误答案端到你面前"，而且没有任何机制会因此变好。**

## 2. P0：会直接让工程目的落空的硬缺陷

### 2.1 长期记忆影响不到回答 ✅ 已修

**现象**：用户说"以后回答都用中文 / 不要用 emoji"，画像确实入库了，但**回答不会变**。

**根因**：

```
agents/manager.py:486     profile_block = self._build_profile_block(user_id)   # 只喂给 L2 规划
agents/orchestrator.py    orchestrate/stream 签名里没有 profile
agents/orchestrator.py    system_prompt() 是固定字符串「你是一个专业的回答生成助手」
```

而 `plan()` 的输出里 `plan_detail` 也**没有传给 orchestrator**。
结果：画像只影响"调哪个工具"，不影响"怎么说话"；
**闲聊轮压根不走 planner**，而说话方式偏好恰恰主要发生在闲聊轮。

**修法**（已落地）：

1. `OrchestratorAgent.orchestrate/stream` 增加 `profile_block`，拼进 **system prompt**
   （画像是"长期约束"，不是"本轮输入"，放 user 里会被当成任务输入而忽略）
2. `Agent.handle()` **每轮只取一次**画像，同时喂给 planner 和回答生成器
   （避免两处各读一次库、拿到不一致的内容）
3. `ManagerAgent.profile_block()` 公开化 + 读失败一律降级为空块

**实机验证**（真 WebSocket + 真 HTTP + mock 模型）：

```
1) 用户说 "以后回答都用中文"
2) GET /api/memories → [preference] 以后回答都用中文 (conf=0.9)
3) 下一轮闲聊的 system prompt:
     你是一个专业的回答生成助手。
     …
     [用户画像](长期记忆,请始终遵守)
     - [偏好] 以后回答都用中文

     以上「用户画像」是这个用户长期稳定的偏好与习惯,生成回答时必须遵守…
```

### 2.2 默认配置下向量检索是噪声 ✅ 已修

**现象**：`embedding_provider` 默认 `mock`，`MockEmbedding` 产生的是**随机向量**。
实测：`MockEmbedding` 下**无关句子的余弦相似度 = 0.8132**，
比真实模型的相关句还高 —— 所以**调阈值没用**，任何阈值都会同时放过噪声和误杀真命中。

**修法**：

1. `BaseEmbeddingService.is_synthetic` 标记（`MockEmbedding.is_synthetic = True`）
2. `SemanticMemoryStore.set_embedding_service()` **拒绝合成向量** → 语义通道关闭
   （构造函数显式注入时 `force=True`，测试仍能覆盖向量路径）
3. `config.embedding_provider` 默认改为 **空** = 不启用向量检索
4. `backend/main.py::_init_long_term_memory` 未配置 provider 时明确只走 FTS + 常驻注入
5. 向量通道阈值恢复为有意义的值（`embedding_min_similarity`，默认 0.35）

**实测对比**（10 条画像，查"北京天气"）：

```
修前: 0.01639 周报要有结论      ← 完全无关
      0.01613 用户是数据分析师
      （真正相关的"查询北京天气的记录"没进 top5）

修后: 0.0164  查询北京天气的记录  ← 正确命中
```

### 2.3 自演化拿不到"答案好不好"的信号 ✅ 已修

**这是 G4 落空的根因。**

```python
# core/critic.py:126
user_corrected = context.user_feedback is not None
```

但全仓 `user_feedback` **只在 critic 内部被读，从来没有任何地方写入**
（`core/agent.py::build_execution_context(...)` 没传这个参数）。

而 `success_rate` 的算法是：

```python
total_tasks = len(context.tasks)
if total_tasks == 0: success_rate = 1.0        # 没工具调用 → 直接判成功
success_count = sum(1 for t in context.tasks if t.success)   # 只看工具 HTTP 是否成功
```

| 情况 | 系统判断（修之前） |
|---|---|
| 工具调用成功 + 答案完全跑题 | **成功** |
| 没有工具调用 + 答案胡说 | **成功** |
| 用户下一轮纠正"不对，应该是…" | **完全不知情** |

**"从纠正中学习"这条链是死的**，而这恰恰是技能训练系统的核心信号。
叠加 `self_evolution_enabled` 默认 `False`，整个闭环默认不转。

#### 现在的实现

**信号入口有两条，走同一条链路：**

| 入口 | 可靠性 | 实现 |
|---|---|---|
| 前端 👍/👎 | 高（用户明确表态） | `POST`→ WS topic `feedback/<conn_id>` → `Agent.apply_explicit_feedback()` |
| 下一轮输入命中纠正语 | 中（规则判定，可能漏判） | `core/correction.py::CorrectionDetector` → 关联上一轮 `execution_id` |

**纠正语检测（`core/correction.py`）**：纯规则，**不做 LLM**。
误判代价不对称 —— 漏判一个纠正只是少学一次，误判一个正常输入会污染记忆库
（系统把"那再帮我看看明天呢"当成"错答"去学）。所以宁可漏判：

- 四类信号：`negation`（不对/错了/搞错）、`replacement`（应该是/我要的是）、
  `redo`（重来/再改）、`dissatisfaction`（太长/看不懂）
- 前置条件：**必须有上一条非空回答** —— 没有"被纠正的对象"就不构成纠正
- 排除纯确认（"好的"/"对"/"谢谢"）和惊讶（"不是吧"）
- 长输入（>60 字）降权 —— 更可能是"新任务 + 顺带吐槽"

**重评机制**：纠正发生在**下一轮**，而上一轮的 critic 早已跑完并记了"成功"。
所以 Agent 保留上一轮的执行上下文（`Agent._last_exec_ctx`），纠正时：

1. 用同一个 `execution_id` **重评**一次，这次带上 `user_feedback`
2. **撤销上一轮的"成功"记录**（`MemoryStore.remove_success`）——
   否则同一轮既算成功又算失败，采纳率就失真了
3. critic 侧：被纠正的轮次**记成失败、不记成功**，并生成 `fix_method` 补丁

**新的质量指标 —— 答案采纳率**：

```
采纳率 = 1 − (被用户纠正的轮数 / 有评估记录的轮数)
```

暴露在 `GET /api/memory/stats`（`adoption_rate` / `corrected` / `evaluated`）。
这是比 `success_rate` 诚实得多的指标 —— 一个"工具全通但答案全错"的系统
`success_rate` 能拿 100%，采纳率不会。

**实机验证**（真实 HTTP + 真实 WebSocket，mock LLM）：

```
[3] 第 1 轮完成 execution_id=exec-1794054545251-d0eaa000
[4] 纠正已处理          ← 隐式路径:"不对，我问的是北京" → replacement, conf=0.90
[5] 普通追问已处理      ← 误判检查:"那再帮我看看明天呢" → 未触发纠正
[6] 反馈已受理 ok=True  ← 显式路径:👎 → feedback_ack
[7] 采纳率=0.6667 evaluated=3 corrected=1
```

> **注意**：critic 写记录受 `SELF_EVOLUTION_ENABLED` 开关控制（默认 `false`）。
> 纠正**检测**一直都在，但开关不开就只检测不学习。上面这次验证开了这个开关。

### 2.4 技能没有可执行、可验证的形态 ✅ 已修

**现状**：一个"技能"= `Skill.method` 一段文本 + `steps` 列表。
- `steps` 的 DAG 执行默认关闭（`skill_dag_enabled=False`）
- orchestrator 只是把 `method` 塞进提示词
- 自动发布的"验收"是静态检查 + 回归样例，而**回归样例是补丁提出者自己给的**

**后果**：教一次 → 得到一段提示词 → **下次能不能做对，没有任何判定依据**。
技能会越积越多，但无法回答"这个技能到底靠不靠谱"。

#### 现在的实现：技能质量账本（`core/skill_quality.py`）

把两类信号合到**一张账本**上：

| 信号 | 来源 | 性质 |
|---|---|---|
| `sample` | 发布/升级时跑回归样例（`ResultValidator`） | 离线、确定、可复现 |
| `usage` | 技能被真实使用后，用户有没有纠正这一轮 | **线上、真实** |

`usage` 这一路接的是 **A-06 的纠正链路** —— 那才是真正的 ground truth。
"工具全调通了但用户每次都要纠正"这种情况，只有 `usage` 能抓到。

**账本**：追加写的 JSONL（`memory/skills/quality.jsonl`），滑动窗口统计。

**同一次执行只算一次**：一轮先被判"成功"，用户下一轮纠正后重评为"失败"——
两次都留着的话，这一轮既算成功又算失败，通过率被抹平。
所以 `usage` 记录带 `execution_id`，后写的覆盖先写的。

#### 自动降级

| 判据 | 阈值 | 含义 |
|---|---|---|
| 验收样例 | 最近 2 次通过率 < 60% | 连自己声明的验收标准都过不了 |
| 线上使用 | 被用过 ≥5 次，采纳率 < 50% | 用户一直在纠正它 |

降级后**不再被 planner 选中**（`SkillStore.list_all()` / `match()` 过滤掉），
管理界面仍然能看到（带徽章 + 原因）。

**降级是推导出来的，不是贴上去的标签** —— 账本数据变好就自动恢复，
不需要人工解封（免得忘了又变成一潭死水）。
所以判据看的是**最近几次**而不是历史聚合：一个早期失败、后来修好的技能，
不会被历史拖住永远降着。

**记账失败 ≠ 降级**：账本挂了的时候返回空集合，绝不能因为账本出问题就把所有技能都禁用掉。

**可观测**：`GET /api/skills/quality` 返回每个技能的通过率与降级状态；
`GET /api/skills` 的每条技能带上 `quality` 字段；前端技能管理面板显示
「通过率 xx%」/「已降级」徽章。

**仍存不足**：验收样例仍然是"谁提补丁谁给"，独立于实现者的标准还没有。
这一条要靠人工审阅样例来兜（`POST /api/patches/{id}/approve` 的审批环节）。

## 2.5 附带发现：中文全文检索等于没有 ✅ 已修

不在原评审清单里，是修 2.2 时被新测试逼出来的。

FTS5 的 `unicode61` 分词器把连续汉字当成**一个** token，
所以「查询北京天气的记录」和「北京天气」永远匹配不上
（`trigram` 要求 ≥3 字符，两字中文同样无解）。

**这意味着**：修好 2.2、让向量通道正确关闭之后，
**中文场景下唯一剩下的检索通道也是死的** —— 长期记忆写进去就再也读不出来。

**修法**：抽出 `core/text_match.py`（二元组切分 + 命中比例打分，
原本只在会话检索里用），给长期记忆检索加一条 **CJK 通道**，
和 FTS 通道一起进 RRF 融合。

**实测**（修前 → 修后）：

```
修前: 查询"北京天气" → 0 条结果
修后: 查询"北京天气" → 查询北京天气的记录   ✓
      查询"回答语言" → 以后回答都用中文      ✓
      查询"数据分析师" → 我是数据分析师      ✓
      查询"画图步骤" → 第一步先取数第二步再画图 ✓
```

性能：2000 条记忆下单次检索 11.9ms（两阶段取数：先只算 id+content，
命中后才取完整行，避免为几百个候选解析 JSON）。

## 3. P1：规模化前必须处理

### 3.1 SQLite 没有并发设置 ✅ 已修

**证据**：`core/memory_db.py` + `core/session_memory.py` 共 **16 处裸 `sqlite3.connect()`**，
**0 处** `journal_mode=WAL`、**0 处** `busy_timeout`、无连接复用。

**后果**：两个 WebSocket 客户端同时写 → `database is locked`。
单机单人跑不出问题，**多用户并发写就会间歇性失败**。

**修法**（已落地）：新增 `core/sqlite_util.py::connect()` 工厂，
统一 `journal_mode=WAL` + `busy_timeout=10000` + `synchronous=NORMAL`，
16 处改成调它。

**实测**：8 线程并发写 200 条 → 0 错误、0 丢数据、0.49s。

### 3.2 会话状态在进程内存 ⏳ 触发条件未到

`backend/session.py` 仍是进程内 `dict`。内容已落库（短期记忆不丢），但：
- 无法多实例部署（同一用户的 WS 必须落到同一进程）
- 重启后所有连接断开，前端要重连

**修法**：要横向扩展就把 session 换成 Redis 或签名的无状态令牌。
**触发条件**：真的要开第二个进程时再改，现在不必。

### 3.3 每轮最多 3 次串行 LLM 往返才出第一个字 ⏳ 未做

```
L0 规则(0 LLM) ──未定案──> L1 判别(1 次) ──低置信──> L2 规划(1 次) ──> 回答生成(1 次)
```

实测在评估集上 **L0 只定案 19/38（50%）**（对抗性样本集，真实流量会高一些）。
trace 已经能直接回答"这一轮慢在哪"（见 §4.2）。

**可选优化**（按需）：
- L1 与 L2 合并成一次调用 —— 会牺牲"分层可评估性"
- `INTENT_MODEL` 指向便宜快模型（已有开关，默认复用主模型）

## 4. P1：验证体系

### 4.1 620 个测试，LLM 全部是替身 ⏳ 部分已修

这是**当前最容易被高估的地方**。

- `tests/` 里 LLM 一律被替换成脚本化响应
- `--live` 通道（真实模型跑评估集）**需要真实 key 才能跑**

所以能确认的是：**管道、降级、隔离、边界**都对。
**不能确认**的是：意图判得准不准、澄清问得好不好、答案好不好。

**风险**：所有"质量"改动（改提示词、改标签定义、改抽取规则）都无法验证是变好还是变坏。

#### ① 真机基线已经跑起来了（DeepSeek `deepseek-flash`）

| 通道 | 指标 | 数值 |
|---|---|---|
| 结构守卫 | 定案率 | 0/38（只判空输入——见 §2.3 的重构） |
| L1 开发集（38 条，**全量走 L1**） | 准确率 | **100%** |
| L1 留出集 + 封存集（95 条） | 准确率 | **95.8%~96.8%**（均 96.3%） |
| 画像抽取（规则） | 精确率 / 召回率 | **100%** / 100% |

**基线是一个分布，不是一个数**：LLM 非确定性，同一条输入两次可能给出不同标签。
`--repeat 3` 会报 min/mean/max，并且**用最差的那一遍做闸门** —— 基线不能靠运气。

#### ② 建基线当场抓到的四个真缺陷

**这是这次投入最大的回报：四个缺陷都不是"模型不够聪明"，全是工程问题。**

| # | 缺陷 | 表现 | 根因 |
|---|---|---|---|
| 1 | **L0 抢在 L1 前面误判** | 「教我怎么用这个工具」被判成 `teach`，用户请助手讲解却被塞进技能学习流程 | L0 有一条**裸关键词分支**（只要出现「教我」就判 teach），排在结构化规则**前面**，LLM 根本没被问到 |
| 2 | 「以后…用…」被判成 teach | 「以后别再用那种语气跟我说话」进技能学习 | 约定信号的正则把「用」「走」当触发词，一个「用」字就命中 |
| 3 | 易混对指标**结构性地永远为 0** | 任何一次易混错都会让闸门失败 | 分母用 `(predicted, expected)` 二元组计数，而二元组里两个标签**必然不等** → "判对"永远进不了分母 |
| 4 | 网络抖一下，基线显示"准确率 20%" | 会误导人删掉本来对的提示词 | 调用失败被记成 `unavailable`，等价于判错。现在**通道不可用就判定本次基线无效**，不出数字 |

**第 1 条最值得记**：我先按"模型判错"去改提示词，
**连续改了 5 版**（加易混反例 / 加定义边界 / 重排成决策流程 / 枚举加注释 / 把 `label` 调到 `reason` 之后），
准确率**一点没动**。最后去查"这句话到底有没有到 LLM"，
才发现是 L0 在 30 毫秒内就把它抢走了。
**教训：改之前先确认这一层有没有被调用。**

随后做了一个更彻底的实验：**把意图规则全部拿掉，只留 LLM**——
130 条标注用例上准确率从 **94.7% 升到 97.7%**。
结论：规则不只是"没帮上忙"，它**在拖低准确率**。详见 `docs/12` §2.3。

#### ③ 留出集机制（防自欺）

改完提示词就见效，很容易是"背下了句子"。所以：

- `intent_eval.jsonl` —— 开发集，用来定位问题
- `intent_eval_holdout{,2,3,4,5}.jsonl` —— **每一批都在改完提示词之后才写**
- `intent_eval_sealed.jsonl` —— 封存集，只在最后跑一次

**留出集上的错误里，有一半是我自己标错的**（而不是模型判错）：

| 我标的 | 实际应该 | 为什么我错了 |
|---|---|---|
| 教我怎么用这个工具 → teach | task | 「教我」有方向：用户教助手 vs 助手教用户 |
| 这个方案太热了 → task | clarify | 用户没请求任何动作 |
| 嗯就那样 / 想起个名字 / 那个字怎么写来着 → clarify | task | 按文档自己的规则「宁可 task 也不要 clarify」 |

**剩余 5 条错判的诚实拆分**（95 条里）：2~3 条是模型真的判错
（`teach` 对「以后…别用…」和「教我**用**…」仍然过判），
2 条是**我的标注**按产品自己的 clarify 规则站不住。

**这件事本身就是结论**：给主观标签打标注，比想象中难；
标错的方向往往是"往自己以为的语义上靠"，而不是"往产品行为上靠"。

#### ④ 仍然缺的部分

- **答案质量没有基线**（只有意图和画像）。要建得先有人工标注的问答对。
- **澄清问得好不好**没有度量。
- 这套基线是**单模型**（`deepseek-flash`）的；换模型要重跑，不能直接沿用数字。

#### ⑤ 管线验证（不需要 key）

`tests/mock_openai.py` 起一个本地 OpenAI 兼容服务，
`tests/test_live_channel_plumbing.py` 用它把整条 `--live` 路径跑通：

- L1 分类器：提示词 → HTTP → OpenAI SDK → 解析成标签（真的走网络栈）
- 评估通道：准确率 / 易混对指标能被真正算出来
- `scripts/intent_eval_nightly.py --live` 这条命令本身能跑通

**它验证的是"管线通不通"，不是"模型准不准"。**
准确率仍然需要真实模型 —— 那件事没法用替身代替。

**这一步当场抓出两个致命 bug**（都是"从没跑过"掩盖下来的）：

| Bug | 后果 |
|---|---|
| Provider 注册只写在 FastAPI lifespan 里 | **所有独立入口**（nightly `--live`、CLI、Streamlit）第一次调 LLM 就炸 `Provider 'openai' 未注册` |
| 测试用 `_l_mod.get_llm_client = lambda: StubLLM()` 直接赋值且没还原 | 后面所有测试拿到的都是假 LLM —— 测试全绿，但真 LLM 通道**从来没被执行过** |

修复：Provider 改成**懒初始化**（`LLMClient.provider` 发现没注册就按配置注册一次，
入口不可能再"忘记"）；测试全局改写由 `conftest.py` 统一还原 + 一条断言守着。

#### ⑥ 画像抽取基线（纯规则，不需要 key）

画像抽取是**纯规则**的，不需要 key —— 所以基线可以立刻建，不用等。

- `tests/data/profile_eval.jsonl`：39 条标注用例（5 个类型 + 10+ 条负例）
- `scripts/profile_eval.py`：精确率 / 召回率 / 分类型报告
- `tests/test_profile_eval.py`：CI 闸门（精确率 ≥95%、召回率 ≥80%）
- `scripts/intent_eval_nightly.py` 现在**一条命令跑两个基线**

**精确率是生死线**：一条错误的画像会持续影响此后每一轮（docs/13 §2.8「宁缺毋滥」）。

**基线数值**：

| 指标 | 修复前 | 现在 |
|---|---|---|
| 精确率 | 86.7% | **100%** |
| 召回率 | 100% | **100%** |

建基线时顺带修掉三个真实缺陷：

1. **同一条方法论存两份** ——「正确做法是先备份再迁移」同时命中两条规则，
   存了两条几乎一样的内容（浪费注入预算 + 提示词里出现两遍）
2. **用户的个人安排被当成偏好** ——「以后我们开会要提前十分钟」
   会被记成"用户偏好"，助手可能真的照着调整
3. **对当前一轮的反应被当成长期偏好** ——「我喜欢这个方案」

### 4.2 没有 per-stage 观测 ✅ 已修

**修法**（已落地）：

1. 新增 `core/trace.py`：`TurnTrace` + `TraceRecorder`（JSONL，一行一轮）
2. `Agent.handle()` 记录 `plan / tools / generate / first_token / total`
   + `intent_layer / intent_confidence / tool_count / profile_chars / reply_chars`
3. 新增 `scripts/trace_report.py` 汇总（p50/p95/max，按意图层分组）
4. 新增 `GET /api/traces?limit=` 接口

**注意**：`total` 必须用 `time.perf_counter()`（单调时钟），
不能和 `time.time()`（wall clock）混用 —— 混用会被 clamp 成 0（这个 bug 被新测试当场抓住）。

**实测**：

```
$ python scripts/trace_report.py

  plan            2       2.0       0.2       3.9       3.9
  generate        2       0.1       0.1       0.1       0.1
```

## 5. 当前做对了、不要动的部分

- **记忆按"记的是什么"分层**（短期=会话内容全量保留 / 长期=用户画像），
  而不是按 TTL —— 这个判断是对的，也是你最初提的
- **存储 ≠ 注入**（全量保留、预算注入）—— 概念清楚，避免"为了省 token 而删历史"
- **意图四层 + 双通道评估集 + 混淆矩阵** —— 这是可演进的形态，比单次 LLM 输出意图强
- **事件流/身份/令牌/会话恢复** —— 有实机验证，是真的通
- **`user_id` 强制过滤** —— 数据隔离这道闸是硬的

## 7. 明确不建议做的事

- **不要**为了"多智能体"再拆更多 Agent。现在的 3 个 Agent（Manager/Learning/Orchestrator）
  职责已经清楚，再拆只是增加 LLM 往返
- **不要**上向量数据库（Qdrant/pgvector）。当前规模（<1 万条）SQLite + Python 打分够用，
  真正的瓶颈是 2.2 的噪声问题，不是数据库
- **不要**做知识图谱。画像条目还没稳定，图谱化只会把噪声结构化
- **不要**用 LLM 替代规则做画像抽取（docs/13 D14）。规则漏抽的代价可控，LLM 误抽的代价是长期污染
  （基线已经证明：规则抽取精确率能到 100%，没有必要引入 LLM）
- **不要**用 LLM 做纠正检测（2.3）。纠正误判的代价是**长期污染记忆库**，
  规则宁可漏判；LLM 在这里只会把不确定的判断变成确定的错误
- **不要**在每次使用技能时都跑一遍验收样例来算通过率。太贵。
  线上信号（A-06 的纠正）本身就是最好的验收样例 —— 用它

## 8. 改造过程中被实机验证抓到的坑（值得单独记）

| 坑 | 表现 | 教训 |
|---|---|---|
| notify 帧同时带 `request` 和 `response`（后者为 null） | 用 `"response" in data` 判断会把 notify 当响应吃掉，客户端永不 ACK，服务端 10s 后放弃推送 | 判空用真值（`data.get("response")`），别用 `in` |
| `time.time()` 与 `time.perf_counter()` 混用 | trace 耗时全被 clamp 成 0 | 耗时统一用单调时钟 |
| mock 向量余弦相似度 0.81 | 阈值调高调低都无解 | 合成向量要**类型级拒绝**，不是调参 |
| FTS5 unicode61 切不开中文 | 修好向量降级后，中文检索结果为空 | 关闭一个通道前必须确认另一个通道真的能用 |
| `"feedback/"` 是 **9** 个字符 | `topic[8:]` 切出 `/conn-id` → 令牌校验必失败 → 前端点👎没反应 | **切片长度要写测试**；协议前缀别靠手数 |
| 上游返回空内容 | 前端只渲染出一个空气泡，用户以为系统卡死 | 回答出口统一兜底（`Agent._ensure_answer`） |
| 正则有捕获组时 `findall` 返回**组内容**不是整个匹配 | 纠正检测全部漏判（返回 `['']`），且不报错 | 用 `finditer` + `group(0)` |
| 测试跑完 `memory/` 里出现失败/成功/trace 文件 | 生产观测数据和测试数据混在一起 | `conftest.py` 隔离 `MemoryStore` 和 `TraceRecorder` |
| Provider 注册只写在 FastAPI lifespan 里 | nightly `--live`、CLI、Streamlit 第一次调 LLM 就炸 `Provider 'openai' 未注册` | 初始化要**懒加载**，不能指望每个入口记得调 |
| 测试直接赋值 `_l_mod.get_llm_client = lambda: StubLLM()` 且没还原 | 后面所有测试拿到的都是假 LLM；测试全绿，但真 LLM 通道**从没被执行过** | 替身用 `monkeypatch`；再加一条断言守着全局入口没被改 |
| 同一轮先记"成功"、后被纠正记"失败" | 通过率被抹平（既算成功又算失败） | 质量账本的记录带 `execution_id`，后写的覆盖先写的 |
| 降级判据用历史聚合通过率 | 早期失败、后来修好的技能永远降着 | 看**最近几次**，让降级能自动恢复 |
| 画像规则命中重叠 | 同一条方法论存两份，浪费注入预算 | 同类型 + 内容重叠 → 只留更完整的那条 |
