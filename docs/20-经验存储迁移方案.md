# 经验存储迁移方案（MemoryStore JSON → SQLite）

> 状态：**已执行完成**（2026-11-20）。对应 `docs/19` §07。
> 本文记录迁移的动机、做法，以及回滚路径 —— 它是唯一一条动过既有数据的改动，
> 留档是为了以后出问题时能按步骤退回去。

## 1. 迁移前：两个库，职责互斥（不是副本）

| 库 | 载体 | 存什么 | 写入方 | 读取方 |
|---|---|---|---|---|
| `MemoryStore` | `memory/failures/*.json`、`successes/*.jsonl`、`skill_patches/pending/*.json` | 失败诊断 / 成功模式 / 待审补丁 | `core/critic.py`（3 处） | `memorykit/long_term`、`core/reflect.py`、`agents/manager.py` |
| `MemoryDB` | `memory/semantic_memory.db` | 用户画像（5 种类型） | `core/memory_writer.py`、`core/semantic_memory.py` | `memorykit/long_term`、REST API |

调用方视角早就统一到 `core/memorykit/`（见 `ARCHITECTURE.md` §6.1），
所以"失败记录存哪"对主链不再有歧义。剩下的问题在**数据层**：

- 跨库统计要查两次（想回答"这个用户的雷区里，哪些已经踩过两次以上"，
  得先查画像、再遍历 JSON 目录，在 Python 里做 join）；
- 备份有两份口径（一个 SQLite 文件 + 一堆目录）；
- 没有事务，写到一半崩掉会留下半份记录。

## 2. 目标与结果

`MemoryDB` 与 `MemoryStore` 成为**同库不同表**，`experience` 表承接全部经验：

| 问题 | 库 | 表 |
|---|---|---|
| 这个人是谁？ | `MemoryDB` | `memories`（FTS + 向量，供语义检索） |
| 什么做法有效/无效？ | `MemoryStore` | `experience`（原文存 `payload`，常用字段提列） |

为什么仍然分表而不合并：两者的写入时机、去重策略、检索方式都不同
（画像要"语义检索 + 置信度合并"，经验要"按时间倒序 + 完整原文"）。
强行合成一张表要加一堆互斥的 `type` 分支，反而更难读。
分表但同库，既保留各自语义，又拿到了关联与备份的便利。

`experience` 表设计上的两个取舍：

- **`payload` 存完整原文**，其余列（`scenario` / `skill` / `status` /
  `success_rate` / `confidence`）是冗余副本，只用于过滤和排序 ——
  这样加字段不用改表，读的时候以 `payload` 为准；
- **不对 `content_hash` 加唯一约束**：同一段诊断文本在不同轮次出现是正常的
  （`trace_id` 不同），加唯一约束会把第二条静默丢掉。幂等只在导入时显式判断。

## 3. 历史数据导入

`scripts/migrate_experience_to_sqlite.py`，四个安全设计：

- **默认 dry-run**：不加 `--apply` 只报告，在临时库上跑同一套导入逻辑，不碰真实库；
- **自动备份**：`--apply` 先把 `memory/` 复制成 `memory.bak-<时间戳>`；
- **幂等**：按 `id` 或 `content_hash` 判重，重复运行不重复插入；
- **可回滚**：按 `batch_id` 精确删除本次导入的记录。

```bash
python scripts/migrate_experience_to_sqlite.py --dry-run          # 看会迁什么
python scripts/migrate_experience_to_sqlite.py --apply            # 迁移 + 备份
python scripts/migrate_experience_to_sqlite.py --rollback <id>    # 回滚
```

执行顺序（脚本已经把 1、4 自动化，2、3 是人工核对）：

1. 停掉服务，确保没有 in-flight 的 `critic.evaluate()`；
2. 跑 `--dry-run`，核对条数与人工预期；
3. 跑 `--apply`，记下输出的 `batch_id` 与备份路径；
4. 抽查：`SELECT kind, count(*) FROM experience GROUP BY kind;`
5. 核对 `GET /api/memory/stats` 数字与旧 JSON 一致后，才删旧目录。

迁移**不会自动发生**：`MemoryStore` 启动时不会偷偷扫描老目录。
自动迁移一旦猜错就没人知道发生了什么 —— 必须显式执行。

### 3.1 实际执行记录（2026-11-20 11:12）

```text
batch_id : import-20261120111205-28231a
备份     : memory.bak-20261120-111205
扫描 25 条 → 新插入 24 条（跳过 1 条）
  failure 8 / patch 9 / success 7
```

**25 进 24，那 1 条是什么**：`success_index.jsonl` 里有两条 `id` 相同的记录，
都是 `succ_exec-1795084615015-6bb1d321`，相隔 10 秒写了两遍、只有 `latency_ms`
不同（35898 / 18777）。这是旧载体的老问题 —— `.jsonl` 是 append，同一 trace
记两次不报错也不去重；新表以 `id` 为主键，`_insert` 是
`ON CONFLICT(id) DO UPDATE`，天然只剩一条。

所以 `success` 的真实条数是 **6 个唯一 trace 被记了 7 次**，迁移顺手修掉了一处
统计虚高。**这不是数据丢失**，是去重。

对账结果：

| 检查 | 结果 |
|---|---|
| JSON 侧唯一 id | 24 |
| 库内条数 | 24 |
| 缺失 / 多出 | 无 / 无 |
| 字段级差异 | 1 处，即上面那条重复记录的 `latency_ms` |
| 回滚演练（在副本上） | 24 条精确删除；回滚后库仍可继续写入 |
| `export_json()` 单向出口 | 四类产出正常 |

字段差异的取舍：导入时遇到同 `id` 是 **skip**（保留先出现的那条），
运行期 `record_success` 是 **UPSERT**（保留最新）。两者不一致是刻意的 ——
导入若用 UPSERT，重复执行会覆盖运行期新写入的同 id 记录，违背幂等承诺。

### 3.2 执行后才发现的一个读路径遗留

迁移完第一轮验收时 `GET /api/memory/overview` 仍返回 `lessons = 8`，
和库里的数一样，**看起来是对的**。但把一条探针写进 `experience` 表后，
接口数字**没有变化** —— 这才暴露它仍在 `rglob("memory/failures/*.json")`。

症状很典型：迁移那一刻数字对得上，之后**新产生的教训一条都不会显示**，
而且不报错。已改为走 `get_memory_store().get_recent_failures()`，
并补 `test_overview_lessons_come_from_store_not_json_dir`（临时目录下没有
`failures/`，能从 `recent` 读到刚写入的诊断就只可能是走库）。

教训：**"数字对得上"不等于"读的是新地方"** —— 迁移后验证要写一条带标记的
新数据，看它是否立刻出现，而不是比对存量条数。

## 4. 回滚

```bash
# 1. 删掉本批次导入的记录
python scripts/migrate_experience_to_sqlite.py --rollback <batch_id>

# 2. 连备份一起恢复
rm -rf memory/ && cp -r memory.bak-<时间戳> memory/

# 3. 代码层面
git revert <迁移提交>    # 回到 JSON 读写
```

**顺序不能反**：先 `revert` 再 `--rollback` 会有一小段时间"两边都写"，
期间的数据哪边都不可信。

## 6. 这次为什么敢动数据

前一轮只交付了方案、没动数据，理由是"3–5 天、风险高、必须先出迁移与回滚"。
这一轮补齐了前置条件后才执行：

1. 回滚路径是**两条独立通道**（数据侧 batch 回滚、代码侧 `git revert`），
   任何一条单独可用；
2. 导入是**幂等**的，重复执行不会产生副本 —— 这消除了"跑到一半失败要不要重来"的判断；
3. 主链的接口一个都没改：`get_memory_store()` 返回的对象方法签名不变，
   critic / API / manager 的调用点零改动，回归面因此收窄到存储层自身。
