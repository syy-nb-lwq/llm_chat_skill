# 经验存储迁移方案（MemoryStore JSON → SQLite）

> 状态：**方案与脚本就绪，数据未迁移**（2026-11-20）。
> 对应 `docs/19` §07。这是唯一一条需要动既有数据的架构问题，
> 所以单独出方案、单独排期，不和其它改动混在一次提交里。

## 1. 现状：两个库，职责互斥（不是副本）

| 库 | 载体 | 存什么 | 写入方 | 读取方 |
|---|---|---|---|---|
| `MemoryStore` | `memory/failures/*.json`、`successes/*`、`skill_patches/*` | 失败诊断 / 成功模式 / 待审补丁 | `core/critic.py`（3 处） | `memorykit/long_term`、`core/reflect.py`、`agents/manager.py` |
| `MemoryDB` | `memory/semantic_memory.db` | 用户画像（5 种类型） | `core/memory_writer.py`、`core/semantic_memory.py` | `memorykit/long_term`、REST API |

调用方视角已经统一到 `core/memorykit/`（见 `ARCHITECTURE.md` §6.1），
所以"失败记录存哪"对主链不再有歧义。剩下的问题在**数据层**：
跨库统计要查两次，备份有两份口径，无法用一条 SQL 关联画像与经验。

## 2. 目标

让 `MemoryDB` 成为**唯一的事实源**，`MemoryStore` 降级为只读历史/导入源：

1. `MemoryDB` 增加 `experience` 表（脚本已实现）；
2. 历史 JSON 一次性导入，`MemoryStore` 保留只读，不再新增写入；
3. `critic` 与 `GET /api/memory/overview` 从同一张表读经验；
4. 提供 `export_json` 单向出口（备份/人工审阅用）。

## 3. 迁移脚本

`scripts/migrate_experience_to_sqlite.py`，四个安全设计：

- **默认 dry-run**：不加 `--apply` 只报告，不写盘；
- **自动备份**：`--apply` 先把 `memory/` 复制成 `memory.bak-<时间戳>`；
- **幂等**：`(kind, content_hash)` 唯一键，重复运行不重复插入；
- **可回滚**：按 `batch_id` 精确删除本次写入。

```bash
python scripts/migrate_experience_to_sqlite.py --dry-run          # 看会迁什么
python scripts/migrate_experience_to_sqlite.py --apply            # 迁移 + 备份
python scripts/migrate_experience_to_sqlite.py --rollback <id>    # 回滚
```

当前 dry-run 实测：`memory/` 下有 **17 条**待迁经验
（failures 8、skill_patches 9；successes 0）。

## 4. 执行步骤（必须按顺序，分两次提交）

### 第一步：只搬数据（本次不做）

1. 停掉服务，确保没有 in-flight 的 `critic.evaluate()`；
2. 跑 `--dry-run`，核对条数与人工预期；
3. 跑 `--apply`，记下输出的 `batch_id` 与备份路径；
4. 用 sqlite3 抽查：`SELECT kind, count(*) FROM experience GROUP BY kind;`
5. **提交只含数据与脚本的变更**，不碰任何读写代码。

### 第二步：切读写（另一次提交）

1. `critic.py` 的 `record_failure/record_success/add_pending_patch` 改为写 `experience` 表；
2. `memorykit/long_term.py` 的经验查询改走新表；
3. `GET /api/memory/overview` 从新表读，验证与旧 JSON 数字一致；
4. 全量回归（当前基线 1028 passed）；
5. 观察 24h 无异常后，把 `MemoryStore` 标记为 deprecated（保留代码，不删）。

## 5. 回滚

任一步出问题：

```bash
# 1. 删掉本次迁移写入的数据库记录
python scripts/migrate_experience_to_sqlite.py --rollback <batch_id>

# 2. 如果需要连备份一起恢复
rm -rf memory/ && cp -r memory.bak-<时间戳> memory/
```

读写切换提交若出问题，先 `git revert` 那次提交（恢复 JSON 读写），
再跑 `--rollback` —— **顺序不能反**，否则会有短暂的"两边都写"。

- [x] 迁移脚本存在，支持 dry-run / 备份 / 幂等 / 回滚（第一步前置条件完成）

- [ ] `/api/memory/overview` 与 critic 读到的记录来自同一张表（第二步完成）

## 7. 为什么这轮不做数据迁移

`docs/19` §07 自己标的是"3–5 天、风险高、必须先出迁移与回滚"。
把数据搬迁和读写切换拆成两次提交，是为了让**任何一步失败都能单独回滚**。
如果合在一次改动里，一旦新数据格式有兼容问题，回滚路径会同时涉及代码和数据，
风险不可控。
