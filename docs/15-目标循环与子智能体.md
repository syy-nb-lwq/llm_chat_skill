# 15 · 从「一问一答」到「目标驱动的助手」

> 起因：用户指出「一轮对话就完了，没有自行探索、造工具、用技能把任务做完的想法；
> 而且应该能组织一或多个子智能体执行任务，主智能体还要能探测到它们的完成情况」。
>
> 这个判断是对的。本文说明现状错在哪、怎么改、以及**必须防住什么**。

---

## 1. 现状：一条直线，不是循环

`core/agent.py::handle()` 现在的形状：

```
纠正检测 → 规划(L1/L2) → 若 clarify 则追问
                        → 否则 执行一次 DAG → 生成回答 → critic 打分 → 结束
```

一次 `handle()` 里，**规划只发生一次，工具只执行一轮**。所以：

| 用户想要 | 实际发生 |
|---|---|
| 「造个工具，用它，再拿结果算东西」 | 造工具（若规划到了），然后**直接用文字回答**，不会再用新工具 |
| 「造工具失败了，改一版再试」 | 不会重试 —— 没有第二轮 |
| 「这个任务要分几步」 | 规划层若只给一步，就只有一步 |
| 「同时做三件互不依赖的事」 | 串行做完，或者干脆只做一件 |

**根因不是模型笨，是架构里根本没有"循环"这个结构。** 规划层每次被调用都
必须一次给出全部步骤，否则没有第二次机会。

## 2. 要补的三个东西

### 2.1 目标循环（Plan → Act → Observe → 判断是否达成）

```
round = 1
while round <= max_rounds:
    plan = 规划(目标, 已知信息, 上一轮结果)
    if plan.goal_done:            # ← 由规划层明确声明"够了"
        break
    results = 执行(plan.tool_tasks)
    findings += 摘要(results)
    if 没有新信息:                 # ← 防原地打转
        break
    round += 1
回答 = 汇总(findings)
```

**关键设计：循环由规划层显式驱动，不是自动无限跑。**

规划层每次输出 `goal_done`（布尔）+ `remaining_note`（还差什么）。
默认 `goal_done=true` —— 这样"你好""算 1+1"这类简单请求**行为和现在完全一样**
（永远只跑一轮），不会因为加了循环而变慢或变啰嗦。

只有当规划层说"还没完"时才会进入第二轮。

### 2.2 子智能体

主智能体可以把**互不依赖的子目标**派给子智能体并行做。

```
主智能体
  ├─ spawn: "查 A 的数据"   → 子A（独立上下文） ─┐
  ├─ spawn: "查 B 的数据"   → 子B（独立上下文） ─┼→ 收集结果 → 继续
  └─ spawn: "造一个工具做C" → 子C（独立上下文） ─┘
```

为什么要子智能体，而不是主智能体自己排队做：

1. **并行**：三件互不依赖的事，串行 3×T，并行 ≈ T
2. **上下文隔离**：子任务的过程（试错、日志、失败重来）不该污染主对话上下文
3. **可组合**：一个子智能体失败不影响其他，主智能体可以只重做失败的那个

#### 工具按需加载：技能优先，而非全量

子智能体执行时**先按任务目标匹配技能**，再用技能自带的工具清单
（`Skill.required_tools` / `tools_needed()`）裁剪工具表（`SubAgentPool._skill_scoped_tools`）：

```
任务目标 → match 技能 → 取技能的工具清单 ∩ 角色白名单 → 裁剪后的工具表 → 注入规划上下文
```

- 原来：工具表来自角色白名单（`role.tools.allow`），技能只提供方法论文字，两条线并行。
  结果是上下文塞满全量工具，而且模型容易在全量工具里选错（工具漂移）。
- 现在：命中的技能决定用哪些工具。实测"选品并上架"从 7 个工具裁到 2 个，
  "充值后重新生成视频"裁到 3 个。
- **安全约束**：技能工具与角色白名单取交集，技能不能越权；无匹配技能 / 技能清单为空
  → 退回角色白名单，避免子智能体"无工具可用"而静默什么都不做。
- 提炼侧负责给技能写工具清单（harvest 用真实工具序列、SkillTrainer 让 LLM 抽取）。

### 2.3 状态可探测

主智能体必须能知道子智能体**在干什么、到哪了、成没成**。三类信息：

| 信息 | 用途 |
|---|---|
| 生命周期状态 | `pending / running / done / failed / timeout` |
| 进度 | 当前在第几轮、最近在调什么工具 |
| 结果 | 结构化产出 / 错误原因 |

没有这个，"组织子智能体"等于开了几个黑盒往外丢任务。

## 3. 必须防住的四件事（这是本文最重要的部分）

一个能自我循环、还能复制自己的系统，出错方式比单轮系统严重得多。
下面四条不是"优化"，是**能不能上线的门槛**。

### 3.1 无限循环 / 烧钱

`max_rounds`（默认 6）+ **总时长预算**（默认 180s）。
任一超限立即收尾，用已有信息给出最好的回答，并说明"没做完，因为…"。

### 3.2 原地打转（最容易被忽略）

模型可能连续几轮做**同一件无效的事**（同一个工具、同样的参数、同样的失败）。
所以每轮记录"动作签名"（工具名+参数哈希）：

- 和第 N-1 轮完全相同 → 判定无进展，**立即停止**并说明"这条路走不通"
- 连续两轮没有任何**新**工具结果 → 同上

### 3.3 子智能体递归爆炸

子智能体如果也能生子智能体，一次任务可能炸成几十个进程。

- **深度限制**：`depth` 默认 1（子智能体不能再派）
- **并发上限**：默认 3
- **子智能体工具白名单**：不给 `run_subagents`，避免递归
- **单个超时**：默认 60s，超时标记 `timeout` 并回收

### 3.4 失败被静默吞掉

子智能体失败时，主智能体**必须知道**并如实告诉用户。
不能出现"三个子任务两个失败，但最终回答说得像全成了"。

所以：汇总时强制统计 `done/failed/timeout` 计数，失败数 > 0 时回答必须提及。

## 4. 落地形态

| 文件 | 职责 |
|---|---|
| `core/subagents.py` | 子智能体定义、池、状态机、并发/深度/超时限制 |
| `core/goal_runner.py` | 目标循环：轮次、预算、无进展检测、findings 累积 |
| `tools/subagent_tool.py` | `run_subagents` 工具（主智能体可调） |
| `agents/manager.py` | 规划 schema 增加 `goal_done` / `remaining_note` |
| `core/agent.py` | `handle()` 接入循环；子智能体进度事件 |

### 子智能体怎么实现

复用现有 `Agent` 的执行能力，但**独立的 Context**（不污染主对话）：

```python
SubAgent(goal, tools_subset, depth, timeout_s)
  .run() -> SubAgentResult(status, findings, tool_calls, error)
```

子智能体内部：规划 → 执行（可多轮，但轮次更少，默认 2）→ 返回结构化 findings。
**它不生成面向用户的回答** —— 只产出事实，由主智能体统一组织语言。

### 事件（前端可见）

| 事件 | 含义 |
|---|---|
| `goal_round` | 第 N 轮开始 |
| `goal_continue` | 规划层说还没完，附 remaining_note |
| `goal_stop` | 循环结束（原因：完成/轮次用尽/超时/无进展） |
| `subagent_spawned` | 派了一个子智能体 |
| `subagent_progress` | 子智能体当前在做什么 |
| `subagent_done` | 子智能体完成（含成败） |

## 6. 明确不做

- **不做**无限自主（没有用户在场时自己找活干）—— 那需要另一套审批与预算体系
- **不做**子智能体互相通信（只与主智能体交换结果）—— 拓扑一复杂就没法调试
- **不给**子智能体独立记忆写入权限（记忆只由主智能体写，避免并发污染画像）
