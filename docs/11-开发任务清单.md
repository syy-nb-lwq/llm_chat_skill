## 1. M0：建立可信基线

> 目标：先证明现有系统能稳定执行和观察。

### M0-01 每个 Turn 生成唯一 `execution_id`

- 优先级：高
- 范围：`core/agent.py`、相关记录入口
- 内容：
  - 引入 `user_id / session_id / turn_id / execution_id` 四级标识
  - `Agent.handle()` 入口创建新 `execution_id`
  - 重试时建立 `parent_execution_id`
  - 修复失败 JSON 互相覆盖问题
- 来源：`10 §4.6 §6.1`
- 验收：同 Session 多 Turn 失败记录不再互相覆盖
- 完成：2026-07-22（`core/agent.py` 入口创建 `IdentityContext`，`execution_id` 经
  `ExecutionContext` 传到 `MemoryStore.record_failure` 落盘；`trace_id` 与其同值）

### M0-02 补齐执行记录字段

- 优先级：高
- 范围：`core/critic.py`、`core/agent.py`
- 内容：

- 来源：`10 §4.5`、`02 §6`、`09 §8`

  `TaskExecutionSummary` 增加 `fallback_to` / `latency_ms`；

## 2. M1：打通技能教学和复用闭环

> 目标：可靠完成一个纯方法论技能（日报生成样板）。
>
> **意图识别的改造方案见 [12-意图分层识别方案.md](./12-意图分层识别方案.md)**。
> 现状是三组高噪声关键词表（技能管理 / 教导 / 工具）各自决定路由，已实测存在
> "查看北京天气 → 技能管理"、"遇到雨天要带伞 → 教导" 这类误判，
> 方案给出四层架构与 P0~P3 落地节奏。

### M1-01 持久化 TeachingSession 状态机

- 优先级：高
- 范围：`agents/skill_trainer.py`、`backend/`、存储层

  - 保存：当前技能名、已收集/缺失字段、待回答问题、用户选择、草稿证据
- 来源：`10 §4.2 §7.1`
- 验收：三轮教学不丢上下文；重启可恢复

### M1-02 允许无工具技能执行

## 3. M2：打通长期记忆

> 目标：让偏好、事实和上下文跨 Session 可恢复。
>
> **详细方案见 [13-记忆分层与RAG方案.md](./13-记忆分层与RAG方案.md)**（五层记忆模型、
> 统一 MemoryItem、写入管线、RRF 召回管线、P0~P5 分阶段）。下表的 M2-01~M2-09 与该方案对应，
> 其中 M2-03 / M2-06 的验收原文直接引用了方案里的断点编号。

### M2-01 统一 MemoryRepository

- 优先级：高
- 范围：`core/memory.py`、`infra/`
- 内容：
  - 业务代码不直接读写 JSON/JSONL/SQLite/YAML
  - 统一 Repository 接口
- 来源：`10 §5.4 §6.2 §8`
- 验收：替换存储不影响上层

### M2-02 MemoryItem 数据模型

- 优先级：高
- 范围：`core/` 新模块
- 内容：
  - 字段：`tenant_id / user_id / scope / type / source_turn_id / confidence / valid_until / supersedes_id / status`
- 来源：`10 §6.2`
- 验收：跨 Session 记忆可追溯

### M2-03 主链路写入

- 优先级：高
- 范围：`core/agent.py`、`agents/`
- 内容：
  - `handle()` 完成时提取候选记忆
  - 敏感检查
  - 去重与冲突检测
  - 写入记忆库
- 来源：`10 §4.3 §8.2`

- 来源：`10 §4.3 §10 M2`
- 验收：embedding 失败不阻塞主流程

### M2-05 修复异步检索 bug

- 优先级：高
- 范围：`agents/manager.py:374`
- 内容：
  - `run_until_complete()` 改为真正异步调用
- 来源：`10 §4.3`、`02 §2`
- 验收：异步召回不再被静默忽略

### M2-06 作用域过滤召回

- 优先级：高
- 范围：`core/semantic_memory.py`、`agents/`
- 内容：
  - 召回必须带 `tenant_id + user_id`
  - 项目记忆带 `project_id`
  - 排序：相关性 / 时效 / 置信度 / 重要度
  - 限制注入 token
- 来源：`10 §8.3`
- 验收：跨用户隔离生效
- 现状核查（2026-07-22）：`SemanticMemoryStore.search()` 的 `user_id` 是**可选参数**，
  且 `agents/manager.py:462` 调用时**根本没传** → 跨用户召回实际处于泄漏状态。
  方案要求把 `tenant_id` / `user_id` 改为**必填**，宁可编译期报错也不静默泄漏。

### M2-07 Session 摘要替代无限滚动

### MCP 接线的三个关键决定

1. **命令解析不能默认用 python**。
   原实现:`sys.executable if not server_path.endswith(".exe") else server_path`
   → `npx -y xxx` 变成 `python npx -y xxx`,一定失败。
   MCP 服务器绝大多数是 `npx`/`uvx` 起的,不是 .py。

2. **一个服务器坏了不影响其它**,也不影响启动。

3. **它是第三方进程**(用 npx/uvx 拉)→等于引入第三方代码执行面,
   **只应由管理员配置**,不让终端用户自助添加。

### 代码执行的安全模型

| 层 | 挡住什么 | 局限 |
|---|---|---|
| 独立子进程 | 崩溃不影响主进程;可设超时、能杀进程组 | **不是安全边界** |
| `-I`(隔离模式) | 忽略 `PYTHONPATH` / 用户 site-packages | 不挡文件访问 |
| 独立 cwd(临时目录) | 写文件不污染仓库 | cwd 逃逸(`..`)仍可达 |
| env 白名单 | **子进程拿不到 API key / token** | 挡不住网络访问 |
| 超时 + 输出截断 | 无限循环/刷屏不会拖死服务 | — |
| 静态黑名单(AST) | 明显危险的 import / 动态执行提前拦 | 启发式,不是保证 |

**明确的局限**:子进程隔离 = 崩溃隔离,不是安全边界。
多租户产品对外开放前必须关掉 `CODE_EXEC_ENABLED` 或换成容器隔离。

### 实机验证(2026-11-16,deepseek-flash)

```
Q: 用一段 python 脚本算一下 1 到 100 的总和
   → L1=task → L2 选中 [write_script, python_exec] → 真实执行
   → 最终回答:「结果:5050」+脚本做了什么

Q: 帮我算一下 128 乘 37 等于多少
   → L2 生成 {"type":"python_exec","params":{"code":"print(128 * 37)"}}
```

**实机验证发现的 4 个真 bug**(全是"从来没连过真服务器"掩盖的):

| Bug | 表现 | 根因 |
|---|---|---|
| `initialize` 响应**读了两次** | 连接一直挂着(无限等待) | `_send_request` 内部已读,又调了一次 `_read_response()` |
| **不抽干 stderr** | 服务器写 stderr 到满 → 阻塞 → 不读 stdin → 死锁 | stderr 是管道,满了就阻塞 |
| **读取无超时** | 一个不回话的服务器能让**整个 agent 启动卡死** | `_read_response` 是裸的 `readline()` |
| `disconnect()` 对 `StreamReader` 调 `close()` | 每次断开 MCP 都抛 `AttributeError` | `close()` 是 `StreamWriter` 的方法 |

另有两个不会报错但会提前抛错的:
- `get_tool_schema` 把**原始 dict** 当 MCPTool 处理 → `AttributeError`
- `create_mcp_source()` 返回实例、`parse_mcp_servers()` 返回规格 —— 两种不一致的约定

**实机结果**(npx 拉 @modelcontextprotocol/server-filesystem):
`connect → True`、14 个工具、`write_file → True`、`read_text_file` 读回 `hello from MCP` ✓

新增测试:`tests/test_code_exec.py`(34)、`tests/test_mcp_source.py`(26)。

## 新增:文档处理(已实施,P0)

> 原计划在 M4 章节。本轮把「能读文档」做了。

### 两个工具

| 工具 | 作用 |
|---|---|
| `read_document` | 读文档 → 带锚点的 markdown |
| `locate_document` | 把锚点还原成原文位置(页码/表名/单元格) |

### 为什么不直接用 markitdown

markitdown 很好,但它输出**扁平 markdown**,丢了位置信息(第几页、哪个 sheet、哪个单元格)。
而位置正是锚点的原料。所以 docx/xlsx/pptx/pdf 走本项目自己的解析器,
其他格式(html/epub/…) 才退回 markitdown。依赖也是**可选**的。

### 锚点机制(这层的核心价值)

```
[B1 p.1] Quarterly Report
[B2 数据|A1:C3] | 城市 | 年度 | 价格 |
```

LLM 引用时可以直接写「见 [B2 数据|A1:C3]」,用户能核对原文。
没有它,用户问「原文怎么说的」时 LLM 只能转述或猜。

### 扫描件必须明确报错

实测发现仓库里的一份中文公文 PDF 是**扫描件**(整页图片,0 个字符)——
pdfplumber 对这类文件返回**空字符。**

如果照常返回空字符字符串,LLM 会回答「文档中未提及相关内容」——
**那是幻觉,而且看起来完全正常。**

所以本模块会检测并明确报错:
「这份 PDF 是**扫描件**(共 8 页,全部没有文本层),无法直接提取文字,需要先做 OCR」。

**本项目不做 OCR**。

### 实机验证(2026-11-17,deepseek-flash)

```
Q: 读一下 D:/tmp/fixture.docx,告诉我里面「开发环境」那句话怎么写的,原文引用一下
→ 读文档 → 原文引用:「开发环境:Windows。生产环境:Linux。」
→ 并标出:块 ID B4 / 段落 ¶3 / 标题路径「项目与方案 > 环境说明」
```

### 实现中修的个真 bug

| Bug | 表现 |
|---|---|
| `.docx` 扩展名不可信 | 伪 docx 被当成真的解析 → 乱码 |
| `md` 不在文本格式分派里 | 落进 markitdown 兜底 → 标题头丢了 |
| 范围解析不接受单个数字 | `blocks="10"` 直接报错 |
| 未知格式会读二进制 | `.exe` 被读成乱码 → LLM 拿着乱码编答案 |

新增测试:`tests/test_document_tool.py`(23)。固件用**真实文件格式**(docx/xlsx/pdf),不用 mock。

### 跨组缺陷（实机验证中发现）

- **前端没回 RPC ACK** — `fastapi-websocket-rpc` 是请求/响应式协议，服务端 `publish()`
  会等客户端回 ACK 才返回，库里 `default_response_timeout` 默认 `None`（永不超时）。
  前端 `websocket.js` 收到 `notify` 只处理不回响应 → 服务端那一轮事件投递被永久卡死
  （表现为"转圈不动"）。
  - 修法一（协议正确性）：`frontend/src/websocket.js` 新增 `_ackNotify(callId)`，
    收到 `notify` 即回 `{"response": {result, result_type, call_id}}`
  - 修法二（服务端兜底）：`backend/websocket_handler.py::push_event` 用
    `asyncio.wait_for(..., PUSH_TIMEOUT=10s)`，客户端不按协议来也不把这一轮卡死
  - 验收：`tests/test_backend.py::test_push_event_times_out_instead_of_hanging`
    + 实机验证（回 ACK 时事件即时送达；不回 ACK 时事件仍全部送达、不再挂死）

### A-06 用户纠正信号（已落地，2026-07-22）

**目标**：让"回答不对"这个唯一的 ground truth 进得去，critic 不再只知道"工具调没调通"。

| 环节 | 实现 |
|---|---|
| 隐式信号 | `core/correction.py::CorrectionDetector`（纯规则，4 类纠正语；必须有上一条非空回答） |
| 显式信号 | 前端 👍/👎 → WS topic `feedback/<conn_id>` → `Agent.apply_explicit_feedback()` |
| 重评 | 保留上一轮执行上下文，纠正时用同一 `execution_id` 重评，并**撤销上一轮的成功记录** |
| critic | 被纠正的轮次记成**失败**、不记成功，并生成 `fix_method` 补丁 |
| 指标 | 答案采纳率 `adoption_rate = 1 − 被纠正轮数/评估轮数`，暴露在 `GET /api/memory/stats` |

**设计取舍**：纠正检测**不用 LLM**。漏判只是少学一次；误判会污染记忆库
（把"那再帮我看看明天呢"当错答去学）。宁可漏判。

### A-07 技能可验证化（已落地，2026-07-22）

**目标**：让"这个技能到底靠不靠谱"有答案，并自动淘汰差的。

| 环节 | 实现 |
|---|---|
| 质量账本 | `core/skill_quality.py`，追加写 JSONL（`memory/skills/quality.jsonl`） |
| 验收样例信号 | 发布/升级时跑 `ResultValidator` → 记进账本 |
| 线上使用信号 | 技能被真实使用后，用户有没有纠正这一轮（接 A-06 的纠正链路） |
| 同轮只算一次 | `usage` 记录带 `execution_id`，后写的覆盖先写的 |
| 自动降级 | 最近 2 次样例通过率 <60%，或用过 ≥5 次采纳率 <50% → 不再被 planner 选中 |
| 可观测 | `GET /api/skills/quality`；前端技能面板显示「通过率 xx%」/「已降级」徽章 |

**设计取舍**：降级是**推导**出来的（数据变好自动恢复），不是贴上去的标签；
判据看最近几次而不是历史聚合。账本挂了的时候**不降级任何技能**。

### A-08 真 LLM 基线（部分落地，2026-07-22）

- `tests/mock_openai.py`：本地 OpenAI 兼容 mock（支持 SSE / 非流式）
- `tests/test_live_channel_plumbing.py`：把 `--live` 通道整条跑通（不需要 key）
  —— 验证的是**管线通不通**，不是模型准不准
- `scripts/profile_eval.py` + `tests/data/profile_eval.jsonl`：画像抽取基线
  （纯规则，现在就能建）→ 精确率 **86.7% → 100%**，CI 闸门 ≥95%
- `scripts/intent_eval_nightly.py`：一条命令跑两个基线

**真机基线（DeepSeek `deepseek-flash`，2026-11-16）**：

| 通道 | 指标 | 数值 |
|---|---|---|
| L0 规则 | 定案 / 准确率 | 19/38，100% |
| L1 开发集（23 条） | 准确率 | **100%** |
| L1 留出集+封存集（95 条） | 准确率 | **94.7%** |
| 画像抽取（规则） | 精确率 / 召回率 | 100% / 100% |

**基线是分布不是单数**：`--repeat 3` 报 min/mean/max，用最差一遍做闸门。

**建基线当场抓到的 4 个真缺陷**：

1. **L0 抢在 L1 前面误判**（最严重）——L0 有裸关键词分支，只要出现「教我」
   就判 teach 并 short-circuit，用户请助手讲解被塞进技能学习流程。
   **代价**：我先按"模型判错"改了 5 版提示词，一点没动 —— 因为根本没走到 LLM。
2. 「以后…用…」被判成 teach（约定信号正则把「用」「走」当触发词）
3. 易混对指标**结构性永远为 0**（分母用 (predicted,expected) 二元组，
   而二元组里两个标签必然不等 → "判对"永远进不了分母）
4. 网络抖一下基线显示"准确率 20%" → 现在**通道不可用就判定本次基线无效**，不出数字

**留出集防自欺**：`intent_eval_holdout{,2,3,4,5}.jsonl` 每批都在改完提示词之后才写，
另有 `intent_eval_sealed.jsonl` 只跑一次。留出集上的错里有 2 条是**我标注标错**的。

### 后续重构：意图规则全部删除（2026-11-16）

用**只有 LLM** 的方案重新量了一遍（130 条标注）：

| 做法 | 准确率 |
|---|---|
| 规则 + LLM | 94.7% |
| **只有 LLM** | **97.7%** |

结论：规则**不是没帮上忙，是在拖低准确率**。已落地：

- `core/intent_detector.py` 从 595 行规则砍到只剩**结构守卫**（判空输入，其余度交 L1）
- `agents/manager.py` 删掉 `should_learn_skill()` / `should_answer_directly()`（死代码 + 规则判意图）
- `tests/test_intent_architecture.py` 新增架构契约测试：**规则不得回到意图判定里**
- 删除 `tests/test_intent_precision_p0.py` / `test_intent_detector.py` / `test_intent_dataset.py`
  （他们断言的是已删除的字面行为；21 条用例已被 133 条 jsonl 评估集覆盖）

**新基线**：L1 开发集 38 条 **100%**，留出集+ 封存集（95 条）**96.3%**。

**代价**：LLM 调用量 50% → ~100%（原来免费吃掉的 19 条要去问模型）。

**待做**：答案质量与澄清质量仍无基线（需要人工标注问答对）；基线是单模型的，换模型要重跑。
