## 0 先承认一件事：前三篇只做到了"描述动态"

`23 §7.1` 里我写的"动态"，实质是：

> 类型变了 → `kb_query` 的 description 跟着变

这叫**描述动态**。它解决的是"模型知道有哪些类型"。

它没解决的是"模型知道有哪些类型之后，**能对它做什么**"。

举个具体的：本体里长出一个 `promotion`（促销活动）类型。在只有描述动态的版本里，
`kb_query` 的描述会多一行"可用类型含 promotion"，agent 能**查**促销活动。
但以下三件事，一件都做不到：

- **检测**：这批促销活动有没有 `end_at < start_at` 的（时间倒挂）
- **动作**：给过期的促销活动打 `expired` 标
- **触发**：发现价格倒挂时通知运营

要做到这三件事，光有描述不够，必须有**能力**。而能力要么人写代码，
要么由本体派生。本文写的是后者。

一句话判据，可以用来自查有没有真正做到：

> **新类型出现后，如果还需要人写代码才能对它做点什么，那就没做到挂接。**

## 1 动态本体的完整意义：五层递进

"动态本体"这四个字被用得极滥，绝大多数场合指的是第 1 层。完整形态是五层，
每层都可以独立成立，但只有到第 4 层才配得上"自主挂接"。

```
┌─ L1 术语层 ─────────────────────────────────────────────┐
│  统一词表：同一个东西在不同系统里叫不同名字，本体负责归一    │
│  "碎花裙" / "dress" / "SKU-001" → 同一个实体                │
│  实现：onto_entity.alias_json + resolve()                   │
├─ L2 描述层 ─────────────────────────────────────────────┤
│  工具描述由本体生成：类型清单、属性清单、可用关系            │
│  实现：kb_query 的 description 在注册时按 onto_type 拼接     │
├─ L3 约束层 ─────────────────────────────────────────────┤
│  schema 与校验规则同源：类型定义的 required/enum/range        │
│  同时是"这个值对不对"的判据，不需要另写一份校验规则          │
│  实现：detect 的隐式规则直接从 schema_json 展开              │
├─ L4 能力层 ─────────────────────────────────────────────┤
│  类型出现 → 可用动词自动对它生效 → 衍生工具自动注册           │
│  实现：derive_capabilities() + register_ontology_capabilities │
├─ L5 动作层 ─────────────────────────────────────────────┐
│  能力被触发 → 真正改变外部世界（打标/通知/入队/回写）        │
│  实现：受限动词 + outbox + 事件源                            │
└─────────────────────────────────────────────────────────┘
```

**为什么必须分开看这五层**：因为它们的实现代价差两个数量级，而收益不是。

- L1、L2 几乎零成本：读表拼字符串。
- L3 是**动态本体最实在的收益**，但也是最容易被忽略的。静态本体下，
  schema 和校验规则是两套东西，要手工同步，一定会漂移。
- L4 是本文主体，成本中等（一张能力表 + 一个派生函数）。
- L5 是**另一个子系统**，成本和前四层不是一个量级（要事件源、要幂等投递、
  要失败重试）。本文只定接口，不实现。

**这五层不能跳级**。L4 的 `detect` 依赖 L3 的隐式规则；L5 的 `notify`
依赖 L4 的 `detect` 产出。跳过 L3 直接做 L4，`detect` 就是个空壳 ——
它能"运行"，但没有规则可跑。

## 2 为什么不能"一个类型一个工具"

最直觉的做法是：本体里有什么类型，就给每个类型生成 `query_xxx` / `detect_xxx`。

必须否掉，理由是算术：

```
50 个类型 × 4 个动词 = 200 个工具
每个工具的 schema 描述 ≈ 120 token
200 × 120 = 24,000 token —— 仅仅为了"让模型知道工具存在"
```

而 `agents/manager.py:151` 每次规划都要把**全部工具名**塞进 prompt，
`core/subagents.py::_skill_scoped_tools` 的存在本身就是为了解决工具太多导致的
"工具漂移"（模型在全量工具里选错）。这是你已经在解决的问题，不能反过来制造。

**结论：类型不产生新工具，只产生参数约束。**

元工具常驻，数量固定；类型影响的是元工具的 `enum` 和描述。

这带来一个必须验证的技术前提：元工具的 `type` 参数要用 `enum` 约束，
否则模型会编造类型名。**这个前提已经成立** —— `tools/validation.py:302-307`
已经在做 enum 校验：

```python
# tools/validation.py:302
# 3) enum 只在类型正确后校验
if not param.enum or name not in out:
    return
if out[name] not in param.enum:
    errors.append(f"参数 {name} 取值非法：{out[name]!r}（可选：{param.enum}）")
```

而且错误信息会**把可选值列出来**，模型拿到报错能自我纠正。这比自己校验 enum
再返回一个模糊错误好得多。

### 2.1 唯一的例外：高频类型可以升级

元工具方案的弱点是"模型要记得住哪个类型有哪些属性"。类型少时没问题，
类型多了描述会膨胀。

解决办法是**不按类型数量分，按使用频次分**：

| 使用频次 | 形态 | 理由 |
|---|---|---|
| 前 12 个类型（按近 30 天查询命中数） | 升级成独立工具 `kb_detect_product_sku` | 高频工具值得占用描述预算 |
| 其余类型 | 只能通过元工具 + `type` 参数访问 | 低频不值得占 |

阈值 12 来自 `core/capabilities.py` 的预算实践：`CAPABILITY_BLOCK_MAX_CHARS = 900`，
再往上就会把有用信息挤出 prompt。12 个衍生工具 × 120 token ≈ 1440，勉强可接受。

**升级必须是自动的、可逆的**：频次掉出前 12，工具要撤回。手动管理升级清单，
半年后一定会和实际使用分布脱节。

## 3 能力的三元组：名词 / 动词 / 变格

你说的"能构建行为动作、函数，实现自主挂接"，落到可实现的形态是三元组。
这三个概念必须分清，否则会滑向"让 LLM 写函数"。

| 元素 | 是什么 | 存储在哪 | 谁定义 |
|---|---|---|---|
| **名词** | 类型（`product_sku`、`category`） | `onto_type` | 种子 / 映射反推 / 数据诱导 |
| **动词** | 固定 7 个（`query`/`detect`/…） | **代码**，不落库 | 人，一次性 |
| **变格** | 某类型对某动词的可用性与参数约束 | `onto_capability` | 自动派生 + 人工覆盖 |

"自主挂接"= **变格自动生成，名词自动进入变格表**。

动词永远不自动生成。这是红线，下一节详说。

### 3.1 红线：不许 LLM 生成函数并挂接

有一个看起来很诱人的设计：

> 本体里出现新类型 → 让 LLM 根据类型定义写一个检测函数 → 注册成工具

必须否掉，三条理由：

1. **这是任意代码执行入口**。`tools/python_exec.py` 顶部的安全模型就是为拦这个建的 ——
   AST 黑名单、模块白名单、`subprocess` 禁用。如果本体能自动生成函数并挂载，
   那条防线等于被绕过：攻击面从"用户让 agent 跑代码"变成"数据里出现一个恶意类型"。
2. **生成物无法审计**。本体是数据，数据会被 CSV 导入、被映射规则写入。
   一个由数据触发的代码生成链路，等于让数据决定执行什么。
3. **它解决不了真正的问题**。你以为需要"每个类型一个函数"，实际需要的是
   "每个类型一套参数约束" —— 后者用 `enum` + schema 就能表达，不需要代码。

所以正确的形态是 **动词表固定、参数由本体给**：

```
kb_detect(type="promotion", scope={...}, rules=["time_order"])
          ↑ 固定                ↑ enum 来自 onto_type
                                     ↑ enum 来自 onto_rule
```

新类型出现，这行立刻能用，因为它只依赖 `onto_type` 里有这一行。

## 4 能力描述的数据结构

### 4.1 核心判断：只存"偏离默认"的部分

能力能不能不建表？不能。但也不能全量落库。

- **全量落库**：50 类型 × 7 动词 = 350 行。每次新增类型要插 7 行，
  每次新增动词要回填所有类型。两张表要手工保持同步，必然漂移。
- **完全不落库**：那"这个类型禁用 detect"、"这个类型的 query 只允许查近 90 天"
  这类人工约束无处可放。

折中：**默认由规则推导，表里只存例外**。

```
默认规则（代码里写死）：
  entity 类型  → query ✓  detect ✓  trace ✓  resolve ✓  assert ✓  tag ✓  notify ✗
  relation 类型 → query ✓  detect ✓  trace ✓  resolve ✗  assert ✓  tag ✗  notify ✗

onto_capability 只存与默认不同的行。
```

`notify` 默认关闭 —— 副作用动作必须显式开启，不能因为建了个类型就自动获得发消息的能力。
这是安全默认值。

### 4.2 表结构

```sql
-- 能力例外表：只存与默认规则不同的 (type_id, verb)
CREATE TABLE IF NOT EXISTS onto_capability (
  type_id          TEXT NOT NULL,
  verb             TEXT NOT NULL,
  enabled          INTEGER NOT NULL DEFAULT 1,
  -- 覆盖默认约束，例如 {"max_hops": 2, "as_of_window_days": 90}
  -- 合并语义：浅合并进默认值，不是替换
  constraints_json TEXT NOT NULL DEFAULT '{}',
  origin           TEXT NOT NULL,   -- manual | seed | derived
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL,
  PRIMARY KEY (type_id, verb)
);

-- 检测规则：显式规则存这里，隐式规则不存（从 schema_json 展开）
CREATE TABLE IF NOT EXISTS onto_rule (
  id          TEXT PRIMARY KEY,
  type_id     TEXT NOT NULL,
  name        TEXT NOT NULL,
  kind        TEXT NOT NULL,     -- schema | explicit
  severity    TEXT NOT NULL,     -- info | warn | error
  spec_json   TEXT NOT NULL,
  enabled     INTEGER NOT NULL DEFAULT 1,
  version     INTEGER NOT NULL DEFAULT 1,
  origin      TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_rule_type ON onto_rule(type_id, enabled);

-- 检测结果：只追加不覆盖，才回答得了"这条告警是什么时候出现的"
CREATE TABLE IF NOT EXISTS onto_finding (
  id            TEXT PRIMARY KEY,
  rule_id       TEXT NOT NULL,
  entity_id     TEXT,
  severity      TEXT NOT NULL,
  detail_json   TEXT NOT NULL DEFAULT '{}',
  status        TEXT NOT NULL DEFAULT 'open',   -- open | resolved | ignored
  run_id        TEXT NOT NULL,
  first_seen_at TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_finding_open ON onto_finding(status, severity);
CREATE INDEX IF NOT EXISTS idx_finding_ent  ON onto_finding(entity_id, rule_id);

-- 内容变更信号：能力失效重算的触发器（见 §7.3）
CREATE TABLE IF NOT EXISTS onto_change (
  id     INTEGER PRIMARY KEY AUTOINCREMENT,
  kind   TEXT NOT NULL,    -- type | rule | entity | assertion
  ref    TEXT NOT NULL,
  action TEXT NOT NULL,    -- insert | update | status | delete
  at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_change_at ON onto_change(at);
```

三处设计要点：

**`onto_finding` 为什么只追加不 UPDATE 字段值**。告警的价值有一半在时间维度上：
"这个属性缺失是三天前开始的，还是存在两年了"。如果每次检测覆盖 `last_seen_at`，
历史就没了。正确做法是 `(rule_id, entity_id)` 唯一打开一条，
后续检测只更新 `last_seen_at`，状态从 `open` 变成 `resolved` 时插入一条关闭记录。

**`onto_rule.kind='schema'` 的行是缓存的，不是真相**。隐式规则由 `schema_json` 展开，
存到 `onto_rule` 只是为了跑批时不用重复展开。**schema 一变，这些行必须失效重算**，
所以它们带 `origin='derived'`，重算时整批删掉重建。

**`onto_change` 是给能力重算用的，不是审计日志**。它只需要回答
"上次重算之后有没有变过"，所以可以定期截断（保留最近一次重算时间点之后的）。
不要把它做成 append-only 的审计表 —— 那会无限增长，最后变成性能问题。

### 4.3 派生算法

`derive_capabilities(conn)` 是唯一的能力来源。所有读能力的路径都走它，
不允许别处再写一套判断。

```python
# kb/service/capability.py

VERB_DEFAULTS: Dict[str, Dict[str, bool]] = {
    KIND_ENTITY:   {"query": True,  "detect": True,  "trace": True,
                    "resolve": True, "assert": True, "tag": True,  "notify": False},
    KIND_RELATION: {"query": True,  "detect": True,  "trace": True,
                    "resolve": False, "assert": True, "tag": False, "notify": False},
}

def derive_capabilities(
    conn,
    *,
    type_status: Sequence[str] = QUERYABLE_TYPE_STATUSES,
) -> List[Capability]:
    """展开 (类型 × 动词) → 能力清单。

    规则：
      1. 只看 status ∈ QUERYABLE_TYPE_STATUSES 的类型（draft 不产生能力）
      2. 默认值来自 VERB_DEFAULTS[kind]
      3. onto_capability 里有行 → enabled 覆盖默认，constraints 浅合并
      4. deprecated 类型的 notify/tag 强制关闭（不能对废弃类型做写入）
    """
```

四条规则里第 1 条和本文的核心判据一致：**`draft` 类型不产生任何能力**。
这和 `22 §3.2` 的"draft 不许跳 active"是同一个闸门 —— 没经过观察期的类型，
不该被 agent 用上。区别只是闸门的位置：一个在写入侧，一个在读取侧。

第 4 条容易被忽略：`deprecated` 类型允许 query（历史数据要能查），
但**不允许写**。如果允许 tag，会出现"往废弃类型上打标"这种不可解释的状态。

## 5 七个受限动词

### 5.1 总表

| 动词 | 语义 | 读/写 | 幂等性 | 失败语义 |
|---|---|---|---|---|
| `query` | 按图模式查 | 读 | 天然幂等 | 返回空 + **说明为什么空** |
| `detect` | 跑规则出告警 | 读 + 写 finding | 按 `(rule, entity, run)` 幂等 | 部分规则失败不阻断其余 |
| `trace` | 反查血缘 | 读 | 天然幂等 | 指到断点，不返回"未知" |
| `resolve` | 术语归一 | 读 | 天然幂等 | 返回候选列表，**不猜** |
| `assert` | 写断言 | 写 | 按 `(s,p,o,source)` 幂等 | **拒绝整批**，不跳过坏行 |
| `tag` | 打标 / 改状态 | 写 | 按 `(entity, tag)` 幂等 | 拒绝 |
| `notify` | 触发外部动作 | 副作用 | 需去重键 | 写 outbox，**不可直接执行** |

表里每一列都是踩过坑的结论，下面逐个说。

### 5.2 query

签名已经在 `kb/service/query.py` 实现，这里补充能力层要加的两样东西。

**① 空结果必须带解释**。这是查询工具最常见的失败模式：

```
模型：kb_query(type="promotion", where={"status": {"eq": "active"}})
返回：[]
模型推断：没有促销活动
实际原因：promotion 类型还在 draft，不在 QUERYABLE_TYPE_STATUSES 里
```

模型不会怀疑工具，它会用"没有数据"当事实继续推理。所以空结果要分三种，
分别给出不同的提示：

| 情况 | `status` 字段 | 提示 |
|---|---|---|
| 类型不在可查范围 | `type_not_queryable` | "promotion 当前状态为 draft，尚未开放查询" |
| 类型可查但无实体 | `no_entity` | "promotion 类型下还没有实体，可能尚未导入数据" |
| 有实体但条件不匹配 | `no_match` | "有 32 个 promotion 实体，但没有满足条件的" |

第三种最重要 —— 它告诉模型"你的条件写严了"，模型会自己放宽重试。
返回一个裸 `[]` 则什么都不会发生。

**② `direction` 必须支持 `in`**。`23 §6.1` 记过这个缺口：现在的 DSL 只能
从 subject 走到 object，查不了"哪些 SPU 属于这个品类"。而自然语言问题里
反向问法至少占一半（"这个品类下有哪些商品"）。这条在 P2 之前必须补上。

### 5.3 detect

这是"及时检测商品"的落点，也是本文最需要写细的部分。

```
kb_detect(
    type: str,              # enum 来自 onto_type
    scope: dict | None,     # 同 query 的 where
    rules: list[str] | None,  # 规则名或 id；None = 全部启用的规则
    limit: int = 500,
) -> {
    "run_id": str,
    "checked": int,
    "findings": [{"entity_id", "entity_name", "rule", "severity", "detail"}],
    "skipped_rules": [{"rule", "reason"}],   # 关键
}
```

**`skipped_rules` 是刻意设计的**。规则可能因为类型不匹配、引用了不存在的属性、
超时而被跳过。如果静默跳过，用户会以为"检测过了，没问题"。这和
`21 §6.1` 里"契约校验失败拒绝整批而不是跳过坏行"是同一条原则：
**静默丢弃是最难查的故障**。

**分页与超时**。检测是逐实体跑的，`limit` 默认 500 而不是"全部"。
理由：一个类型可能有 10 万实体，全量检测会超时，超时后前端只看到"失败"，
用户不知道跑完了多少。正确做法是分批 + 返回 `next_cursor`，
让调用方能续跑。**宁可返回"这次只检了 500 个"，也不要返回一个可能超时的全量结果。**

**finding 的幂等**。同一实体同一规则重复检测，不应该产生两条告警：

```sql
-- 已有 open 的同样告警 → 只更新 last_seen_at
UPDATE onto_finding SET last_seen_at = :now
WHERE rule_id = :rule AND entity_id = :ent AND status = 'open';

-- 没有 → 插入
INSERT INTO onto_finding (...) VALUES (...);
```

用 `(rule_id, entity_id, status='open')` 做唯一性判断。**不能靠 `run_id` 去重**，
因为每次检测 run_id 都不同，那等于完全没有去重。

### 5.4 trace

反查血缘：给定一条断言，回答"它从哪来"。

```
kb_trace(assertion_id) -> {
    "chain": [
        {"level": "assertion", "id": ..., "predicate": ..., "confidence": 0.9},
        {"level": "mapping",   "id": ..., "transform": "trim"},
        {"level": "raw",       "id": ..., "source": "csv:products", "row_no": 8821},
        {"level": "source",    "name": "商品中心导出", "fetched_at": ...},
    ]
}
```

**失败时不能返回"未知"**。血缘断链有三种原因，必须区分：

- `missing_source_ref`：这条断言是早期数据，`source_ref` 字段为空（迁移前）
- `dangling_ref`：`source_ref` 指向的 raw 记录已被归档清理
- `inferred`：这条断言是推理产物，`source_ref` 以 `rule:` 开头，本来就没有源数据

第三种最容易被误判为"断链"。推理产物的血缘指向**规则**而非**数据**，
要单独标注 `{"level": "rule", "rule_id": ..., "inputs": [...]}`。

这也是 `23` 里定的 `source_ref` 七种前缀的用途所在 —— 前缀决定血缘往上走哪条路。

### 5.5 resolve

术语归一。`kb/onto/entities.py::search` 已实现（FTS + 子串双通道），
能力层要补的是**返回候选而非最佳答案**。

```
kb_resolve(text="碎花裙", type=None) -> {
    "candidates": [
        {"entity_id", "name", "type", "score", "matched_by": "alias"},
        ...
    ],
    "ambiguous": true,     # 多个候选分数接近
    "suggestion": "可能指 碎花连衣裙(SKU-001) 或 高腰A字裙(SKU-003)"
}
```

**为什么不能让 resolve 直接返回"最可能的那个"**：中文商品名歧义极多，
"碎花裙"可能是连衣裙也可能是半身裙。猜错一次的代价是模型基于错误实体
继续推理，比"不知道"危险得多。这和 `_aggregate` 那个假 sum 是同一类问题 ——
**宁可暴露不确定，也不要给一个看似确定的错答案**。

### 5.6 assert / tag

两个写动词。闸门在 `23 §7.4` 已经定过（写操作要带 `source_ref`、结构化源可自动晋升、
LLM 抽取必须 support≥3），这里只补充能力层的一条：

**`assert` 和 `tag` 默认不开放给子智能体**。`core/subagents.py` 有角色白名单，
本体能力注册时应该和它配合：能力注册到 hub 是"全局可见"，
但子智能体的工具裁剪会按角色白名单过滤。所以调用方要在角色配置里显式给出
`kb_assert`，否则子智能体拿不到。

这个分层很重要：**注册 ≠ 授权**。`visibility="global"` 只表示"在工具表里"，
能不能用由角色白名单和技能 `required_tools` 决定。

### 5.7 notify：唯一有副作用的动词

`notify` 是"行为动作"的落点，也是最容易出事的一个。核心设计：
**不直接执行，写 outbox**。

```sql
CREATE TABLE IF NOT EXISTS onto_outbox (
  id          TEXT PRIMARY KEY,
  topic       TEXT NOT NULL,       -- 例如 "promotion.price_inverted"
  payload_json TEXT NOT NULL,
  dedup_key   TEXT NOT NULL,       -- 调用方给，用于抑制重复通知
  status      TEXT NOT NULL DEFAULT 'pending',  -- pending | sent | failed | dead
  attempts    INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT NOT NULL,
  next_try_at TEXT,
  last_error  TEXT
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_outbox_dedup
  ON onto_outbox(dedup_key) WHERE status != 'dead';
```

三条理由：

1. **副作用不能回滚**。`assert` 写错了可以再写一条抵消，消息发出去收不回来。
   所以副作用必须先落库、再投递，落库那一刻是唯一可靠的回滚点。
2. **投递会失败**。API 超时、下游重启、限流，都是常态。直接在工具调用里同步投递，
   等于让 agent 的一次对话承担下游可用性。
3. **需要去重**。同一批检测跑两次，不能给运营发两遍消息。`dedup_key`
   由调用方给（通常是 `(rule_id, entity_id, 日期)`），DB 唯一索引兜底。

`notify` 默认对所有类型关闭（`VERB_DEFAULTS` 里都是 `False`），
必须显式在 `onto_capability` 里打开。这是**唯一一个默认关闭的动词**，
因为它有外部后果。

## 6 检测规则 DSL

### 6.1 两类规则，只有一类是免费的

| 类别 | 来源 | 例子 | 维护成本 |
|---|---|---|---|
| **隐式**（schema 派生） | `onto_type.schema_json` | 必填缺失、类型不符、枚举越界、数值越界 | **零**，schema 变它就变 |
| **显式**（人工/规则库） | `onto_rule.spec_json` | 价格突变 >30%、标题含违禁词、类目错放 | 要人定义 |

隐式规则是动态本体相对静态本体最实在的收益。静态本体下，
"字段定义"和"校验规则"是两套东西 —— 定义写在 DDL 里，校验写在 ETL 脚本里，
加一个必填字段要改两个地方，漏掉一个就开始产生脏数据。

动态本体下两者同源：`schema_json` 里 `required: true`，检测引擎就自动检查它。
**这就是"及时检测商品"能成立的技术前提**。没有这一条，检测规则永远追不上 schema 变化。

### 6.2 现有 `schema_json` 结构（实测）

`kb/seed/ecommerce.yaml` 里现在的形态是：

```yaml
- id: product_sku
  label: 商品SKU
  kind: entity
  schema:
    attributes:
      - {name: title,  type: string,  required: true}
      - {name: price,  type: number}
      - {name: stock,  type: integer}
      - {name: status, type: string}
      - {name: created_at, type: date}
```

只有 `name` / `type` / `required` 三个字段。**要支撑隐式规则，还差四个**：

| 字段 | 用途 | 缺了会怎样 |
|---|---|---|
| `enum` | 值域约束 | 无法检测"status 是 active 还是 actived"，只能检测空值 |
| `min` / `max` | 数值范围 | 无法检测 price = -1 |
| `format` | 日期/URL/手机号 | 无法检测日期写成"2026年13月" |
| `cardinality` | 单值还是多值 | 无法检测"一个 SKU 有两个不同价格" |

这四个字段是**增量**的，不破坏现有数据：没写就是"不约束"。
所以不需要迁移版本，`23 §5.6.3` 的 expand-contract 三步在这里用不上 ——
这也是它值得写进设计的理由：**不是所有变更都需要走三步，
只有"改变已有字段语义"的才需要。纯新增字段是安全的。**

扩展后的形态：

```yaml
- id: product_sku
  schema:
    attributes:
      - name: title
        type: string
        required: true
        min_length: 2
        max_length: 120
      - name: price
        type: number
        min: 0
        max: 9999999
      - name: status
        type: string
        enum: [on_sale, off_shelf, sold_out, draft]
        required: true
      - name: created_at
        type: date
        format: iso8601
        required: true
```

### 6.3 隐式规则：九条，全部由 schema 展开

每次 `detect` 前，从 `onto_type.schema_json` 展开成规则。**不落库、不缓存跨调用**，
理由在 §4.2 提过：缓存会和 schema 漂移。

| # | 规则 | 触发条件 | 判据 |
|---|---|---|---|
| R1 | `required_missing` | `required: true` | 属性为空或缺失 |
| R2 | `type_mismatch` | 有 `type` | 值无法转换成声明类型 |
| R3 | `enum_violation` | 有 `enum` | 值不在枚举内 |
| R4 | `range_violation` | 有 `min`/`max` | 数值越界 |
| R5 | `length_violation` | 有 `min_length`/`max_length` | 字符串长度越界 |
| R6 | `format_invalid` | 有 `format` | 不匹配格式 |
| R7 | `cardinality_violation` | `cardinality: one` | 同一实体同一属性有多条 active 断言 |
| R8 | `relation_domain` | 关系有 `domain` | 断言主体类型 ≠ domain |
| R9 | `relation_range` | 关系有 `range` | 断言客体类型 ≠ range |

R1–R6 逐实体跑，R7–R9 逐断言跑 —— **两类要分开扫**，因为性能特征完全不同：
前者是"每个实体取属性再检查"，后者是"全表扫断言再看两端类型"。

R8/R9 的典型价值：`belongs_to_category` 声明了 `domain=product_sku, range=category`。
如果映射规则把 SPU 也映射成了 `belongs_to_category` 的主体，
R8 会立刻抓出来。**没有这个检查，图里会长出类型不对的边，
而查询时只会表现为"查不到"，不会表现为"数据错了"。**

### 6.4 显式规则的结构

显式规则要能表达"价格突变 30%"这类领域判断。设计上必须**声明式、可校验、
不允许任意代码**（理由同 §3.1）。

```yaml
- id: rule_price_spike
  type_id: product_sku
  name: 价格突变
  kind: explicit
  severity: warn
  spec:
    # 比较对象：同一实体在窗口内的历史值
    compare: previous_value
    attribute: price
    window_days: 30
    condition:
      op: ratio_exceeded
      value: 0.30
    # 例外：这些情况不算异常
    except:
      - when: attribute_changed
        attribute: status         # 从 draft 转 on_sale 时价格会变，正常
      - when: within_days
        value: 7                  # 新品上架 7 天内价格波动正常

- id: rule_title_banned_word
  type_id: product_sku
  name: 标题含违禁词
  kind: explicit
  severity: error
  spec:
    attribute: title
    condition:
      op: contains_any
      value: ["最低价", "全网第一", "国家级"]
```

**`except` 是必须有的，不是可选优化**。没有例外规则，检测结果里 80% 是噪音，
运营看两天就不看了。规则的价值不取决于它抓多少，取决于**误报率**。
一条 30% 误报的规则比没有规则更糟 —— 它会训练用户忽略告警。

### 6.5 操作符白名单

显式规则的 `condition.op` 只能取以下值。**白名单而非黑名单**，
理由和 `kb/service/dsl.py` 不拼 SQL 一样：黑名单永远漏，白名单漏不了。

| op | 语义 | 可编译成 SQL |
|---|---|---|
| `eq` / `ne` | 等于 / 不等于 | ✓ |
| `gt` / `gte` / `lt` / `lte` | 比较 | ✓ |
| `in` / `not_in` | 集合 | ✓ |
| `is_null` / `not_null` | 空判断 | ✓ |
| `contains_any` / `contains_all` | 子串包含（任一/全部） | ✓（LIKE） |
| `matches` | 正则 | ✗（SQLite 需自定义函数） |
| `ratio_exceeded` | 相对变化超阈值 | ✗（需两条断言做比） |
| `deviation_from_mean` | 偏离均值 N 倍 | ✗（需窗口聚合） |

### 6.6 执行引擎：能下推就下推，不能下推要有上限

分两条路径，**不要试图统一**：

**路径 A：可编译成 SQL 的规则 → 一条 SQL 跑完整个 scope**

R1–R6 和 `eq/gt/in/contains` 这类都能下推。属性值存在
`onto_assertion.value_json` 里，SQLite 的 `json_extract` 可以直读：

```sql
-- R3 enum_violation 的编译产物（示意）
SELECT a.subject_id, a.value_json
FROM onto_assertion a
WHERE a.predicate = 'status'
  AND a.status = 'active'
  AND json_extract(a.value_json, '$') NOT IN ('on_sale','off_shelf','sold_out','draft')
```

一次扫全表，比逐实体 Python 循环快一到两个数量级。这就是"下推"的意义。

**路径 B：无法下推的规则 → Python 逐实体，但必须带预算**

`ratio_exceeded` 要拿两个时间点的值做比，SQL 写起来会变成一个自连接，
可读性极差且容易写错。这类走 Python，但：

```python
MAX_PYTHON_ENTITIES = 2000   # 超过就分批
MAX_RULE_SECONDS = 5.0       # 单规则超时
```

超限时**不是静默截断，而是往 `skipped_rules` 里写一条**
`{"rule": ..., "reason": "scope 超过 2000 实体，本次只检查前 2000"}`。
理由同 §5.3。

**一条实测出来的约束**：`23 §6.3` 记过 `json_type(json('299.0')) = 'real'`，
不是 `'number'`。所以 R4 的编译产物里判断数值类型要写
`json_type(v,'$') IN ('integer','real')`，写 `'number'` 会静默返回空集 ——
**规则看起来跑了，实际一条都没检查**。这是最危险的一类 bug。

### 6.7 规则的版本与幂等

规则改了，历史 finding 怎么办？这是必须回答的，否则规则迭代一次，
告警列表就全是"已失效规则产生的告警"。

| 变更类型 | 处理 |
|---|---|
| 改 `severity` | 不影响已有 finding，新产出的用新级别 |
| 改 `condition.value`（如 0.30 → 0.20） | **不追溯**。旧 finding 是当时判定的产物，保留 |
| 删除规则 | finding 保留但标记 `rule_deleted`，不再产出新 finding |
| 改 `type_id` | 视为新规则（`id` 不同），旧规则停用 |

「不追溯」这个选择需要解释：追溯意味着改一次规则就要重算历史所有 finding，
而重算结果会和当时的判定不一致 —— 用户看到"上周的告警消失了"，
第一反应是系统不可靠。**保留历史、只影响未来**，代价是 finding 列表里
会有旧规则的产物，用 `rule_version` 字段标注即可。

## 7 能力派生：挂进 ToolHub

### 7.1 挂接点只有一处

调研结论（`21`/`23` 之后重新核对的）：现有系统里**四处读工具，没有一处关心工具从哪来**。

| 位置 | 现在 | 接本体后 |
|---|---|---|
| `tools/hub.py:459` `get_tool_hub()` | `_register_if_absent(...)` 手写注册 | 末尾加一行 `register_ontology_capabilities(_hub)` |
| `core/capabilities.py:97` | `names = set(hub.names())` | **零改动** |
| `agents/manager.py:151` `_available_tool_names()` | `list(get_tool_hub().names())` | **零改动** |
| `core/subagents.py:338` `_skill_scoped_tools` | 按 `tools_needed()` 裁剪 | **零改动** |
| `core/critic.py:362` | `list(get_tool_hub().names())` | **零改动** |

这是这次调研最有价值的发现：**你的架构里"工具从哪来"和"工具怎么用"已经解耦了**。
`core/capabilities.py:32` 的注释甚至已经写着：

> **关键：清单必须从 ToolHub 动态生成，不能写死。**

理念早就在，只是能力的**来源**还停在手写。所以挂接不是改造，是补一个源头。

### 7.2 注册函数的契约

```python
# kb/service/mount.py

META_OWNER = "ontology:meta"        # 元工具，常驻，不撤回
DERIVED_OWNER = "ontology:derived"  # 衍生工具，随类型变化撤回重建

META_TOOLS: List[Type[Tool]] = [
    KbQueryTool, KbDetectTool, KbTraceTool, KbResolveTool,
]

def register_ontology_capabilities(
    hub,
    conn=None,
    *,
    db_path: Optional[str] = None,
    top_n: int = 12,
) -> MountResult:
    """把本体的能力挂进 ToolHub。

    分两批：
      1. 元工具（4 个，固定）—— 只在不存在时注册，永不撤回
      2. 衍生工具（top_n 个类型的专属工具）—— 先撤后建

    返回 MountResult(registered, unregistered, skipped, errors, version)
    """
```

**为什么元工具要常驻而衍生工具要重建**：元工具不依赖本体内容，
注册一次就能一直用；衍生工具的名字来自类型 id，类型变了名字就变了，
必须整批换掉。混在一起撤回会把元工具一起干掉。

### 7.3 失效重算：三个方案，选第二个

本体变了，能力要跟着变。三种实现：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 重启重建 | 改了本体就重启进程 | 实现最简单 | 每次改建模都要重启才能验证 —— 正是"先独立跑通再接入"要避免的 |
| B 版本号 + 惰性重建 | 每次取工具前比对版本号，变了才重建 | 无需重启、无变化时零开销 | 需要一把锁 |
| C 事件订阅 | 本体变更发事件，监听器重建 | 实时 | 要引入事件总线，单机单用户不成比例 |

选 **B**。理由：方案 A 的缺点恰好是用户明确表达过的痛点（独立跑通的价值
就在于改一次不用重启整个 agent）；方案 C 为了一秒的实时性引入一个子系统，
和"不引入 Neo4j"是同一个判断。

实现：

```python
# 版本号 = max(onto_change.id)，一次索引扫描，微秒级
def capability_version(conn) -> int:
    row = conn.execute("SELECT COALESCE(MAX(id), 0) AS v FROM onto_change").fetchone()
    return int(row["v"])

_mount_lock = threading.Lock()
_last_version: int = -1

def ensure_mounted(hub, conn) -> Optional[MountResult]:
    global _last_version
    v = capability_version(conn)
    if v == _last_version:
        return None                      # 绝大多数调用走这里
    with _mount_lock:
        if v == _last_version:           # 双检：另一个线程刚做完
            return None
        result = _remount(hub, conn)
        _last_version = v
        return result
```

**双检锁不是过度设计**。`get_tool_hub()` 会在多个并发请求里被调用，
重算里有 `unregister_owner` + 批量注册，中间态是"工具表缺了一半"。
另一个线程这时候取工具表，会拿到不完整的能力，规划就会漏掉任务。

**版本号用 `onto_change.id` 而不是时间戳**。时间戳在并发写入时会撞
（`now_iso()` 精度到秒），两个几乎同时的变更可能拿到同一个版本号，
第二个就不会触发重算。`AUTOINCREMENT` 的 id 单调递增，不会撞。

### 7.4 撤回：复用现成机制

`ToolHub.unregister_owner(owner_agent_id)` 已经存在
（`tools/hub.py:200`，注释写着"出了事要能立刻收手"）。

这正是撤回衍生工具需要的东西：

```python
def _remount(hub, conn) -> MountResult:
    # 1. 撤掉旧的衍生工具（元工具不在这个 owner 下，不受影响）
    removed = hub.unregister_owner(DERIVED_OWNER)

    # 2. 按当前本体重算
    caps = derive_capabilities(conn)
    top_types = _top_types_by_usage(conn, n=top_n)

    # 3. 重新注册
    registered = []
    for cap in caps:
        if cap.type_id not in top_types:
            continue                      # 低频类型走元工具
        tool = _make_derived_tool(cap)
        try:
            hub.register_python_tool(tool, owner_agent_id=DERIVED_OWNER,
                                     visibility="global")
            registered.append(tool.name)
        except ValueError:
            pass                          # 已存在同名（理论上不会，撤过了）
    ...
```

**衍生工具的命名规则**：`kb_{verb}_{type_id}`，例如 `kb_detect_product_sku`。

这条规则很重要，因为技能会引用这些名字。命名必须**确定可推导**：
给定 `(verb, type_id)` 就能算出工具名，不需要查表。这样：
- 技能作者能自己写对名字
- 校验时不需要"名字映射表"这种第三份真相
- 类型废弃 → 工具消失 → 技能校验失败（见 §8）

### 7.5 注册 ≠ 授权

必须强调，因为这里容易出安全事故：

`visibility="global"` 只表示工具**在工具表里可见**，不表示任何调用方都能用。

实际能不能用，由三层过滤决定：

```
ToolHub 里存在                    ← 注册决定
   ↓
角色白名单（core/subagents.py）    ← 角色配置决定
   ↓
技能 required_tools（tools_needed）← 技能声明决定
```

所以 `kb_assert`、`kb_notify` 这类写动词注册进去是安全的 ——
它们不会自动被子智能体拿到，除非角色配置里显式给出。

**但有一个例外必须处理**：主 Agent（不是子智能体）走的是
`agents/manager.py` 的 `_available_tool_names()`，那里读的是全量
`hub.names()`，**没有角色白名单这一层**。所以如果 `kb_notify` 注册成全局，
主 Agent 可以直接调用它发消息。

处理方式有两种，选后者：

- 用 `visibility="owner"` 限制 —— 但主 Agent 不是 owner，它就拿不到了，过度限制
- **在工具内部做闸门**：`KbNotifyTool.execute()` 检查 `config.kb_notify_enabled`，
  没开直接返回"未启用"。和 `Tool.required_flag` 的机制一致

选后者的理由：`required_flag` 已经是项目里现成的模式（`tools/base.py:91`），
`PythonSource` 扫描时会查这个开关。用它比新造一套可见性规则更省事，也更符合现有约定。

## 8 技能侧：能力 id 必须可校验

### 8.1 这个 bug 的精确位置

之前我说"技能引用了不存在的工具，系统不报错"。核对代码后，实际情况更精确，
也更值得修：

```
skills/validator.py:validate_skill()   只校验 steps[].tool
skills/models.py:tools_needed()        required_tools 非空时，忽略 steps[].tool
core/subagents.py:_skill_scoped_tools  用 tools_needed()
```

**校验读的字段和运行时读的字段不是同一个。**

活证据是 `skills/user/选品评分与上架文案@1.0.0.yaml`：

```yaml
steps: []                     # ← 空
required_tools:
- ecom_product_scorer         # ← 这两个在 tools/ 里根本不存在
- ecom_listing_gen
```

`steps` 是空的，所以 `validate_skill` 的循环一次都没进，**校验通过**。
运行时的 `tools_needed()` 返回那两个名字，`_skill_scoped_tools` 求交集得空，
退回全量工具表 —— 技能以为自己有专用工具，实际拿到 20 个通用工具让模型自己挑。

这就是"工具漂移"的成因，而 `_skill_scoped_tools` 本来是为了解决它。

### 8.2 修法：让校验和运行时读同一个函数

```python
# skills/validator.py
def validate_skill(skill: Skill, tool_names: Iterable[str] = ()) -> List[str]:
    ...
    # 新增：校验 tools_needed()，而不是只校验 steps[].tool
    # 理由：tools_needed() 是显式优先的，required_tools 会覆盖 steps
    # 只查 steps 等于漏掉 required_tools 这条路
    for t in (skill.tools_needed() if hasattr(skill, "tools_needed") else []):
        if t and tool_set and t not in tool_set:
            issues.append(f"技能声明了未知工具 {t}")
```

**这一条不依赖本体，可以立刻做**。现在就有悬空技能在跑，
它是纯 bug，等的不是架构，是一个五行的改动。

### 8.3 为什么这个 bug 与"自主挂接"是同一件事

看起来是个孤立的校验疏漏，实际不是。它暴露的是同一个结构问题：

> **能力没有稳定的 id，所以引用它的人无从校验。**

`ecom_product_scorer` 这个名字是凭空写的，没有任何地方定义过它。
写的时候不会报错，跑的时候静默降级，所以你直到翻代码才发现。

本体驱动能力之后，这个问题结构性地消失了：

| 环节 | 现在的悬空技能 | 本体驱动之后 |
|---|---|---|
| 工具名从哪来 | 人随手写 | `kb_{verb}_{type_id}`，由本体决定 |
| 名字写错了 | 不报错 | 类型不存在 → 工具不存在 → 校验失败 |
| 类型废弃了 | 不报错 | 工具撤回 → 校验失败 |
| 能力缺口 | 无人知道 | `call_tool` 对未知工具调 `record_gap`（`tools/hub.py:245`） |

**这就是"自主挂接"真正的价值**：不是省了写代码的力气，
而是让"引用了不存在的能力"变成编译期错误，而不是运行时的静默降级。

### 8.4 能力 id 的引用形态

技能里怎么写？两种，按场景选：

| 场景 | 写法 | 校验粒度 |
|---|---|---|
| 技能服务多个类型 | `required_tools: [kb_detect]` + step params 里指定 type | 只校验元工具存在 |
| 技能只服务一个类型 | `required_tools: [kb_detect_product_sku]` | 校验到类型级 |

**推荐后者**，因为校验粒度决定了这个机制有没有用。如果所有技能都只写
`kb_detect`，那"类型废弃导致技能失效"这件事永远不会被发现 ——
元工具永远存在，校验永远通过。

只有技能明确写 `kb_detect_product_sku`，类型 `product_sku` 被废弃时
工具撤回、校验失败、技能进 `probation`，这条链才闭合。

## 9 事件源：让"及时"真正成立

这一节只定接口，不实现。因为它和本体解耦，是另一个子系统。

### 9.1 现状：系统是对话驱动的

现在没有商品变更事件流。用户问，才查；不问，什么都不发生。

所以"及时检测商品"的"及时"目前只能做到"用户问的时候顺带查一下"。
这不是设计缺陷，是范围限制，要说清楚。

### 9.2 三种事件来源

| 方式 | 做法 | 延迟 | 成本 | 适用 |
|---|---|---|---|---|
| **Push** | 商品中心 webhook 回调 | 秒级 | 要对方支持 + 要暴露端口 + 要防重放 | 有对接条件的生产环境 |
| **Poll** | 定时拉变更集 | 分钟~小时 | 要水位 + 要处理"漏变更" | **起步推荐** |
| **Reconcile** | 定时全量比对 checksum | 天级 | 要全量读 | 兜底，防止 poll 漏数据 |

起步用 **Poll + Reconcile 兜底**。理由：Push 需要对方配合，
而 Reconcile 能兜住 Poll 的所有漏网 —— 这和 `kb/ingest` 里
`onto_raw` 的 checksum 机制是同一套东西，已经实现了。

### 9.3 Poll 的水位

复用 `23 §2.4` 定的三种水位模式，但对商品场景有一处必须额外处理：

**"已删除"的变更往往不在变更集里**。商品中心按 `updated_at` 给变更时，
被删除的记录通常不会出现（记录没了）。所以 poll 之后必须做一次
"本地有、远端没有"的比对，否则下架商品在知识库里永远 active。

这是接入层的一类通病：**数据源只说它有什么，不说它没什么**。
对增量拉取来说，"不存在"本身就是信息，但没有任何字段承载它。
正确做法：

```sql
-- 本轮拉到的 id 集合记为 seen
-- 上轮 active 但本轮没 seen 的 → 标记 pending_delete，连续 2 轮没出现才真删
```

"连续 2 轮"是刻意的：一次网络抖动或分页漏读，不该导致商品被下架。
**删除是破坏性操作，宁可慢一轮。**

### 9.4 触发后的链路

```
poll 发现变更
  → ingest（复用现有 pipeline，幂等靠 checksum）
  → 标记 onto_change（kind=entity, action=update）
  → 触发 detect（scope = 变更的那批实体，不是全量）
  → finding 有 error 级 → notify（写 outbox）
```

关键在第三步 **scope 只含变更实体**。全量检测在商品库上不可行
（十万级实体），而增量检测的代价和变更量成正比，可以做到分钟级。

这也是为什么 `kb_detect` 的 `scope` 参数必须支持"按实体 id 列表"，
而不只是 `where` 条件。

## 10 分阶段实施

按"价值 ÷ 依赖"排，不按技术优雅排。

| 阶段 | 内容 | 依赖 | 验收标准 | 量级 |
|---|---|---|---|---|
| **P1** | 修 `validate_skill` 校验 `tools_needed()` | 无 | 悬空技能被报错；现有 15 个技能全部过一遍 | 五行 |
| **P2** | `schema_json` 补四个字段 + 隐式规则引擎（R1–R6） | 无 | 给一张商品 CSV，`detect` 能抓出必填缺失和枚举越界 | 中 |
| **P3** | `kb_detect` 元工具 + `onto_rule` / `onto_finding` 表 | P2 | finding 幂等；`skipped_rules` 有内容；超 2000 实体分批 | 中 |
| **P4** | 能力派生 + 注册进 ToolHub（元工具 4 个） | P3 | `hub.names()` 里出现 4 个 kb 工具；`capabilities.py` 清单自动体现 | 小 |
| **P5** | 衍生工具（top 12 类型）+ 失效重算 | P4 | 改本体不重启，工具自动换；类型废弃后工具消失 | 中 |
| **P6** | 显式规则 + `except` + 操作符白名单 | P3 | 价格突变规则误报率 < 20%（用真实数据标定） | 中 |
| **P7** | 事件源（poll + reconcile） | P3 | 商品变更后 5 分钟内产出 finding | 大 |

**P1 必须先做**，虽然它和本体无关。理由：它只有五行，收益是
"以后所有技能的工具引用都可校验"，是后面所有阶段的前提。
先做它，P5 的"类型废弃 → 技能失效"链条才有意义。

**P2 必须在 P3 之前**。反过来做的话，`kb_detect` 会是个没有规则的壳，
只能返回空列表 —— 而空列表会被模型理解成"没问题"，比没有这个工具更糟。

**P7 可以最后**。没有它，前面六个阶段的全部能力都在，只是从"及时"退化成"按需"。
这是唯一一个可以长期缺位的阶段。

## 11 决策记录

每条都写了否掉的方案，因为"为什么不做"比"做什么"更容易被后来的人推翻。

**D1 否掉"每个类型生成一个工具"。**
50 类型 × 4 动词 = 200 工具 ≈ 24000 token 描述。而
`agents/manager.py:151` 每次规划都塞全部工具名，`_skill_scoped_tools`
的存在就是为了对抗工具过多。不能一边解决它一边制造它。

**D2 否掉"LLM 生成检测函数并挂接"。**
原因不是保守，是它会被数据驱动执行：本体是数据，数据来自 CSV 导入和映射规则，
让数据决定生成什么代码等于绕过 `tools/python_exec.py` 的 AST 黑名单。

**D3 否掉"能力全量落库"。**
50 类型 × 7 动词 = 350 行要维护，新增类型要插 7 行，新增动词要回填全部。
只存例外（`onto_capability`），默认值写在代码里。

**D4 选"版本号 + 惰性重建"，不选重启也不选事件总线。**
重启的缺点是用户明确提过的痛点（独立跑通就是为了不重启）；
事件总线为了一秒实时性引入一个子系统，和"不引入 Neo4j"同一判断。

**D5 选"衍生工具先撤后建"，不选"增量更新"。**
增量更新要算差集（哪些类型新增/删除/改名），差集算错的后果是工具表里
残留指向已删类型的工具，调用时报"类型不存在"。整批换掉没有这个风险，
代价只是重算 12 个工具，微秒级。

**D6 选"`notify` 默认关闭"，不选"默认开启"。**
它是唯一有外部后果的动词。安全默认值应该是"不说不动"。

**D7 选"finding 不追溯"，不选"规则改了重算历史"。**
追溯会让用户看到"上周的告警消失了"，第一反应是系统不可靠。

**D8 否掉"把 detect 做成独立 Agent"。**
本体是能力不是人格。加一个角色，Manager→Learning→Orchestrator 之间
就多一跳，而 detect 是个纯函数：输入 scope 和规则，输出 findings。没有规划需求。

**D9 选"空结果分三种状态"，不选"返回裸 `[]`"。**
模型不会怀疑工具，它会把"没有数据"当事实。裸 `[]` 是静默错误。

**D10 选"元工具 + top 12 衍生"，不选"全部衍生"或"全部元工具"。**
全部元工具：模型要记住哪个类型有哪些属性，类型多了会记错。
全部衍生：工具爆炸。用使用频次切分，且升级/降级都自动。

## 12 待拍板

按紧急程度排，前三条影响 P2/P3 的实现。

1. **`schema_json` 补四个字段（enum/min-max/format/cardinality），同意吗？**
   这是 P2 的前提。补了之后，隐式规则的价值立刻兑现；不补，`detect`
   只能查"必填缺失"一种，价值大打折扣。

2. **`detect` 的 scope 上限 500 / 2000 怎么定？**
   我按"单次调用 500 实体、单规则 2000 实体"写的。这个数字取决于你的
   商品量级 —— 如果单个类型就 10 万实体，分批策略要重新设计。

3. **衍生工具的 top N = 12 合适吗？**
   这个数字是从 `CAPABILITY_BLOCK_MAX_CHARS = 900` 倒推的。
   如果你的 prompt 预算不同，要跟着调。

4. **P8 事件源如果长期不做，"及时检测"用什么替代？**
   替代方案是"用户每次打开商品分析页面时自动跑一次增量检测"。
   这是产品决策，不是技术决策。

5. **要不要保留 `ecom_product_scorer` / `ecom_listing_gen` 这两个能力？**
   它们是悬空引用。要么补实现（可以用 `create_tool` 声明式造），
   要么从技能里删掉。按 P1 修完之后，这个技能会被标为有问题，
   你得决定是修技能还是补工具。

## 13 与 21/22/23 的关系

一句话：**前三篇把知识库建起来，这一篇把它接到 agent 手上。**

| 前三篇的产出 | 本篇怎么用 |
|---|---|
| `onto_type` 六表 + `schema_json` | 能力的"名词"来源；隐式规则从 `schema_json` 展开 |
| `kb/service/query.py` 的 DSL | `kb_query` 的实现，本文只加"空结果分三种" |
| `kb/onto/entities.py::search` | `kb_resolve` 的实现，本文只加"返回候选而非答案" |
| `onto_raw.checksum` | §9 的 reconcile 直接复用，不另造 |
| `QUERYABLE_TYPE_STATUSES` | `derive_capabilities` 的第一条规则：draft 不产生能力 |
| `23 §7.4` 的写闸门 | `kb_assert` / `kb_tag` 的前置条件 |

**没有一处需要推翻前三篇的设计**。这是分层的意义：
建库和挂接之间只依赖接口，不依赖实现。
