## 1. 现状诊断

代码里已经有"分层意图识别"的说法（`core/intent_detector.py` 头部注释、`agents/manager.py` 的
`plan()` docstring），但**实际是一条关键词瀑布**，不是分层决策。分层只体现在"省 LLM 调用"，
没有体现在"决策质量"。

### 1.1 实际执行路径

```
ManagerAgent.plan(user_input)
  ├─ IntentDetector.detect()          ← Layer 0/1，纯关键词
  │    ├─ 命中 GREETING/FAREWELL/...  → 直接 CHITCHAT，结束
  │    ├─ 命中 TEACH                  → 直接 TEACH，结束
  │    ├─ 命中 RETRY                  → 标记 is_retry，交给 LLM
  │    └─ 命中工具关键词              → 返回 WEATHER/SEARCH（但下游没人接）
  ├─ should_learn_skill()             ← 又一组关键词
  ├─ _is_management_intent()          ← 第三组关键词
  └─ _llm_plan()                      ← Layer 2，intent 是自由文本
```

三组互不相干的关键词表各自决定路由，且都在 LLM 之前生效。

### 1.2 已验证的精度问题

以下结论均在当前代码上实测复现：

| # | 问题 | 实测 |
|---|---|---|
| P1 | `_MANAGEMENT_KEYWORDS` 含 `"查看"`，子串匹配无边界 | `"查看北京天气"` → 判定为**技能管理**意图，不查天气 |
| P2 | `_TEACHING_KEYWORDS` 含 `"要"` / `"遇到"` / `"以后"` | `"遇到雨天要带伞"`、`"以后我们开会要提前十分钟"`、`"这个方案要分三步"`、`"我要一个计算器"` → 全部判定为**教导**意图 |
| P3 | Layer 1 工具关键词含 `"查"` / `"怎么"` / `"为什么"` | `"搜索是一个动词吗"` → 判定为 `search` 并带 `tool=web_search` |
| P4 | `IntentCategory` 有 16 个，`IntentType` 只有 6 个 | `WEATHER / SEARCH / CALCULATE / TRANSLATE / CODE / CUSTOM / CLARIFY` **无落地分支**，`CLARIFY` 从不产生 |
| P5 | `PLAN_SCHEMA.properties.intent` 是 `{"type":"string"}` | LLM 返回自由文本，再用 `_is_simple_intent()` 对**LLM 自己写的散文**做关键词匹配来二次分类 |
| P6 | Layer 1 的工具关键词命中后仍会走 LLM | 该层结果对最终路由无影响，只污染 `tool_type` 字段 |

### 1.3 根因

1. **意图与规划耦合**：一次 LLM 调用同时干"这是什么意图"和"调哪些工具"。意图错了污染规划，
   规划错了也污染意图，无法分别评估、分别优化。
2. **闭集被当成开集**：内部有 16 个意图标签，但从未把这份闭集交给 LLM；LLM 拿到的是自由文本
   `intent` 字段。
3. **规则用黑名单式关键词**：靠"出现某个词"来判定语义类别，没有结构/句式/上下文约束。
4. **没有置信度语义**：规则命中就是终局（哪怕只有 0.7），LLM 输出就是终局（哪怕模棱两可）。
5. **CLARIFY 缺席**：识别不了就硬猜，猜错就走错分支，没有"我不确定"的出口。

## 2. 目标设计

### 2.1 四层结构

```
┌─ L0 守卫层 ────────────────────────────────────────────────┐
│ 纯确定性，0 次 LLM，0 次 LLM 也对                           │
│ · 空输入 / 超长输入 / 系统指令 → 直接返回                    │
│ · 整句归一化后精确命中闲聊白名单 → CHITCHAT (conf=1.0)       │
│ · 结构性信号检测（见 2.3）→ 命中即定，不进 LLM               │
└───────────────────────────┬────────────────────────────────┘
                            ▼ 未命中
┌─ L1 判别层 ────────────────────────────────────────────────┐
│ 一次**小模型 / 低温度**调用，只做闭集分类                    │
│ 输入：user_input + 最近 2 轮 + 召回的长期记忆摘要            │
│ 输出：{label ∈ 闭集, confidence, slots, needs_clarify}      │
│ 退出条件：confidence ≥ τ₁(0.75) → 定案                      │
│           confidence < τ₁ → 升级 L2（带 L1 结果作为先验）    │
└───────────────────────────┬────────────────────────────────┘
                            ▼
┌─ L2 规划层 ────────────────────────────────────────────────┐
│ 现有的 LLM plan 调用（保留），但**职责收窄为规划**             │
│ 输入：L1 的 label（作为强约束注入）+ 召回记忆 + 技能/工具清单 │
│ 输出：selected_skill + tool_tasks(DAG)                      │
│ 不再输出 intent                                            │
└───────────────────────────┬────────────────────────────────┘
                            ▼
┌─ L3 澄清层 ────────────────────────────────────────────────┐
│ L1 低置信 / L2 无法产出工具 / 关键 slot 缺失                 │
│ → 生成**一个**带候选项的具体问题，而不是硬猜                 │
└────────────────────────────────────────────────────────────┘
```

### 2.2 意图闭集（对齐 `IntentType`，去掉死标签）

路由层只需 6 个标签，与 `IntentType` 一一对应，不再有两套枚举：

| label | 含义 | 后续动作 |
|---|---|---|
| `chitchat` | 寒暄/确认/感谢/否定/询问身份 | 直接回答，不进 critic |
| `teach` | 用户要教新技能/方法论 | 走 `SkillTrainer` |
| `manage` | 技能管理（列出/版本/回滚/启停） | 走技能管理接口 |
| `retry` | 重做上一轮 | 取上轮 tool_tasks 重放 |
| `task` | 需要工具/技能完成 | 进 L2 规划 |
| `clarify` | 意图不明或缺关键信息 | 进 L3 澄清 |

`WEATHER / SEARCH / CALCULATE / …` 这些**不是意图，是任务子类**——它们属于 L2 的规划结果，
不该在 L1 与 `chitchat` 并列比较。`IntentCategory` 里那 6 个任务子类应降级为
`TaskKind`，只在 L2 规划后作为标签存在。

> **决策（2026-07-22）**：L1 **不细分到工具类型**。是否需要调工具、调哪个工具，
> 全部由 L2 规划层决定。L1 只回答"这是什么意图"，保持 6 个标签的闭集简单，
> 这样评估集可以保持稳定，误判成本也最低。
>
> 推论：L1 的输出**不携带** `tool_type` 字段（现在的 `IntentResult.tool_type`
> 对下游无人使用，属于死字段，应删）。

### 2.3 结构守卫:规则**不判意图**(⚠️ 已推翻原设计)

> **本节原来写的是"如何把 L0 规则写得更精确"。
> 真机基线证明这个方向本身就错了 —— 现已推翻。**

#### 实测(130 条标注用例,`deepseek-flash`)

| 做法 | 准确率 |
|---|---|
| 规则(L0)+ LLM(L1) | **94.7%** |
| **只有 LLM** | **97.7%** |

规则**不是没帮上忙,是在拖低准确率**。

#### 为什么用规则做意图识别是错的

1. **意图是语义问题,规则只看得到字面。**
   「教我怎么用这个工具」和「教我一种排查方法」
   字面都含「教我」,语义相反(一个是助手教用户,一个是用户教助手)。
2. **每条规则都是在猜"用户大概会怎么说"。**
   一万种说法,猜不完;而且**猜错的时候是静默的** —— 没人会发现。
3. **最严重的是它抢在 LLM 前面。**
   命中就 `return`,这句话 LLM 根本看不到。
   真机基线里的 10 条错判,我把提示词连改 5 版都没效果,
   因为**那段代码根本没被执行**。

#### 现在的设计:守卫只判结构事实

```python
def detect(self, text):
    if not text.strip():
        return IntentResult(CLARIFY, detail="空输入")   # 结构事实
    return IntentResult(UNKNOWN)   # 余下全部交给 L1
```

**就这一条。没有任何"猜用户怎么说"的规则。**

判据(写进代码注释):**如果一条规则的成立依赖"用户大概会这样表达",它就不该在这里。**

关于「你好」「列出所有技能」这种"看起来很明显"的:
**"看起来明显"不是判据。** 真机基线里规则正是靠"看起来明显"
把 10 条判错的。它们全部走 L1。

#### 代价

原来免费吃掉的那 19 条,现在要去问模型 → **LLM 调用量 50% → ~100%**。
一轮对话本来已经 2~3 次调用,多这一次得到的是 +3 个百分点准确率和"不会再被规则默默带偏"。

#### 一个反面教训

代码里一度同时存在**两条** teach 判定路径:一条裸关键词、
一条结构化规则,而裸关键词那条排在前面。
旁边还写着注释"原先用裸串表导致误判,现在要求方法论载体" ——
**注释写了要修的话,代码没删。** 这种"两处判同一件事"的结构,必然漂移。

### 2.4 L1 的提示词与输出契约

```json
{
  "type": "object",
  "properties": {
    "label": {
      "type": "string",
      "enum": ["chitchat", "teach", "manage", "retry", "task", "clarify"]
    },
    "confidence": {"type": "number", "minimum": 0, "maximum": 1},
    "slots": {
      "type": "object",
      "properties": {
        "city": {"type": "string"},
        "date": {"type": "string"},
        "target_skill": {"type": "string"},
        "referent": {"type": "string"}
      }
    },
    "needs_clarify": {"type": "boolean"},
    "reason": {"type": "string"}
  },
  "required": ["label", "confidence", "reason"]
}
```

提示词要点：

1. **给出闭集定义**（每个 label 一句定义 + 2 个正例 + 1 个易混反例）
2. **明确易混边界**：
   - "查看北京天气" → `task`（不是 `manage`）
   - "遇到雨天要带伞" → `task`/`chitchat`（不是 `teach`）
   - "以后做 X 就按 Y 来" → `teach`
3. **允许输出 `clarify`** 且不惩罚
4. 温度 0.0，`reason` 要求一句话

### 2.5 置信度与升级策略

| 层 | 产出 | 阈值 | 不达标时 |
|---|---|---|---|
| L0 | conf = 1.0 | — | 进入 L1 |
| L1 | conf ∈ [0,1] | τ₁ = 0.75 | 升级 L2，intent 用 L1 label（带 `uncertain=true`） |
| L2 | 有无工具任务 | — | 无任务且 L1 低置信 → L3 澄清 |

- LLM 不可用 / 调用失败 → 降级到 L0，再降级到"直接回答"（不崩）
- 记录每层的 `escalation_level` 与 `confidence`，进日志与可观测面板

### 2.6 L3 澄清

- 只问**一个**问题，带 2~3 个候选项（从 `slots` 缺失项或技能清单里取）
- 澄清轮次上限 1 轮，超限则走兜底回答并记录为"未解决"
- 澄清本身是短轮次，**不进 critic、不写长期记忆**

## 4. 评估闭环

现在的 `tests/test_intent_dataset.py` 只测规则层，**LLM 层零覆盖**——这正是问题没被发现的原因。

建议建立双通道评估集 `tests/data/intent_eval.jsonl`：

```jsonl
{"input": "查看北京天气", "label": "task", "layer": "L1", "note": "曾被误判为 manage"}
{"input": "遇到雨天要带伞", "label": "task", "layer": "L1", "note": "曾被误判为 teach"}
{"input": "以后做日报就按三段式来", "label": "teach", "layer": "L1"}
{"input": "把版本回滚到 1.0.0", "label": "manage", "layer": "L1"}
{"input": "你好", "label": "chitchat", "layer": "L0"}
```

指标：

| 指标 | 目标 |
|---|---|
| L0 精确率 | 100%（白名单+结构规则，出现误判即 bug） |
| L1 总体准确率 | ≥ 90% |
| 易混对（manage/task、teach/task）准确率 | ≥ 95% |
| 升级率（L0 未命中 → L1） | 观测项，异常升高说明 L0 过窄 |
| 澄清率 | 观测项，异常升高说明 L1 判别差 |

跑法：
- `pytest tests/test_intent_detector.py` —— 规则层（无 LLM，CI 必跑）
- `pytest tests/test_intent_llm_eval.py --live` —— LLM 层（需 API key，进 nightly）

改提示词 / 改规则后跑一遍评估集，出混淆矩阵。

## 5.1 P1 已完成（I-02，2026-07-22）

### 落地文件

| 文件 | 作用 |
|---|---|
| `core/intent_labels.py`（新） | 意图闭集 `IntentLabel`（6）、任务子类 `TaskKind`（6）、`LABEL_DEFINITIONS`（每个标签：定义 + 正例 + 易混反例）、`INTENT_RESULT_SCHEMA`（枚举约束）、提示词构造、解析 |
| `core/llm_judge.py`（新） | `L1Classifier`：一次 LLM 调用做闭集分类，输出 `IntentDecision(label/confidence/slots/needs_clarify/reason)`；非法标签 / 非法 JSON / 调用异常一律降级为 `None` |
| `core/intent_detector.py`（改） | 降级为 **L0 守卫层**：只做"证明强意图"，不定案就交 L1。`IntentCategory` 保留 16 个作为 **L0 规则细节**，通过 `_CATEGORY_TO_LABEL` 映射到闭集 |
| `agents/manager.py`（改） | `plan()` 改为 L0→L1→L2 编排；`PLAN_SCHEMA` 去掉自由文本 `intent`，改为 `plan_detail`；删除 `_is_simple_intent()`；`_is_management_intent` / `should_learn_skill` 改为复用 L0 的同一份规则 |

### 关键实现决策

1. **意图与规划彻底解耦**：`PLAN_SCHEMA.properties.intent`（自由文本）已删除。
   L2 的系统提示词明确写"意图已经由上游判别层判定，你不需要重新判断意图"。
   LLM 再也拿不到"意图"这个字段，就没法自由发挥。
2. **L1 的标签作为强约束注入 L2**：`_build_intent_hint_block()` 把 L1 的
   `label` / `confidence` / `slots` 拼成一段固定文本塞进 L2 的用户提示词，
   让规划器知道"这轮已经被判成什么"。
3. **低置信不放弃，升级 L2**（D4）：L1 置信度 < τ₁(0.75) 时**不**直接定案，
   带着 L1 的结果升级 L2 兜底。宁可多调一次工具，也不要漏答。
   `PlanResult.intent_uncertain=True` 标记这次是"不确定着走的"。
4. **L1 失败不拖垮链路**：LLM 异常 / 非法标签 / 非法 JSON → `classify()` 返回 `None`
   → 直接进 L2 → L2 也失败 → 兜底"直接回答"。
5. **三处规则精度修复**（在 P0 基础上继续修）：

   | 问题 | 修法 |
   |---|---|
   | 短闲聊词埋在词里：`执**行**` 命中确认词"行"、`**hi**s` 命中问候词 | 新增 `_matches_at_boundary()`：关键词必须落在**小句边界**（前后是句首/句尾/标点），等价于中文的"词边界" |
   | 单字泛词误判天气：`讲个冷**笑话**` 命中"冷"、`这个方案太**热**了` | "冷/热/晴" 从强关键词降级为**上下文依赖词**，必须与"今天/明天/现在/当地…"同句出现才判天气 |
   | L0 与 L1 各写一套教导/管理规则 | 规则本体收敛到 `core/intent_detector.py`，L0 守卫层与 `ManagerAgent` 共用同一份常量与判定函数 |

### 三条硬约束

1. **只问一个问题**，并给 2~3 个候选项 —— 一次问一堆等于没问
2. **连续澄清上限 1 轮** —— 用户不答就直接答，不许把人卡在澄清里
   （正常推进的轮次会把计数归零，所以"问一句 → 用户答 → 再问一句"是允许的）
3. **澄清轮不进 critic、不写长期记忆** —— 它不是一次任务执行

### 顺带修掉一个真实缺陷：前端没回 ACK

实机验证澄清链路时发现：服务端 `publish()` 之后**只收到第一个事件**就卡住。

根因：`fastapi-websocket-rpc` 是**请求/响应式**协议 —— 服务端 `publish()` 会等客户端
回 ACK 才返回，而库里 `default_response_timeout` 默认 `None`（**永不超时**）。
前端 `websocket.js` 收到 `notify` 后只处理、不回响应 → 服务端那一轮的事件投递被永久卡死
（表现就是"转圈不动"）。

两处都补了：

| 位置 | 修法 |
|---|---|
| `frontend/src/websocket.js` | 收到 `notify` 后回 `{"response": {result, result_type, call_id}}` —— 协议正确性 |
| `backend/websocket_handler.py::push_event` | `asyncio.wait_for(..., PUSH_TIMEOUT=10s)` —— 客户端不按协议来时也不把这一轮卡死 |

实测：回 ACK 时全部事件即时送达；不回 ACK 时事件仍全部送达（服务端超时后继续推进），
不再永久挂死。

## 6. 模型选型：L1 用哪个模型

### 6.1 L1 这一层到底做什么

一句话：**把一句话归到 6 个标签之一，并给出置信度**。

具体输入输出：

```
输入: "查看北京天气" + 最近 2 轮对话 + 召回的用户画像摘要
输出: {label: "task", confidence: 0.93, slots: {city: "北京"}, needs_clarify: false, reason: "查询天气"}
```

它**不做**的事：不选工具、不选技能、不规划步骤、不生成回答。

### 6.2 为什么之前会想到"分一个小模型"

当时的理由是：分类任务看起来"便宜"，而主模型是"贵的"。但重新审视后，
这个理由并不成立——**主模型做闭集分类的准确率通常不比小模型差**，
小模型唯一稳定的优势是延迟和单价，而不是准确率。

而**把 L1 拆出来单独做**，真正的收益是另外三条，与用哪个模型无关：

| 收益 | 说明 |
|---|---|
| **可评估** | 意图分类的准确率可以单独度量，不用被规划质量干扰。现在意图和规划混在一次调用里，意图错了污染规划，反之亦然——**无法归因** |
| **提示词干净** | 分类提示词只放标签定义和正反例；规划提示词只放技能清单和工具清单。混在一起两边都变长、效果都变差 |
| **参数可分开调** | 分类要 `temperature=0`（要确定性）；规划需要创造性（要高一点温度）。混在一起只能取一个折中值 |

### 6.3 结论与落地

> **决策（2026-07-22）：默认复用主模型。**

- L1 用**同一个** LLM provider / 模型，不新增模型配置项
- 但 `temperature=0`、`max_tokens` 限制小（分类输出很短），走独立的调用参数
- **保留一个可选覆盖**：新增 `INTENT_MODEL` 配置项，**默认为空 = 复用主模型**。
  只有显式配置时才切换到别的模型。这样将来发现主模型太慢/太贵时，
  改一行配置即可，不用改代码

所以"分一个模型"这件事从**架构决策**降级为**配置项**——不预设、不绑定、随时可切。

### 6.4 成本

| 项 | 影响 |
|---|---|
| 多一次 LLM 调用 | 每轮 +1 次调用。L0 命中（L0 白名单闲聊、结构化强意图）的路径**完全免除** |
| 延迟 | 主模型约 +300~800ms。若实测影响体验，再用 `INTENT_MODEL` 指向小模型 |
| 成本 | 分类输出仅 ~50 token，相比规划 + 生成的 token 量占比很小 |

| 项 | 影响 |

## 8. 明确不做的事

- **不做**端到端的多 Agent 投票分类（成本高、收益不确定，先把单分类器做准）
- **不做**在线自学习分类器（先用离线评估集把提示词调稳）
- **不做**把 `TaskKind`（天气/搜索/计算…）继续留在 L1——它们是规划结果，不是意图
- **不**让 L0 的规则去覆盖 L1 的结论（规则只在 L1 之前"省调用"，不做二次否决）
- **不**默认引入第二个模型——`INTENT_MODEL` 留空即可，切换只是改配置
